# Ссылки на товары в RetailCRM ведут на 404 — причина и решение

Разбор от 2026-08-28. Работы ведутся на стороне сайта (1С-Битрикс).

---

## Что сломано

Админ отправляет клиенту ссылку на товар из карточки в CRM — клиент получает 404.

Проверены все 456 товаров каталога, каждая ссылка открыта на сайте:

| Что происходит по ссылке | Товаров |
|---|---|
| ведёт точно на карточку | 110 (24%) |
| ведёт на карточку, но через 301-редирект | 199 (44%) |
| уводит на раздел — карточки клиент не видит | 46 (10%) |
| чистый 404 | 101 (22%) |

**Нерабочая ссылка — у 147 товаров из 456, почти каждый третий.**

Цифры сняты 2026-08-28 и плывут по ходу дня: за несколько часов между двумя прогонами
12 товаров перешли из рабочих в «уводит на раздел».

---

## Где ломается

Не в RetailCRM. Она записывает ровно то, что ей дал Битрикс.

Цепочка: Битрикс генерит файл выгрузки
`https://barhatflowers.ru/bitrix/catalog_export/retailcrm.xml` (ежедневно около 19:30)
→ RetailCRM его забирает. Битая ссылка есть **уже в этом файле**.

Модуль `intaro.retailcrm` берёт ссылку готовой у Битрикса и просто приклеивает домен
([lib/icml/xmlofferbuilder.php](https://github.com/retailcrm/bitrix-module/blob/master/intaro.retailcrm/lib/icml/xmlofferbuilder.php)):

```php
$this->xmlOffer->url = $item['DETAIL_PAGE_URL']
    ? $this->serverName . $item['DETAIL_PAGE_URL']
    : '';
```

Своей логики построения ссылок и настроек URL у модуля нет — в форме профиля выгрузки
таких полей не существует. **Поэтому в настройках модуля и в самой CRM крутить нечего.**

### Главное: ссылку определяет первая привязка к разделу

Не основной раздел товара. Это неочевидно и стоило одной неверной гипотезы.

У «Нежности» основным разделом стоит «Клубнично-цветочные букеты», canonical у страницы
правильный — а в выгрузку уходит `/catalog/vse-bukety/nezhnost/`.

Механика: модуль выбирает товары запросом **без фильтра по разделу**. Битрикс на такой
запрос отдаёт **по строке на каждую привязку** элемента к разделу, в каждой свой
`DETAIL_PAGE_URL`. Модуль берёт первую строку — то есть привязку, созданную раньше
прочих. Основной раздел в этом не участвует.

Проверено на всех 456 товарах: первая привязка определяет ссылку **однозначно, без
единого исключения**. Разложение по 355 товарам (без «Товаров МС»):

| Что стоит первой привязкой | Ссылка верна | Неканоническая | Нет страницы |
|---|---|---|---|
| навигационный раздел («Все букеты», «Кому», «Событие») | 0 | 152 | 13 |
| товарный раздел | 110 | 47 | 33 |

Если первой стоит навигационный раздел — ссылка сломана всегда, 165 из 165. Товары,
которые заводили сразу в товарный раздел, а в «Все букеты» добавляли потом, работают.
Отсюда разнобой: одинаковые с виду букеты ведут себя по-разному.

---

## Почему ручная починка не подходит

Напрашивается разовая правка: переставить привязки у 245 товаров скриптом. **Так делать
не надо.**

Порядок привязок — это порядок их создания. Он снова собьётся при первом же новом товаре,
если его добавят сначала в «Все букеты». Импорт из МойСклада создаёт привязки в своём
порядке. Через полгода вернёмся к тому же, только чинить будем те товары, что успели
завести, и узнаем об этом опять из жалобы админа.

Ссылка должна быть верной **по построению**. Один раз вмешиваемся в выгрузку — дальше
она чинит себя сама, включая все будущие товары.

Ещё одно важное наблюдение: сайт **сам** 301-редиректит любой неканонический адрес
товара на канонический. Значит на сайте всё настроено верно, дублей страниц для
поисковика нет, и перестраивать URL каталога (рискованная операция с редиректами и
просадкой индексации) **не нужно**. Чинить надо только выгрузку.

---

## Решение: пост-обработчик выгрузки

Небольшой PHP-скрипт на стороне сайта. Запускается по крону **после** генерации ICML,
читает файл модуля, исправляет ссылки и кладёт результат в отдельный файл. В настройках
магазина RetailCRM указывается путь к исправленному файлу.

Модуль при этом не трогаем — его обновления ничего не сломают.

### Правило, по которому проставляется ссылка

Одно, общее, без списка исключений:

> Ссылка выдаётся, только если у товара есть публичная страница. Иначе тег `url`
> остаётся пустым.

Страница есть, когда выполняются оба условия:

1. элемент активен **с учётом дат** («Активность с / по»);
2. все разделы канонического пути активны.

Правильный адрес берётся по **основному разделу** элемента — тому самому, который в
карточке уже проставлен верно и по которому сайт строит canonical:

```php
// ссылка ровно та, что сайт объявляет канонической
CIBlockElement::GetList(
    [], 
    ['ID' => $elementId, 'SECTION_ID' => $element['IBLOCK_SECTION_ID'], 'ACTIVE_DATE' => 'Y'],
    false, false,
    ['ID', 'DETAIL_PAGE_URL']
);
```

### Что это даёт по каждой группе

| Группа | Товаров | Что произойдёт |
|---|---|---|
| ссылка неканоническая | 199 | подставится канонический адрес |
| нет страницы на сайте (сезонные) | 46 | ссылка станет пустой; вернут товар на сайт — появится сама |
| «Товары МС» | 101 | останутся в CRM, но без ссылки |
| ссылка верна | 110 | не изменится |

**«Товары МС» из выгрузки не убираем.** Эти позиции нужны в CRM для работы, просто на
сайте их нет. Пустая ссылка — правильное для них состояние: админ видит товар, но не
может отправить клиенту несуществующую страницу.

Правило общее и покрывает будущее: любой новый технический раздел или снятый с публикации
товар автоматически поедет без ссылки, а не с битой.

### Порядок внедрения

1. Бэкап базы.
2. Положить скрипт на сайт, прогнать **на одном товаре** — например на «Нежности».
3. Проверить в получившемся файле, что у товара в теге `url` канонический адрес.
4. Поставить в крон после генерации ICML (она идёт около 19:30).
5. В RetailCRM: Администрирование → Магазины → указать путь к исправленному файлу.
6. Дождаться загрузки каталога в CRM и прогнать проверку (ниже).

## Как проверить результат

Глазами на паре товаров проверять нельзя: 44% ссылок открываются **только** через
редирект и на вид выглядят исправными.

```bash
python scripts/check_product_urls.py            # весь каталог, ~30 минут
python scripts/check_product_urls.py --limit 40  # быстрая проверка, ~3 минуты
```

Скрипт берёт `url` у всех товаров через API RetailCRM, открывает каждую ссылку и
печатает сводку. Полный список проблемных кладёт в `data/bad_product_urls.json`.

Обход идёт по одной ссылке за раз намеренно: карточка генерится на сайте около 4 секунд,
и при проверке в несколько потоков сайт отдаёт 503 (на 6 потоках отбились две трети
ссылок). Ускорять нельзя — результат станет мусором.

**Целевое состояние:** «ведёт точно на карточку» — все товары, у которых ссылка вообще
есть; «неканоническая» и «уводит на раздел» — по нулям.

Отдельно: ежедневный сторож в дашборде, который прогоняет проверку сам и показывает,
если битые ссылки появились снова. Нужен как страховка на случай, если выгрузка
перестанет обновляться или пост-обработчик отвалится.

## Чего делать не нужно

- **Менять «основной раздел» у товара.** На ссылку в выгрузке он не влияет — проверено
  на «Нежности»: основной раздел там правильный, canonical правильный, а в выгрузку
  всё равно уходит `/vse-bukety/`.
- **Переставлять привязки разовым скриптом.** Вернётся с первым новым товаром.
- **Убирать товары из навигационных разделов** («Все букеты», «Кому», «Событие») — на
  них держится навигация сайта.
- **Менять шаблон URL детальной страницы.** Это смена адресов всего каталога, редиректы
  и риск просадки индексации — ради проблемы, которая решается в выгрузке.
- **Искать настройку в RetailCRM.** CRM ссылки не строит, она их принимает.
- **Искать проблему в нашем коде.** Цепочки МойСклад → Битрикс → RetailCRM в репозитории
  `barhat-codex` нет вообще.

---

## Побочные находки

Обе к ссылкам отношения не имеют, но всплыли при разборе.

- **Остатки в CRM не передаются совсем.** В файле выгрузки у всех 454 офферов стоит
  `quantity="0"`. Значит судить о наличии товара по данным CRM нельзя.
- **Карточка товара на сайте отдаётся ~4 секунды.** Замерено на живых страницах, включая
  главную. Для клиента, перешедшего по ссылке из чата, это долго.
