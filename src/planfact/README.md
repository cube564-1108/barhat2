# ПланФакт — клиент API

**Статус:** клиент готов, встроен в синхронизацию счетов (`src/invoices/server.py`, раздел `/api/invoices/planfact/*`). Отдельного standalone-сервиса нет — модуль используется только как библиотека.

## Откуда взята спецификация

Официальная документация `apidoc.planfact.io` — SPA (redoc/swagger-ui), вся спецификация зашита в JS одним блоком и не читается частями. Реальная схема запросов/ответов собрана из двух публичных репозиториев ПланФакт:

- [`planfact-agent-kit`](https://github.com/planfact/planfact-agent-kit) — текстовое описание эндпоинтов, параметров фильтрации, пагинации, форматов дат (`OPERATIONS.md`, `LOOKUPS.md`, `QUICKSTART.md`).
- [`planfact-api-php-example`](https://github.com/planfact/planfact-api-php-example) — рабочие примеры curl-запросов. `curl/put.php` — единственный найденный ДОСЛОВНЫЙ пример тела запроса на запись разбивки операции по `items[]`, на нём основана схема в `client.py`.

## Подключение

- Base URL: `https://api.planfact.io/api/v1/`
- Авторизация: заголовок `X-ApiKey: <ключ>` (не Bearer)
- Ключ — переменная окружения `PLANFACT_API_KEY` в `.env` в корне проекта
- Все ответы: `{"data": ..., "isSuccess": bool, "errorMessage": str|None, "errorCode": str|None}`
- Пагинация: `offset`/`limit`, лимит по умолчанию и максимум — 10000
- Rate limit: `X-RateLimit-Limit` (запросов/мин), `429` → подождать 2-5с, максимум 3 попытки

## Матчинг счетов Бархата с операциями ПланФакт

Вместо попытки угадать системную категорию "нераспределённые расходы" (её точный API-идентификатор нигде не задокументирован дословно) — поиск идёт по `searchString="REF-"` в `POST /operations/list`: находит все Outcome-операции, в назначении платежа которых есть подстрока `REF-` — это наш собственный `match_code` (`src/invoices/storage.py`, `REF-000123`), формат специально выбран непохожим на обычную нумерацию счетов контрагентов (см. план `plans/2026-08-14-invoice-approval-automation.md`, раздел "Уточнения от владельца после исследования API ПланФакт").

Дальше в `src/invoices/server.py` (`_run_planfact_sync`):
1. Regex `REF-\d{6}` вычленяет код из `comment` операции.
2. `get_invoice_by_match_code()` ищет счёт.
3. Строки распределения счёта (`invoice_line_items`) транслируются в `items[]` операции через таблицы сопоставления `invoice_store_planfact_projects` (салон → `projectId`) и `invoice_expense_categories.planfact_category_id` (статья → `operationCategoryId`) — обе редактируются админом в интерфейсе.
4. `PUT /operations/outcome/{id}` — **полная** замена `items[]`, verhнеуровневые поля (`operationDate`, `accountId`, `comment`, `isCommitted`) берутся из уже загруженной операции, не изобретаются заново (PUT, не PATCH — при пропуске поля рискуем его затереть).
5. При успехе — `mark_invoice_paid()`.

Всё, что не удалось сматчить однозначно (нет счёта с таким кодом, счёт не распределён, нет сопоставления салона/статьи с ПланФакт, статус счёта не подходит, ошибка записи) — не теряется молча, а попадает в `invoice_planfact_unmatched` и видно админу в дашборде ("Требует внимания").

## Известные пробелы (не подтверждено примерами)

- Точный ответ `GET /operationcategories/group-list` (группировка по типам) — не понадобился благодаря матчингу по `searchString` вместо категории.
- Формат ошибок (`errorCode`/`errorMessage`) при блокирующих проверках (архивный проект/контрагент/счёт) — обрабатывается как обычная неудача записи (`update_outcome_operation` возвращает `False`), причина уходит в лог, но конкретный текст ошибки ПФ не парсится отдельно.

## Запуск синхронизации

Только вручную, кнопкой «Синхронизировать с ПланФакт» в разделе «Счета» дашборда (admin) — по аналогии с синхронизацией МойСклад (`src/moysklad/server.py`, `/sync`). Автоматический периодический поллинг сознательно не делали на первом этапе (см. план, Фаза 6) — сначала проверить на реальных счетах, дальше можно перевести на фоновый поток по той же схеме, что миграции БД: DB-лок против гонки двух gunicorn-воркеров.

Первый запуск после подключения — обязательно через `dry_run=true` (см. `POST /api/invoices/planfact/sync`), чтобы увидеть, что синхронизация собирается записать, до реальной записи в боевой ПланФакт.
