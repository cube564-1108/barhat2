# Модульбанк — клиент API

**Статус:** клиент готов, встроен в отправку счетов (`src/invoices/server.py`, `POST /api/invoices/<id>/send-to-bank`). Отдельного standalone-сервиса нет — модуль используется только как библиотека.

## Откуда взята спецификация

Официальная документация `api.modulbank.ru` не читается напрямую — та же ситуация, что с ПланФакт (см. `src/planfact/README.md`). Схема запроса подтверждена дословно исходным кодом рабочей Python-обёртки [`github.com/Otetz/modulbank`](https://github.com/Otetz/modulbank) (`modulbank/client.py:create_payment_draft`, `modulbank/client_bank_exchange.py`, `modulbank/structs.py`) — библиотека реализует именно тот метод, что нужен нам.

## Подключение

- Base URL: `https://api.modulbank.ru/v1/`
- Метод: `POST operation-upload/1c`
- Авторизация: заголовок `Authorization: Bearer <токен>` (НЕ `X-ApiKey`, как у ПланФакт)
- Токен — переменная окружения `MODULBANK_API_TOKEN` в `.env` в корне проекта
- Тело запроса — **не** JSON-структура платежа, а классический текстовый 1С-обмен (`1CClientBankExchange`) целиком строкой в поле `"document"` (сборка — `document.py`)
- Ответ: `{"totalLoaded": int, "errors": [str, ...]}`
- `sandbox_mode=True` → заголовок `sandbox: on` — банк создаёт черновик в тестовом контуре, ни на что не влияет; использовать перед первой боевой отправкой
- Банк всегда создаёт платёжку в статусе «Черновик» — подписание доступно только вручную в личном кабинете, поэтому даже боевая (не sandbox) загрузка сама по себе не двигает деньги

## Один токен — несколько компаний

В кабинете Модульбанка заведено несколько юрлиц/ИП владельца (ООО Кофферс, ИП Насуленко и т.д.), у каждой — свой расчётный счёт, но токен API один на весь кабинет. Счёт списания определяется не токеном, а реквизитами внутри самого документа (`ПлательщикСчет`/`РасчСчет`).

Поэтому реквизиты плательщика **не в `.env`**, а в справочнике плательщиков Бархата (`invoice_payers`, «На кого выставлен счёт» в форме счёта) — `src/invoices/storage.py`: `get_payer_bank_requisites()`, `update_payer_bank_requisites()`, редактируется админом там же, где название компании. Пустые реквизиты у плательщика = этот плательщик не проводится через банк-автоматику, счёт закрывается вручную («Отметить оплаченным», как было до Фазы 5) — отдельного флага на этот случай специально не заводили, это следует из заполненности реквизитов (`payer_has_bank_requisites()`).

## Известные пробелы (не подтверждено примерами)

- Точный список кодов ошибок при отклонении черновика (невалидный БИК, несуществующий счёт списания и т.п.) — обёртка Otetz не типизирует их отдельно, `errors: [str]` из ответа прокидывается в UI как есть.
- Поле `ВидПлатежа` в 1С-документе объявлено обязательным в схеме секции, но сама библиотека Otetz его не заполняет (баг или несущественность для Модульбанка) — мы повторяем это поведение (см. `document.py`), а не изобретаем значение.
- Лимиты на частоту запросов к `operation-upload/1c` — не задокументированы нигде из найденных источников; отправка происходит по одному счёту за раз по явному действию админа, массового потока нет.

## Запуск

Только вручную, кнопкой «Отправить в банк» в карточке согласованного счёта (admin) — с чекбоксом sandbox для первой проверки перед боевой отправкой (см. план `plans/2026-08-14-invoice-approval-automation.md`, Фаза 5). Автотриггер сразу после согласования (как изначально планировалось) — следующий шаг после того, как ручная отправка проверена на реальных счетах.
