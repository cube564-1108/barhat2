# Фильтр периода одним полем (обращение #18)

**Goal.** В фильтрах «Согласования счетов» вместо четырёх полей `<input type="date">`
(«Заведён с/по», «Оплата (план) с/по») — два поля периода с календарём, где диапазон
выбирается выделением, а один день выбирается как один день.

**Откуда.** Обращение #18 от 16.09.2026, модуль `invoices_v2`, автор — admin, экран
`/invoices-v2`, 1600×1041, UTC+7.

## Причина (разбор)

1. Даты рисуются общим циклом по `FILTERS` в сетку `repeat(4, 1fr)`
   (`invoices-v2.js:114-117`, `invoices-v2.css:353`). На 1600px «Оплата (план) с» —
   последняя ячейка строки, «Оплата (план) по» — первая ячейка следующей: пара
   визуально перестаёт быть парой.
2. Один день = два одинаковых ввода через два открытия нативного календаря.
3. Каждая дата уходит запросом сразу (`bindFilters`, ветка `change`): выбор периода —
   два похода к списку, первый из которых бессмыслен («с 16.09 по бесконечность»).
   Воркеров на проде два, запрос к `/data` стоит 90-700 мс.
4. Нативный календарь не показывает диапазон и не оформляется по DESIGN-SPEC.

Сервер ни при чём: `created_from / created_to / due_from / due_to`
(`src/invoices/storage.py:2645-2667`) — ровно то, что нужно диапазону. Правка
фронтовая, API не меняется.

## Решение

Свой компонент периода — как `iv2-ms` (мультивыбор) сделан вместо нативного
`<select multiple>` по тем же причинам: нативное не оформляется и неудобно.

**Общий файл, применяем пока в счетах** (решение владельца 23.09.2026). Пары
`type="date"` живут ещё в курьерах, кассовых сменах, списаниях и ABC — следующее
такое же обращение придёт оттуда, и переводить их надо будет по одному модулю за
деплой (правило «одна правка за деплой»).

**Поведение**
- Одно поле на пару. На кнопке: `Все даты` / `16.09.2026` / `12.09 – 20.09.2026`.
- В окне два месяца рядом (на узком экране один), выбор протяжкой мыши и кликом
  «начало → конец», подсветка диапазона по ходу.
- Клик по одному дню и повторный клик по нему же (или закрытие окна) = этот один
  день, обе границы равны.
- Поля «с» и «по» вводом с клавиатуры (`дд.мм.гггг`) — там же, в окне.
- Пресеты: Сегодня, Вчера, 7 дней, Текущий месяц, Прошлый месяц, 30 дней.
- Список перезагружается ОДИН раз — когда диапазон замкнут или сброшен.
- Чип активного фильтра один на период, крестик снимает обе границы.

**Границы ответственности**
- Компонент не знает про счета: он отдаёт `onChange(from, to)` строками `YYYY-MM-DD`.
- Перевод в UTC остаётся в `buildListParams` модуля счетов (`dayStartUtc/dayEndUtc`),
  как было. Компонент работает только с календарными датами.
- Даты собираются через `new Date(y, m-1, d)`. `new Date('2026-09-16')` — это
  UTC-полночь, и при отрицательном смещении даёт вчерашний день.

## Проверено

- `node scripts/test_date_range.js` — 13 разделов, зелёный; падает на версиях,
  где край уходит запросом сам по себе, где незавершённый выбор теряется при
  закрытии и где своё событие не опознаётся.
- `node scripts/test_invoices_filters.js` — зелёный; на прежнем `invoices-v2.js`
  падает на первом же разделе.
- Параметры запроса те же: `created_from=2026-09-12 00:00:00`,
  `created_to=2026-09-20 23:59:59`, `due_from/due_to` — без времени.

## Что осталось за рамками

- Перевод остальных модулей на компонент (курьеры, кассовые смены, списания,
  ABC) — отдельными задачами, по одному деплою.
- «Сумма от / до» в тех же фильтрах осталась парой полей: та же болезнь, но
  правка «одна за деплой», и период был в обращении.
- Выбор времени (часы/минуты) — в фильтрах счетов не нужен.
