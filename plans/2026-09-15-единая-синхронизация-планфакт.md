# Единая синхронизация с ПланФактом

**Дата:** 2026-09-15
**Модуль:** Согласование счетов (`src/invoices/`)
**Решение владельца:** автоматический прогон остаётся, кнопка нужна чтобы не ждать тика.

## Зачем

Разноска сейчас разорвана на два места, и человек обязан помнить оба:

| Что | Где кнопка | Как работает |
|---|---|---|
| Заявки по картам (расход, пополнение) | «Рабочие карты» → «Разнести сейчас» | создаёт операции в ПланФакте; автомат раз в час |
| Оплаченные счета с расчётного счёта | «Синхронизация» → «Синхронизировать» | ищет операции по коду `REF-000123` и дозаполняет проект/статью; **автомата нет** |

Отсутствие автомата у второй половины — источник тихого хвоста: с 7 по 15 сентября
не разносилось ничего, и заметили это только по жалобе.

Плюс два механизма защиты от повторного запуска сделаны по-разному: карты — лок с TTL,
счета — флаг `started` в логе (залипал намертво, см. коммит `e7dbbb5`).

## Цель

Одна кнопка «Синхронизировать с ПланФактом» для админа, которая делает оба этапа
подряд и показывает один отчёт. Автомат — раз в час карты, раз в сутки счета.

# Критика фаз (2026-09-15)

Проверено по коду, не по памяти. Два блокера, один вопрос владельцу.

## Фаза 1 — блокер: циклический импорт

`_run_planfact_sync` живёт в `server.py` (строка 2795), а `server.py` импортирует
`cards_sync`. Новый `planfact_run.py`, импортирующий обе половины, замкнёт круг,
как только `server.py` позовёт его для ручки.

**Правка:** сначала вынести `_run_planfact_sync` из `server.py` в
`invoices/planfact_sync.py` отдельным коммитом, ничего не меняя по сути. Только
потом строить `run_full_sync` поверх двух модулей. Проверено: функция не
обращается к `current_user`, то есть из фонового потока вызывается как есть —
переносится механически.

**Правка:** «квота проверяется один раз на прогон» — неверно. Месячная квота
может кончиться между этапами. Проверять перед каждым этапом; внутри этапа
защита уже есть — клиент сам не ходит наружу при исчерпании.

## Фаза 2 — блокер: TTL лока короче прогона = дубли в ПланФакте

`LOCK_TTL_SECONDS` = 10 минут. Этап счетов — цикл `while True` по страницам
операций за 60 дней (`server.py:2808`), и **лока у него сейчас нет вообще**.
Если объединить этапы под одним локом и прогон окажется длиннее TTL, талон
протухнет на ходу, второй воркер начнёт параллельный прогон — и создаст вторые
операции. Защита маркерами спасает только разноску карт; счета матчатся по
`REF-` и могут обновиться дважды.

**Правка:** продлевать лок внутри цикла по страницам (`renew_sync_lock` по
времени, как в `cards_sync`), а не только между этапами. Без этого фазу 1
делать нельзя — сейчас два механизма живут порознь и не пересекаются, а после
объединения риск появляется.

## Фаза 3 — вопрос владельцу: автомат меняет бизнес-статус

Разноска счетов не только дозаполняет ПланФакт: `server.py:2791` вызывает
`mark_invoice_paid(invoice["id"], changed_by="planfact-sync")`. Сегодня это
происходит только когда админ нажал кнопку. Перевод в автомат означает, что
счета начнут **сами** становиться «оплаченными» по данным ПланФакта — в том
числе при ошибочном совпадении по коду `REF-`.

Это решение не техническое.

**Решение владельца (15.09.2026):** статус ставится автоматом, при этом ручная
отметка обязана остаться. Обе ручные точки уже есть и автоматом не
затрагиваются — кнопка в карточке (`server.py:1644`) и массовое действие
(`server.py:1998`); задача фазы — их не сломать и покрыть сторожем.

В истории счёта автор отметки виден: `planfact-sync` против имени человека —
по нему всегда можно отличить, кто поставил «оплачен».

**Правка:** ночное окно задать в UTC явно. Контейнер живёт в UTC, салоны в
UTC+5 и UTC+7 — «ночь» для них это 19:00–23:00 UTC, а не 00:00.

## Фаза 4 — «единый отчёт» требует того, чего нет

У разноски карт нет состояния в базе: кнопка запускает поток и сразу отвечает,
результат виден только по бейджам в списке. У счетов состояние есть
(`invoice_planfact_sync_log`). Показать один отчёт по двум этапам сейчас
физически нечем.

**Правка:** добавить в фазу 2 запись итогов обоих этапов в общий лог
(создано/уже было/с ошибкой по картам + сматчено/требует внимания по счетам),
и только после этого делать отчёт в интерфейсе. Иначе фаза 4 упрётся в пустоту.

**Правка:** кнопку «Что уедет в ПланФакт» с «Рабочих карт» не убирать. Она
синхронная, ничего не пишет и отвечает за секунды — это единственный способ
увидеть причины, не дожидаясь фонового прогона. Убрать только «Разнести
сейчас», чтобы запуск был в одном месте.

## Фаза 5 — чего не хватает в сторожах

- падение первого этапа не отменяет второй;
- прогон длиннее TTL не даёт второму воркеру начать параллельный (иначе дубли);
- ручка без `X-Requested-With` отвечает 403;
- заявка с будущей датой не попадает ни в один из этапов (уже покрыто
  `test_card_sync.py` разделом 9, но в общем прогоне проверить отдельно).

## Что остаётся верным

Объединение само по себе — правильное решение: сегодняшняя путаница «нажал
«Синхронизировать», а он разносит счета, не карты» стоила половины рабочего
дня. Порядок этапов тоже верный: карты создают операции, счета дозаполняют
чужие — обратный порядок ничего не меняет, но карты дешевле и падают чаще,
поэтому их итог полезнее увидеть первым.

## Риски

- **Долгий прогон в одном потоке.** Карты + счета за 60 дней — минуты. Лок
  продлевать по времени, а не после каждой заявки (правило из CLAUDE.md).
- **Живой вызов из обработчика.** Кнопка обязана только запускать фоновый поток
  и сразу отвечать: живой вызов ПланФакта из обработчика дважды забирал обоих
  воркеров и клал сайт.
- **Дубли операций.** Защита прежняя: маркеры `[cardexp:id]` за 180 дней и
  `planfact_synced_at`. Объединение этапов её не трогает.
