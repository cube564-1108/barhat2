# Модуль списания товара флористами — план

**Статус:** ✅ План готов к реализации (критика пройдена, Чат 3 из 3)
**Дата создания:** 2026-08-16
**Цель:** Флорист сам оформляет списание товара (фото + одна или несколько позиций из каталога МойСклад + кол-во) в модуле дашборда, управляющий точки согласует, после согласования списание автоматически уходит в МойСклад документом «Списание» — без ручного переноса управляющим.

---

## Контекст (текущий процесс и что уже есть в проекте)

**Текущий процесс (ручной):**
Флорист списывает товар → фотографирует → скидывает фото + текстовое описание кол-ва в чат мессенджера → управляющий вручную переносит списание в МойСклад.

**Что уже есть в проекте:**
- `src/moysklad/client.py` — рабочий REST-клиент (remap 1.2), Bearer/Basic auth, retry на 429. Методов для создания документов (списание/оприходование) пока нет — только чтение.
- `src/moysklad/storage.py` — товары и остатки уже синхронизируются в `data/moysklad.db`. `get_products(folder_id, archived, limit)` (storage.py:721) и `get_stores()` (storage.py:793) — каталог для выбора флористом берём отсюда, без похода в API на каждый чих.
- `src/invoices/` — прямой аналог workflow: статусная модель `on_approval → approved/rejected` (storage.py:155), таблица вложений `invoice_attachments` (server.py:395-424, `send_from_directory`), эндпоинты `approve`/`reject` с проверкой текущего статуса и записью `approved_by`/`approved_at`. **Важно:** в invoices редактирование (`PUT`) — только `role_required("admin")`, у создателя нет своего edit-эндпоинта — этот же паттерн переносим сюда (см. Фазу 4).
- `src/cashshifts/` — прямой аналог ролевой модели: `user_stores`, `get_user_stores`, `check_store_access` (storage.py). Флорист жёстко привязан к одной точке, управляющий (роль `manager`) — к нескольким через ту же таблицу.
- `src/auth.py`: `ROLE_SECTIONS` (строка 40-42) — `florist` сейчас видит только `cash_shifts`, `manager` — `cash_shifts`+`invoices`+др. `ALL_MODULES` (строка 258) — плоский список имён модулей для прав доступа.
- `src/pyrus/server.py` — главная точка входа Flask-приложения, здесь регистрируются все blueprint'ы модулей (строки 88-124) в `try/except ImportError` блоках.
- **Несовпадение складов:** склады МойСклад (`stores` в `moysklad.db`, id = UUID) и точки продаж (`stores` в `barhat.db`, id = INTEGER, модуль `cashshifts`) — разные несвязанные таблицы. Та же проблема зафиксирована в `plans/2026-08-15-stock-monitoring.md` — решаем в этом плане одной таблицей-связкой, которую тот план сможет переиспользовать.

## Аналоги / на что опираемся

1. **МойСклад API — документ «Списание» (Loss):** `POST /entity/loss`. Обязательные поля: `organization`, `store`, `positions[]` (`assortment` + `quantity`). Черновик создаётся с `applicable: false` (остаток не меняется), для реального списания — `applicable: true`. Организация в МойСклад одна на компанию — её `meta.href` получаем один раз через `GET /entity/organization` и кладём в `.env` (`MOYSKLAD_ORGANIZATION_HREF`), аналогично токену.
2. **Внутренний аналог workflow согласования** — `src/invoices` (черновик → согласование → проведение + вложения). Копируем почти 1:1, меняя целевую систему (МойСклад вместо банка) и добавляя реальную отправку по API вместо просто смены статуса.
3. **Внутренний аналог ролевой модели точек** — `src/cashshifts` (`user_stores`, `check_store_access`).

## Принятые решения

| Вопрос | Решение |
|---|---|
| Канал ввода для флориста | Модуль в дашборде (веб-форма) |
| Как указывается товар | Выбор из уже синхронизированного каталога МойСклад |
| Кто согласует | Управляющий точки (роль `manager`, доступ только к своим точкам через `user_stores`); админ — все точки |
| Позиции в заявке | **Несколько позиций в одной заявке** (разные товары/кол-во, каждая своя фото) — аналог `cash_collections`, одно согласование на всю пачку |
| Редактирование после подачи | Своего edit-эндпоинта у флориста нет (как в invoices) — но флорист может **отменить свою же заявку** (`DELETE`), пока она в статусе `on_approval` и управляющий её ещё не тронул. Ошибся — отменил, создал заново. Если управляющий уже отклонил — правка невозможна, только новая заявка |
| Ошибка при отправке в МойСклад после согласования | Статус `failed` + ручной/автоматический повтор (`POST /retry`), заявка не считается потерянной |
| Хранение фото | Свой `writeoff_attachments` по паттерну `invoice_attachments` (локальный диск + `send_from_directory`), без преждевременной унификации в общий attachments-модуль |

## Фаза 3: МойСклад-клиент — создание документа списания

**Goal:** Метод `create_loss()` в `src/moysklad/client.py`, который реально проводит списание.

**Критика (Чат 3):** в черновике Фазы 4 было заложено «создавать списание по каждой позиции отдельно» — это неверно и создавало риск частично проведённого списания (позиция 1 ушла, позиция 2 упала по таймауту → заявка «наполовину в МойСклад», сложно откатить/повторить без дублей). Документ «Списание» в МойСклад **сам поддерживает массив `positions[]`** — правильное решение: **один документ на всю заявку**, одним атомарным POST-запросом. Либо весь документ создался, либо нет — частичных состояний внутри заявки не бывает.

**Задачи:**
- [ ] Получить и сохранить `MOYSKLAD_ORGANIZATION_HREF` в `.env` (одноразово: `GET /entity/organization`, взять первую/единственную запись)
- [ ] Добавить в `MoySkladClient`:
  ```python
  def create_loss(
      self,
      store_href: str,
      positions: list[dict],   # [{"assortment_href": str, "quantity": float}, ...] — ВСЕ позиции заявки одним документом
      applicable: bool = True,
      description: Optional[str] = None,
  ) -> Optional[Dict]:
      """Создать документ 'Списание' (POST /entity/loss) на все позиции заявки за один запрос"""
  ```
- [ ] Обработка ошибок: не глотать исключение молча — вызывающий код (Фаза 4) должен получить и записать причину в `writeoffs.moysklad_error`
- [ ] Ручной тест на реальном (или тестовом) аккаунте МойСклад: списание с 2+ позициями одним документом, проверка что остаток уменьшился по каждому товару

**Constraints:**
- `applicable: true` сразу — черновики (`false`) не нужны в этом сценарии, согласование уже произошло на стороне дашборда
- Не хардкодить `organization`/`store` href в коде — только через `.env`/таблицу связки
- Ровно один HTTP-запрос на всю заявку — не по одному запросу на позицию

**Done when:**
- Вызов `create_loss()` с несколькими позициями создаёт один документ, остаток уменьшается на `quantity` по каждому товару
- Ошибка API (неверный товар, недостаточно прав) возвращается как понятная строка, не как uncaught exception

## Фаза 4: Flask API модуля writeoffs

**Goal:** REST API — по паттерну `src/invoices/server.py`, blueprint `writeoffs_bp` (`url_prefix="/api/writeoffs"`).

**Эндпоинты:**
- [ ] `GET /api/writeoffs/catalog?store_id=` — список товаров для выбора (проксирует `moysklad.storage.get_products`, отфильтрованных по остаткам склада точки, если остаток = 0 — не показывать)
- [ ] `POST /api/writeoffs` `{store_id, positions: [{moysklad_product_id, quantity, reason}]}` — создаёт заявку в статусе `on_approval`, `store_id` для роли `florist` берётся из его привязки (не из запроса), как в cashshifts
- [ ] `POST /api/writeoffs/positions/<id>/attachments` — загрузка фото для позиции (multipart, поле `file`, паттерн `invoices` `upload_attachment`)
- [ ] `GET /api/writeoffs/attachments/<id>/download` — отдача фото (`send_from_directory`)
- [ ] `GET /api/writeoffs?store_id=&status=&date_from=&date_to=` — список с фильтрами, доступ по ролям (florist — своя точка, manager — свои точки через `user_stores`, admin — все)
- [ ] `GET /api/writeoffs/<id>` — детали заявки + позиции + вложения
- [ ] `DELETE /api/writeoffs/<id>` — отмена своей заявки автором, только пока `status='on_approval'`
- [ ] `POST /api/writeoffs/<id>/approve` — только `manager`/`admin` с доступом к точке заявки. Алгоритм:
  1. Атомарный `UPDATE writeoffs SET status='processing', approved_by=?, approved_at=datetime('now') WHERE id=? AND status='on_approval'` — проверить `rowcount == 1`; если 0, значит заявку уже кто-то обработал (двойной клик/два управляющих одновременно) → вернуть 409, ничего не отправлять
  2. Только после успешного захвата статуса — собрать все позиции заявки и вызвать `create_loss()` **одним запросом**
  3. Успех → `status='sent'`, сохранить `moysklad_loss_id`. Ошибка API → `status='failed'`, сохранить `moysklad_error`
- [ ] `POST /api/writeoffs/<id>/reject` `{reason}` — только `manager`/`admin` с доступом к точке, тот же паттерн атомарного `UPDATE ... WHERE status='on_approval'` (защита от гонки с одновременным `/approve`)
- [ ] `POST /api/writeoffs/<id>/retry` — только для `status='failed'`, тот же атомарный захват (`failed → processing`) перед повторным вызовом `create_loss()`

**Constraints:**
- Все эндпоинты — `@login_required`/`@section_required("writeoffs")` как в invoices/cashshifts
- Проверка доступа к точке — переиспользовать `check_store_access` из `cashshifts/storage.py` (не дублировать логику)
- **Ни один код-путь не вызывает `create_loss()`, не захватив статус атомарным `UPDATE ... WHERE status IN (...)` с проверкой `rowcount`** — иначе двойной клик по «Согласовать» или гонка `approve`/`retry` создаст два документа списания в МойСклад на одну заявку. Это правило, а не рекомендация: списание физически уменьшает остаток, задвоение не откатывается автоматически
- Известный остаточный риск (осознанно не решается в MVP): если `create_loss()` реально создал документ в МойСклад, но ответ не дошёл до сервера (обрыв сети/таймаут) — заявка помечается `failed`, а документ в МойСклад уже есть. `/retry` создаст второй. При масштабе проекта (ручное согласование, не десятки заявок в секунду) — принимаем как редкий крайний случай с ручной сверкой, а не проектируем распределённую идемпотentность ради него

**Done when:**
- Полный цикл (создание → согласование → успешная отправка) проверен через curl/Postman
- Сценарий `failed` → `retry` → `sent` проверен вручную (например, временно передав неверный `store_href`)

## Фаза 7: Тестирование на реальных данных

**Goal:** Убедиться, что списание в проде физически уменьшает остаток в МойСклад, а не только меняет статус в БД проекта.

**Сценарии:**
- [ ] Заявка с одной позицией → согласование → остаток в МойСклад уменьшился на нужное кол-во
- [ ] Заявка с несколькими позициями (разные товары) → согласование → **один** документ списания со всеми позициями, каждая корректна
- [ ] Отклонение заявки управляющим → в МойСклад ничего не создаётся
- [ ] Отмена заявки флористом до согласования → заявка пропадает из очереди управляющего
- [ ] Симуляция сбоя API (временно битый `store_href`) → статус `failed`, видна ошибка, `/retry` после починки данных доводит до `sent`
- [ ] Двойной клик по «Согласовать» (или два таба) на одной заявке → документ в МойСклад создаётся только один раз, второй запрос получает 409
- [ ] Проверка прав: флорист другой точки не видит чужую заявку; управляющий не своей точки — тоже

**Constraints:**
- Тестировать на реальном `.env` с МойСклад (или отдельном тестовом аккаунте, если доступен — уточнить у владельца перед прогоном на боевых остатках)

**Done when:**
- Все сценарии выше отработаны и подтверждены визуально в МойСклад (веб-интерфейс МойСклад, не только через API)

## Критика плана (Чат 3)

**1. Лучшее ли решение по каждой фазе?**
- Фаза 3/4 — найден и исправлен реальный баг: черновик отправлял списание по одной позиции за раз (риск частично проведённой заявки). Исправлено на один атомарный документ на всю заявку — это и есть решение, которое даёт нативная поддержка `positions[]` в МойСклад, ничего изобретать не пришлось.
- Фаза 1 (таблица-связка складов) — намеренно спроектирована нейтрально, чтобы её мог переиспользовать план `stock-monitoring`. Не overengineering: связка нужна прямо сейчас этому модулю, переиспользуемость — побочный бесплатный эффект от нормализации имени таблицы, а не отдельная фаза работы.
- Остальные фазы — прямое повторение уже проверенных в проде паттернов (`invoices`, `cashshifts`), без новых абстракций.

**2. Конфликты между фазами?**
- Найден и исправлен: Фаза 3 (клиент) и Фаза 4 (API) были рассинхронизированы по модели отправки (по позициям vs одним документом) — теперь согласованы.
- Остаточный риск гонки `approve`/`reject`/`retry` на одной заявке — закрыт атомарным `UPDATE ... WHERE status = ...` с проверкой `rowcount` в каждом из трёх эндпоинтов (Фаза 4).
- Других конфликтов между фазами нет — модуль изолирован в `src/writeoffs/`, точки соприкосновения (auth, cashshifts, moysklad) — только на чтение существующих функций, без изменения их поведения.

**3. Безопасность?**
- Задвоение списания при двойном клике — закрыто (см. п.2).
- Остаточный риск «ответ МойСклад потерян по таймауту, а документ создан» — осознанно не решается инженерно в MVP (см. Фазу 4, constraint), т.к. при ручном согласовании через дашборд это редкий крайний случай, а не системный риск при текущем масштабе (не десятки заявок в секунду). Если проявится на практике — тогда добавлять идемпотентность (например, поле `description` с уникальным ID заявки + поиск существующего документа перед retry).
- Доступ по ролям и точкам — переиспользует уже проверенный в проде `check_store_access`, не новый код с новыми дырами.

**4. Соответствие бизнес-целям?**
- Прямое попадание в принцип CLAUDE.md «человек принимает только решения, всё остальное — агенты»: единственное ручное действие управляющего — клик «Согласовать»/«Отклонить» по факту (решение), сама передача данных в МойСклад — полностью автоматическая. Раньше управляющий тратил время на ручной перенос данных — теперь на это не тратит время вообще.
- Экономия времени управляющего — цель заявленная владельцем изначально — достигается: было «посмотреть фото в чате → зайти в МойСклад → вручную создать документ», станет «посмотреть фото в дашборде → один клик».

**Дополнительно замечено, не блокирует реализацию:**
- Каталог товаров (`moysklad.db`) сейчас синхронизируется только вручную (`scripts/update_moysklad.py`, крона нет — тот же пробел, что уже зафиксирован в плане `stock-monitoring`). Если каталог не обновлять регулярно, новые товары не появятся в форме списания сразу. Не блокирует запуск модуля, но стоит когда-нибудь закрыть тем же куском работы, что и `stock-monitoring` (Фаза «Планировщик»).
- Рост числа файлов фото на диске со временем — при объёме одного цветочного бизнеса не является проблемой на годы вперёд, специально не проектируем ротацию/архивацию сейчас (не код ради кода).
