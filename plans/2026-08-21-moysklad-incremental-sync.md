# Инкрементальная синхронизация МойСклад

**Дата:** 2026-08-21
**Проблема:** каждый прогон синхронизации заказов длится 20–40 минут и тяжело нагружает прод.

## Диагноз

`src/moysklad/server.py::trigger_sync` фильтрует заказы по дате **создания**:
`filter=created>=<6 месяцев назад>`. Граница пересчитывается при каждом запуске, поэтому
каждый прогон заново выкачивает все ~28К заказов за полгода, хотя изменились из них единицы.

28К заказов / 100 на страницу (больше нельзя — МойСклад не разворачивает `positions`
при `limit > 100`) = ~280 запросов с тяжёлым `expand`, плюс пауза 0.3 с на страницу.
Время растёт линейно с ростом числа заказов в день.

## Решение

Фильтровать по `updated>=<курсор последней синхронизации>`. Заказ, у которого сменился
статус, получает свежий `updated` и подтянется — это ровно то, что нужно ABC-анализу.
Прогон раз в 30 минут = одна страница вместо 280.

## Фазы

### Фаза 1. Курсор и лок в хранилище — [x]

**Goal:** таблица `sync_state` (ключ-значение) + межпроцессный лок на прогон синхронизации.
**Done when:** курсор переживает перезапуск воркера; два воркера gunicorn не могут
запустить синхронизацию одновременно.

- [x] Таблица `sync_state (key, value, updated_at)` в `_init_db`
- [x] `get_sync_state` / `set_sync_state`
- [x] `try_acquire_sync_lock` / `renew_sync_lock` / `release_sync_lock` (лок с TTL,
      атомарный `UPDATE ... WHERE expires < now`)

### Фаза 2. Фикс потери позиций при обновлении заказа — [x]

**Goal:** позиции, удалённые из заказа в МойСклад, должны исчезать и в локальной БД.
**Done when:** повторный синк изменённого заказа не оставляет в `order_positions` строк,
которых уже нет в заказе.

- [x] `DELETE FROM order_positions WHERE order_id = ?` перед вставкой позиций

Без этого инкрементальный синк (заказ правится по ходу жизни и приезжает повторно)
начнёт накапливать «мёртвые» позиции, завышая выручку в ABC.

### Фаза 3. Инкрементальный режим — [x]

**Goal:** два режима прогона — `incremental` (по `updated`) и `full` (по `created`).
**Done when:** обычный прогон занимает секунды; заказы со сменившимся статусом подтягиваются.

- [x] `order=updated,asc` / `order=created,asc` — стабильная пагинация
- [x] Курсор хранится в формате и часовом поясе МойСклад (максимальный `updated`
      среди загруженных строк) — конверсия таймзон не нужна вообще
- [x] Overlap 15 минут при чтении курсора — заказы, изменённые во время прогона
- [x] В `incremental` курсор двигается даже при обрыве (asc-сортировка это позволяет),
      в `full` — только при полном успехе

### Фаза 4. Автозапуск по расписанию — [x]

**Goal:** синхронизация идёт сама, кнопку жать не нужно.
**Done when:** данные ABC свежие без ручных действий; на двух воркерах прогон один.

- [x] Фоновый поток-планировщик, интервал 30 минут
- [x] Лидер выбирается локом из фазы 1
- [x] Раз в 7 дней ночью — полный ресинк (ловит заказы, удалённые в МойСклад:
      инкремент по `updated` их не видит в принципе)

**Goal:** видно, когда данные обновлялись; ручной полный ресинк доступен админу.
**Done when:** на странице ABC есть отметка времени последней синхронизации.

- [x] Кнопка синхронизации запускает инкремент (секунды)
- [x] Пункт «Полная пересинхронизация» — отдельным действием
