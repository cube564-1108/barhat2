# ABC-анализ товаров — план

**Статус:** [x] Реализовано, задеплоено, работает на проде. Фаза 5 (нагрузка + дизайн) готова локально, ждёт разрешения на деплой
**Дата:** 2026-08-15
**Цель:** Модуль ABC-анализа товаров с выбором периода отчёта (по дате продажи) и канала продаж. Данные — через API. Товары берём из всех разделов МойСклад, кроме раздела «Товары МС».

---

## Архитектурное решение: откуда брать данные

**Единый источник — МойСклад, сущность `customerorder` (заказ покупателя).** Подтверждено разведкой реальных данных (Фаза 1): канал продаж — это нативное поле `customerorder.salesChannel` (ссылка на справочник `/entity/saleschannel`), а не кастомный атрибут и не что-то, что нужно тянуть из RetailCRM отдельно. Один и тот же объект `customerorder` при запросе с `expand=positions,positions.assortment,state` отдаёт всё необходимое за один вызов:

- `created` — дата создания заказа (= «дата продажи» по решению владельца)
- `state.name` — статус («Выполнен», «Отменён», ... — см. полный список ниже)
- `salesChannel` — ссылка на канал продаж (id; имя — из отдельно синхронизированного справочника)
- `positions.rows[]` — позиции: `quantity`, `price`, `discount`, `assortment.{id, name, archived, productFolder.id}`

`demand` (отгрузка) для ABC не нужна — у неё те же позиции, но нет `state` (только флаг `applicable`), и `customerorder` уже даёт весь набор данных. RetailCRM для ABC не используется вообще — она остаётся источником только для кассовых смен (`src/cashshifts/retailcrm_client.py`), это отдельная задача.

---

## Зафиксированные бизнес-решения (владелец)

- **Метрика ABC:** выручка (сумма продаж)
- **Дата продажи:** дата создания заказа (`customerorder.created`)
- **Статусы заказов:** только оплаченные/выполненные → фильтр `state.name == 'Выполнен'`
- **Исключение:** товары из раздела «Товары МС» (и всех его подпапок) не участвуют в анализе
- **Источник данных:** МойСклад, единственная сущность `customerorder`

**Решение для реализации:** резолвить исключаемые id **динамически по имени** корневой папки `Товары МС` (сама папка + прямые потомки) при каждой синхронизации, а не хардкодить UUID в коде — надёжнее на случай, если id когда-нибудь изменится.

### Найденные и исправленные баги (все — pre-existing, не мои изменения этой сессии)
Все три бага маскировали друг друга: `get_sales_orders()` не работал вообще → `save_sales_order()` никогда не выполнялся → его собственные баги ни разу не проявлялись до сегодняшнего дня.

1. `client.py::get_sales_orders()` стучался в несуществующий путь `/entity/salesorder` (правильный — `/entity/customerorder`) → любая загрузка заказов падала с ошибкой 1005
2. `storage.py::save_sales_order()` — несовпадение числа колонок (19) и значений (18) в `INSERT` (лишняя `updated_at` в списке колонок без значения) → `sqlite3.ProgrammingError` при каждом вызове
3. `storage.py::save_sales_order()` — `order.get('rate', 1.0)` трактовал `rate` как число, а МойСклад отдаёт объект `{value?, currency}` → `sqlite3` ошибка биндинга параметра (dict вместо числа)
4. `storage.py::save_folder()` — брал родителя из ключа `parent`, а МойСклад отдаёт его под `productFolder` (и как meta-ссылку, не с прямым `id`) → `parent_id` никогда не сохранялся, дерево папок было плоским
5. (Обнаружено при реализации Фазы 2, не баг, а недокументированное поведение API) — при списочном запросе `GET /entity/customerorder` с `expand=positions,...` и `limit > 100` МойСклад молча перестаёт вкладывать `positions.rows` (отдаёт только `meta`, без содержимого) — порог измерен эмпирически (100 работает, 200 — нет). `fetcher.py` теперь снижает `batch_size` до 100, когда `expand` содержит `positions`

Все пять — исправлены и проверены на реальных данных (см. Фазу 2).

### Как канал продаж на самом деле выглядит в данных
Каждая позиция заказа хранит `assortment.productFolder` — прямая ссылка на папку товара, так что не нужно отдельно джойнить каталог `products` с позициями: связь уже приходит вложенной прямо в заказ.

### [x] Фаза 5 — Синхронизация не должна тормозить сайт + дизайн-стандарт (2026-08-21)

Жалоба владельца после работы модуля на проде: **«синхронизация с МойСклад очень сильно замедляет работу всего сайта»**.
Разбор показал, что дело не в самих запросах к API МойСклад, а в четырёх местах, где модуль насиловал диск и воркеры.
На Amvera `/data` — один диск на все базы (`barhat.db` авторизации, `pyrus.db`, `moysklad.db`), поэтому дисковая
очередь от синхронизации тормозила вообще всё, включая вход в дашборд.

**Найденные причины и что сделано:**

- [x] **`get_storage()` создавал новый `MoySkladStorage` на каждый вызов**, а его `__init__` гоняет `_init_db()`:
      ~10 `CREATE TABLE IF NOT EXISTS`, 13 `CREATE INDEX IF NOT EXISTS` и `PRAGMA table_info`-миграции.
      Это выполнялось на **каждый** HTTP-запрос к `/api/moysklad/*` — в том числе на опрос `/sync-status`
      раз в 2 секунды все 40 минут синка. → кэш инстансов по пути к БД
- [x] **Каждый заказ сохранялся отдельной транзакцией**: 28 336 заказов = 28 336 соединений, коммитов и fsync
      на сетевой диск. → `save_sales_orders_batch()`, страница из 100 заказов пишется одной транзакцией
      (явный `BEGIN` + `SAVEPOINT` на заказ, чтобы один битый заказ не ронял всю страницу).
      Замер: **быстрее в 8.8 раза** на локальном SSD, на сетевом диске разрыв больше
- [x] **`PRAGMA journal_mode=WAL` выполнялась на каждом соединении** (то есть на каждый заказ), хотя это
      персистентное свойство файла БД. → перенесена в `_init_db`, добавлена `synchronous=NORMAL`
      (штатная пара к WAL: fsync на чекпойнте, а не на каждой транзакции)
- [x] **`/sync-status` вызывал `get_stats()`** — шесть `COUNT(*)` с полным сканом, включая `order_positions`
      (46К строк), и так каждые 2 секунды. → прогресс пишет сам фоновый поток
      (`update_sync_log_progress`), статус читает одну строку `sync_log` по индексу
- [x] **`raw_data` заказа дублировал все позиции**, которые и так лежат в `order_positions.raw_data` —
      локальная БД на 28К заказов разрослась до **1.17 ГБ**. → в `raw_data` заказа позиции больше не кладутся
      (никто их оттуда не читал — проверено грепом)
- [x] **Пауза 0.3 с между страницами**: фоновый поток крутится внутри воркера gunicorn, который параллельно
      обслуживает сайт; без паузы он непрерывно держит GIL на разборе JSON. +1.5 минуты к сорока — незаметно
- [x] **Открытие страницы без периода = `GROUP BY` по всей базе.** Замер на реальных данных: **5.8 с** против
      **0.18 с** с периодом. → период по умолчанию — последние 30 дней (и «Сбросить» возвращает к нему же)
- [x] **Опрос статуса на фронте 2 с → 10 с**
- [x] **Прерванный синк залипал навсегда**: запись `sync_log` со статусом `started` после перезапуска воркера
      блокировала кнопку без возможности перезапуска. → колонка `progress_at` + `_sync_log_is_stale()`
