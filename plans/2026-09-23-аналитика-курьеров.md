# Аналитика по работе курьеров

> Закрыт 23.09.2026, на проде. Осталcя замер цены экрана на реальном объёме.
> Экран согласован со Стасом 23.09.2026, макет — в разделе 3.

## Goal

Управляющий за один экран отвечает на вопросы: сколько заказов взяли курьеры,
сколько довезли, какая доля вовремя, где теряем заказы и по чьей вине.
Разрез — по курьерам, фильтр — период и салоны (множественный выбор).

## Done when

- Вкладка «Аналитика» в «Контроле доставки» открывается, считает шесть метрик
  за произвольный период и любой набор салонов.
- Три списка детализации отдают номера заказов с курьерами.
- Числа сходятся между собой, и расхождение объяснено строкой на экране.
- Сторожа зелёные, `EXPLAIN QUERY PLAN` на объёме прода использует индекс.

## 2. Модель данных

```
delivery_assignments           courier_orders                courier_sites
─────────────────────          ──────────────────            ─────────────
retailcrm_order_id  ──────────► retailcrm_order_id (PK)      code (PK)
courier_user_id                 order_number                 name
courier_name                    delivery_date                city
state                           delivery_time_from           utc_offset
claimed_at                      delivery_time_to
delivered_at                    site_code ───────────────────► code
released_at                     delivery_code
release_reason                  status
```

Состояния: `claimed` · `picked_up` · `delivered` · `released` · `problem`.
Причины снятия: `self` · `admin` · `expired` · `outsourced` · `order_gone`.

### Определения метрик (согласованы)

Период считается **по `courier_orders.delivery_date`**, а не по дате брони:
тогда все шесть чисел живут на одном множестве заказов и сходятся между собой.
Салон — `courier_orders.site_code`.

| Метрика | Как считается |
|---|---|
| Броней | все записи `delivery_assignments` по заказам периода |
| Сняли руками | `state='released' AND release_reason IN ('self','admin')`, на плитке разбивка |
| Всего доставок | `state='delivered'` |
| Доля вовремя | доставки, где факт ≤ конца интервала, делить на доставки **с известным интервалом** |
| Среднее опоздание | среднее по **опоздавшим**, а не по всем доставкам |
| Ушло аутсорсу | `release_reason='outsourced'` |

Шесть правил, каждое — цена прошлой ошибки:

1. **Доставленное раньше интервала — вовремя.** Опоздание считается только от
   `delivery_time_to`.
2. **Заказ без интервала не участвует в доле вообще** — ни в числителе, ни в
   знаменателе, и его число видно на экране. Доля, посчитанная по молча
   отброшенным записям, выглядит правдоподобно и врёт.
3. **Среднее опоздание — по опоздавшим.** Усреднение с нулями доставленных
   вовремя превращает 40 минут в 6 и прячет проблему.
4. **Считаем БРОНИ, а не заказы.** У одного заказа их бывает несколько подряд:
   взял → снял → взял другой курьер. «Броней 247» — это 247 нажатий «Взять»,
   и сходимость держится именно на записях брони. Иначе число не сойдётся ни с
   одним слагаемым, и разбираться в этом будут задним числом.
5. **Курьер — это `courier_user_id`, а не имя.** `courier_name` в брони —
   снимок на момент захвата; человека переименовали, и он разъезжается на две
   строки. Группируем по идентификатору, показываем последнее известное имя.
6. **Пояс не задан у салона — заказ не посчитан, а не «вовремя».**
   `utc_offset` бывает `NULL` (салон новый, пояс не проставили). Такие заказы
   идут в отдельный счётчик с именем салона — иначе метрика тихо считает их
   доставленными в срок и зовёт чинить то, что не сломано.

### Пояс салона — обязательная часть формулы

`delivered_at` лежит в UTC, `delivery_time_to` — стенные часы салона. Салоны в
UTC+5 и UTC+7. Сравнение «в лоб» даст пять часов опоздания у каждого заказа
Екатеринбурга — то есть метрика будет выглядеть работающей и показывать чушь.
Сравниваем `delivered_at + utc_offset` против `delivery_date + delivery_time_to`.

Сторож обязан содержать заказы **двух городов с разным смещением** — иначе он
зеленеет на коде, где пояс не учтён вовсе.

Решения по виду:

- **Полоски доли нет** — только число; сравнение даёт сортировка по колонке.
- **Плитка несёт свою базу** («171 из 198»): процент без знаменателя не
  проверяется, при трёх доставках 66,7% не значит ничего.
- **Строка сходимости обязательна.** Броней 247, доставок 198 — первый вопрос
  «где остальные 49», и он должен получать ответ на экране, а не в голове.
- **Блоки детализации закрыты по умолчанию** и переживают смену фильтра.
- **Опоздания сортируются по величине**, сверху худшее.
- **Номер заказа — текстом, без ссылки в CRM**: во вкладке «Доставка» он тоже
  текст, а расхождение между соседними вкладками читается как поломка.
- **Курьер с нулём доставок, но с бронями, из таблицы не пропадает** — иначе
  «взял девять, снял девять» не видно нигде.
- **Доля при малом числе доставок помечается «мало данных».** У курьера с
  двумя доставками «50,0 %» читается так же уверенно, как «86,4 %» у курьера с
  двумя сотнями, и по нему примут решение о человеке. Ниже пяти доставок
  процент показываем приглушённым с подписью, а не прячем: прятать — значит
  снова отвечать за него в голове.

Третий блок отвечает на вопрос, которого не было в заказе метрик, но он тут
самый дорогой: заказы чаще уходят службе не потому, что курьер передумал, а
потому что его не нашлось вовсе. Это чинится числом людей и условиями на
непопулярные слоты, а не разговором с курьерами.

## 4. Риски

| Риск | Что делаем |
|---|---|
| **`delivered_at` — это момент нажатия «Доставил», а не факт вручения** | Другого источника нет. Пишем это подписью под таблицей: метрика меряет отметку курьера. Не выдумывать «уточнение» по статусу CRM — получим вторую правду |
| **Цена экрана на сетевом `/data`** | Один поход в базу за ответ, агрегаты в SQL, выборки по индексу. Замер `timings_ms` в ответе — по правилу «мерить внутри ручки» |
| **Фильтр по двум полям** (`delivery_date` + `site_code`) | Одиночные индексы не складываются. Нужен составной, проверка — `EXPLAIN QUERY PLAN` на копии боевой базы, а не по времени ответа |
| **Пояс салона** | См. раздел 2. Сторож на двух городах |
| **Заказы без интервала** | Считаем отдельно и показываем. Не подставлять «стандартный интервал» |
| **Период в год** | Списки детализации могут дать тысячи строк. Отрисовка кусками, как во вкладке «Доставка»; серверную пагинацию не заводим — у неё свой список граблей (CLAUDE.md), а здесь она не нужна |

## 7. Вопросы, на которые ответит только прод

- Сколько заказов реально приходит без интервала доставки. Если их много —
  доля «вовремя» считается по куску выборки, и это придётся показывать
  заметнее, чем строкой внизу.
- Насколько `delivered_at` расходится с реальным вручением. Косвенно видно по
  доставкам, отмеченным сразу пачкой в конце смены.
