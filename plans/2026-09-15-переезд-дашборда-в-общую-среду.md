## Зачем

Дашборд построен отдельно от общей среды: свой репозиторий, свой аккаунт Amvera, свои
SQLite-базы, свой синк RetailCRM. Команда ведёт сервисы вокруг одного ядра `barkhat-core`,
и пока дашборд снаружи — его нельзя починить чужими руками, а его данные не видны из
Пульса. Переезд убирает обе стены.

## Фаза B — деплой через SSH (в работе)

Блокера нет. Дашборд остаётся в ЛИЧНОМ аккаунте Amvera Стаса (решение «а»), значит и
деплой настраивается в его панели — доступ к общему аккаунту Романа для этого не нужен.
Отсюда же следствие: ключ `stas@barhat` Роман добавил в ОБЩИЙ аккаунт, в личный его
нужно добавить самому, иначе пуш не пройдёт.

- [ ] Добавить SSH-ключ `stas@barhat` в личный аккаунт Amvera
- [ ] Взять из панели SSH-URL git-репозитория проекта дашборда
- [ ] `git remote add amvera <ssh-url>`
- [ ] `git fetch amvera` — посмотреть, что лежит в `master` на проде
- [ ] Первый пуш: при non-fast-forward сначала `git merge amvera/master`
      (в прод-`master` бывают панельные коммиты «Updated config»)
- [ ] `git push amvera main:master` — Amvera собирает из `master`, не из `main`
- [ ] Дождаться сборки: лог сборки `exit code: 0`, приложение отвечает
- [ ] Проверить прод вживую: `/health` отвечает, `persistent: true`, вход в дашборд работает
- [ ] Отключить автосборку из GitHub `barhat2` — иначе два источника деплоя
- [ ] Переключить `origin` на `barkhat-hq/barkhat-dashboard`, старый `barhat2` оставить
      как `old` до конца обкатки

**Done when:** правка уезжает на прод командой `git push amvera main:master` из репозитория
организации, а `barhat2` больше ни на что не влияет.

**Откат:** вернуть автосборку из `barhat2` в панели — старый путь доставки цел, пока
репозиторий не удалён.

**Грабли (проверено на других сервисах):**
- Amvera не запускает билд без нового коммита — при «немом» билде нужен retry-коммит
- `Internal server error` в логе сборки — инфраструктурный сбой Amvera, лечится повтором

## Побочная находка (отдельной задачей)

У шести планировщиков дашборда есть выключатель `*_SCHEDULER=0`, у ленты доставки курьеров
(`couriers/delivery_feed.py: start_feed_scheduler`) — нет: стартует всегда, если настроен
RetailCRM, и локальный запуск с боевым `.env` уходит в боевой API. Нужен
`COURIERS_FEED_SCHEDULER` по образцу остальных, дефолт `1`.
