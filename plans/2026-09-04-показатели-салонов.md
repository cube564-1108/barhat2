# Показатели салонов для управляющих — план

**Статус:** [x] План готов к реализации (Чаты 1–3 пройдены), код не написан
**Дата:** 2026-09-04
**Цель:** один экран, на котором управляющий видит по своему салону (и городу) пять
показателей текущего месяца: отгрузки и выполнение плана, долю канала «Улица»,
подтверждённую негативную ОС, качество сборки (в т.ч. по флористам) и долю доставок
внешними такси-службами.

---

## Goal → Context → Constraints → Done when

**Goal.** Управляющий открывает раздел «Показатели салонов» и за 5 секунд понимает,
как идёт месяц: сколько отгрузили против плана, сколько дала «Улица», сколько
негатива, какое качество сборки, сколько заказов отдано агрегаторам.

**Context.** Всё сырьё уже есть или добывается существующим кодом:

| Показатель | Источник | Что уже готово |
|---|---|---|
| 1. Отгрузки + план | RetailCRM `api/v5/orders` | синк по дате доставки в [couriers/retailcrm.py](src/couriers/retailcrm.py); плана нет нигде |
| 2. Канал «Улица» | тот же ответ CRM, `orderMethod` | поле не сохраняется |
| 3. Негативная ОС | Pyrus форма 1291124 | форма есть в справочнике, **задачи не грузятся вообще** |
| 4. Качество сборки | Pyrus форма 1327961 | витрина `quality_scores` + отчёты в [quality.py](src/pyrus/quality.py) |
| 5. Доля такси-служб | тот же ответ CRM, `delivery.code` + курьер | курьер и дата есть, тип доставки не сохраняется |
| 6. Списание цветка | МойСклад, документы `enter` и `loss` | документы не синхронизируются |
| 7. Средняя цена клубники | там же | документы не синхронизируются |

**Constraints.**
- Python 3.11, Flask-blueprint внутри мастер-приложения `src/pyrus/server.py`.
- Внешние API — только из фонового синка под локом, никогда из обработчика запроса
  (дважды укладывало прод).
- Соединения через `sqlite_conn.connect`, пути через `storage_paths.resolve`.
- Интерфейс строго по `DESIGN-SPEC.md`: токены `--bx-*`, Vollkorn, без эмодзи, чек-лист §9.
- Не ломать модуль «Оплата курьерам»: он про деньги и работает на той же витрине.

**Done when.**
- [ ] Экран открывается у admin / manager / sso_viewer; менеджер видит только свои салоны.
- [ ] Пять показателей за текущий месяц сходятся с выборочной проверкой в CRM и Pyrus.
- [ ] Есть переключатель месяца и разрез «салон ↔ город».
- [ ] Видно, на какой момент данные (время последнего синка), и видно несопоставленные
      источники (салон CRM/Pyrus, не привязанный ни к одному салону справочника).
- [ ] План на месяц вводится в интерфейсе и хранится по месяцам.

## Решения владельца (2026-09-04)

1. **Отгрузка** = заказ в статусе `complete` («Выполнен»), месяц определяется **датой доставки**.
   Группа `complete` шире (`order-delivery-complete` «Заказ доставлен», `uderzhanie`
   «Удержание») — они **не** считаются, ровно как в «Оплате курьерам».
2. **Сумма отгрузки** = `summ` (только товары, без стоимости доставки).
3. **План** вводится в дашборде: план на месяц по каждому салону, город = сумма своих салонов.
4. **Негативная ОС** считается только со значением «Объективность проблемы = Подтверждено».
5. **Доступ:** управляющий видит только свои салоны (`user_stores`), админ — всю сеть.
6. **Состав салонов** — текущие 9 из справочника; остальные сайты CRM в показатели не идут.
10. **Склад — из МойСклада.** Приход = документ **«Оприходование»** (`enter`): поступление
    товара на склад с количеством и ценой по каждой номенклатуре. Списание = документ
    **«Списание»** (`loss`). Группы товаров — папки каталога **«Товары МС / Цветы»** и
    **«Товары МС / Клубника»**.
    - Доля списания цветка = сумма списанного цветка ÷ сумма оприходованного цветка
      за тот же период по складу салона.
    - Средняя цена клубники = сумма оприходованной клубники ÷ (вес оприходованной −
      вес списанной) за тот же период.

## Архитектура

### Где считать и где хранить

```
RetailCRM ──синк(есть, расширяем)──> couriers.db.courier_orders     ← п.1, 2, 5
Pyrus 1291124 ──синк(новый)────────> pyrus.db.nos_feedback           ← п.3
Pyrus 1327961 ──синк(есть)─────────> pyrus.db.quality_scores         ← п.4
МойСклад enter/loss ──синк(новый)──> moysklad.db.warehouse_flows     ← п.6, 7
                                     moysklad.db.warehouse_groups    ← папки → цветок/клубника
                                     barhat.db.salon_links           ← маппинг источников
                                     barhat.db.moysklad_store_links  ← склад МС → салон (есть)
                                     barhat.db.salon_plans           ← планы по месяцам
                    ↓
        src/salonkpi/server.py  (Blueprint /api/salon-kpi)
                    ↓
        src/dashboard/salon-kpi.js  (раздел «Показатели салонов»)
```

**Решение: не заводить второй синк заказов CRM, а расширить существующий.**
Модуль «Оплата курьерам» уже качает ровно тот же набор — `complete` + фильтр по дате
доставки. Второй синк означал бы удвоенную нагрузку на CRM и на медленный `/data`,
плюс два расходящихся ответа на вопрос «сколько отгрузили». Добавляем в
`courier_orders` три колонки (`total_summ`, `order_method`, `delivery_code`) и три поля
в `parse_order`.

**Но одними колонками не обойтись (найдено при критике, Чат 3).** Синк выбрасывает
заказы при записи — [couriers/server.py:146](src/couriers/server.py#L146):

```python
if not parsed["courier_id"] and not parsed["net_cost"]:
    continue     # самовывоз, «таких больше половины выполненных»
```

Для выплат это правильно, для показателей — смертельно: «Улица» это преимущественно
самовывоз (за 01–02.09 `self-delivery` 123 заказа против `dostavka-kurerom` 129), и
показатель №2 на такой витрине не считается вообще, а №1 занижен примерно вдвое.

Поэтому **фильтр «к выплате» переезжает из записи в чтение**: витрина хранит все
выполненные заказы, а запросы модуля курьеров получают условие
`courier_id IS NOT NULL OR net_cost > 0`. Рассмотренная альтернатива — вторая таблица
только для показателей — отвергнута: она возвращает ровно то, от чего уходим (два
набора данных и два ответа на «сколько отгрузили»), и прячет сегодняшний побочный
эффект — заказы без курьера и без себестоимости сейчас не видны нигде. Цена решения:
объём витрины растёт примерно вдвое (≈20 тыс. строк на 90 дней вместо ≈10 тыс. —
для SQLite незаметно) и правка касается денежных запросов, поэтому неизменность
отчёта выплат до/после закрывается тестом (шаг 1.9).

Цена решения: витрина глубиной с момента запуска синка (24.08.2026) — сравнения
«год к году» на ней не построить. Для «текущего месяца» этого достаточно; исторические
периоды догружаются ручным прогоном за период.

### Справочник соответствий — ядро модуля

Одна таблица связей вместо трёх колонок, потому что у салона бывает несколько ключей
в одном источнике (Академ и Академ-Крафт в CRM):

```sql
CREATE TABLE salon_links (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    store_id INTEGER NOT NULL,          -- barhat.db.stores.id
    source TEXT NOT NULL,               -- 'crm_site' | 'pyrus_nos' | 'pyrus_quality'
    external_key TEXT NOT NULL,         -- 'barkhat-ekb' | 'ЕКБ Б89' | 'ЕКБ Бажова'
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE UNIQUE INDEX idx_salon_links_key ON salon_links(source, external_key);
```

Уникальность по `(source, external_key)` — один внешний ключ не может принадлежать двум
салонам. Начальные значения — сид на 9 салонов × 3 источника, дальше правится в UI.

**Обязательный экран «Несопоставленное».** Список ключей, встреченных в данных за период,
но не привязанных ни к одному салону, с количеством и суммой. Без него переименование
салона в Pyrus молча обнуляет показатель, и это выглядит как «у нас стало меньше
негатива», а не как поломка. Тот же список показывается плашкой на главном экране,
если за выбранный месяц есть непривязанные записи.

### Планы отгрузок

```sql
CREATE TABLE salon_plans (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    store_id INTEGER NOT NULL,
    month TEXT NOT NULL,                -- 'YYYY-MM'
    plan_amount REAL NOT NULL,
    updated_by TEXT,
    updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE UNIQUE INDEX idx_salon_plans_month ON salon_plans(store_id, month);
```

Запись — `INSERT ... ON CONFLICT(store_id, month) DO UPDATE`, одним соединением,
править может только админ. Прошлые месяцы не перетираются: план — исторический факт.

### Витрина негативной ОС

По образцу `quality_scores`: одна строка на задачу, поля формы разложены по колонкам,
`raw_data` не парсится при чтении.

```sql
CREATE TABLE nos_feedback (
    task_id INTEGER PRIMARY KEY,
    form_id INTEGER NOT NULL,
    feedback_date TEXT,        -- поле 2, при пустом — create_date
    salon TEXT,                -- поле 16, сырое название из Pyrus
    category TEXT,             -- поле 18
    objectivity TEXT,          -- поле 22, нормализованное (trim!)
    source TEXT,               -- поле 20 «Откуда претензия»
    is_critical INTEGER,       -- поле 28
    order_number TEXT,         -- поле 5
    review_status TEXT,        -- поле 26
    updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

Синк — **не новый планировщик, а второй шаг существующего цикла Pyrus**
(`_scheduler_loop` в [pyrus/server.py:1721](src/pyrus/server.py#L1721)): в `pyrus.db` должен
писать один поток, иначе две волны бьют по одному файлу на общем диске `/data`. Своё
имя в `try_claim_scheduled_run('nos', ...)` — чтобы интервалы можно было развести.
Объём смешной (≈100 задач/мес), окно — последние 60 дней.

## Формулы показателей

Период по умолчанию — текущий месяц; переключатель месяца обязателен (управляющий
закрывает прошлый месяц уже в новом).

**1. Отгрузки и выполнение плана**
```
факт   = SUM(total_summ) по courier_orders, status='complete',
         delivery_date BETWEEN <1-е> AND <последнее число месяца>, site ∈ салона
план   = salon_plans.plan_amount за месяц
выполнение = факт / план * 100
```
Плюс две служебные цифры, без которых процент в середине месяца ни о чём не говорит:
темп (`факт / прошедшие дни × дней в месяце`) и «нужно в день, чтобы выполнить».

**2. Канал «Улица»**
```
улица = SUM(total_summ) где order_method = 'offline'
доля  = улица / факт * 100
```

**3. Негативная ОС**
```
кол-во = COUNT(nos_feedback) где objectivity = 'Подтверждено'
         и feedback_date в месяце, салон через salon_links
```
Рядом серым — «в разборе N» (объективность «Необходимо разбираться»): за август это
51 из 95, и без этой подписи основная цифра выглядит как полный объём негатива,
хотя это только разобранная его часть. Разрез по категориям ОС (Доставка, Цветок,
Ягода, Сервис, Сборка букета) — в раскрытии карточки.

**4. Качество сборки**

У видов заказа **два максимума**: 14 баллов (клубничный и цветочный букет, коробочка,
боксы) и 18 (клубнично-цветочный букет, коробочка с букетом, цветочно-клубничный бокс) —
см. `CATEGORIES_14` / `CATEGORIES_18` в [quality.py](src/pyrus/quality.py). Это разные
шкалы, и усреднять сырые баллы между ними нельзя: салон с бо́льшей долей
18-балльных заказов получит более высокий «средний балл» просто из-за состава.

```
главная цифра, % = SUM(total_score) / SUM(max_score) * 100     -- сравнима между салонами
рядом            = средний балл отдельно по 14- и по 18-балльным
подпись          = сколько оценок каждой группы
```

Показываем всегда все три: процент как основную величину, пару средних баллов
(«13,1 из 14 · 16,2 из 18») и состав выборки — без него процент не проверить.

**То же самое и по флористам**, и по той же причине: один собирает преимущественно
комбинированные заказы, другой — букеты, и их сырые баллы несравнимы. В раскрытии
салона — флорист, процент от максимума, оба средних балла и число оценок; сортировка
по проценту. Готовая функция `quality.get_salon_florists` уже отдаёт разбивку
`cat14` / `cat18` — её и берём, ничего не переписывая.

Имена флористов в Pyrus обезличены («Флорист 4») — так и будет отображаться.

**5. Доля такси-служб**
```
знаменатель = COUNT(заказов) где delivery_code ∈ курьерские типы
числитель   = те же заказы, где courier_id ∈ {2, 12, 169}
доля        = числитель / знаменатель * 100
```
Курьерские типы доставки и список такси-служб — **справочники с флагом**, не константы
в коде: `delivery_types.counts_as_courier` (сид: `dostavka-kurerom`, `courier`, `2`) и
`couriers.is_external_taxi` (сид: 2, 12, 169). Существующий `is_service` не подходит —
он шире и включает Купер с Фловоу.

**6. Доля списания цветка**
```
доля = SUM(списано, ₽) / SUM(оприходовано, ₽) * 100
```
Оба слагаемых — за один период, по складу салона, по товарам из папки
«Товары МС / Цветы». Сумма позиции = `quantity × price`. Если оприходования за период
не было, показатель не считается (`null`), а не показывает 0 или бесконечность.
Доля выше 20% помечается: практика показывает 4–14%, а 98% — это уже вопрос к тому,
как на точке оформляют документы, а не размер потерь.

**7. Средняя цена клубники**
```
цена = SUM(оприходовано, ₽) / (вес оприходованного − вес списанного)
```
Смысл: во сколько обошёлся килограмм клубники, реально пошедшей в дело, — чем больше
списали, тем дороже вышел остаток. Рядом обязательно показываем **закупочную цену**
(`сумма / вес прихода`): без неё непонятно, что именно добавило списание.

Знаменатель может стать нулём или отрицательным — списали больше, чем приняли за
период (например, остаток прошлого месяца). Тогда цена не считается и выводится «—»
с пояснением; выдавать в этом месте отрицательное число или делить на ноль нельзя.

Вес хранится в единицах МойСклада как есть. Перевод в килограммы — **коэффициент в
справочнике группы, а не константа в коде**: сейчас у товара «Клубника» единица не
задана и фактически это граммы, но как только её заведут в килограммах, зашитая
тысяча превратит 1 000 ₽/кг в миллион.

**Разрез «город»** — агрегат по салонам города; города берутся из `CITY_ALIASES`
(Новосибирск, Екатеринбург, Барнаул, Томск, Челябинск).

## Критика по фазам (Чат 3)

Проверялось по четырём вопросам: решает ли задачу, лучшее ли это решение, нет ли
конфликта с другими фазами, безопасно ли.

**Фаза 0 — принята с дополнением.** Справочник связей обязателен, спорить не с чем:
названия расходятся в четырёх системах и правятся людьми. Но было упущено два шага —
UI справочника (без него фазу нельзя проверить руками, а Фаза 5 к ней не относится) и
автоподсказка сопоставления. Ручное сопоставление 27 связей — это ровно тот ручной
труд, который CLAUDE.md велит отдавать агенту; предлагать связь автоматически, а
создавать только по клику. Добавлены шаги 0.7 и 0.8.

**Фаза 1 — переделана, была неработоспособна.** Синк курьеров отбрасывает при записи
заказы без курьера и без себестоимости, то есть весь самовывоз. «Улица» — это в
основном самовывоз, поэтому показатель №2 на такой витрине не считается вообще, а №1
занижен примерно вдвое. Три колонки этого не лечат. Фильтр «к выплате» перенесён из
записи в чтение (шаги 1.4–1.5), добавлен обязательный регресс выплат (1.9). Заодно
всплыло, что заказы без курьера и без себестоимости сейчас не видны нигде — после
правки они появятся в данных.

Отдельно добавлен шаг 1.8: новый курьер-агрегатор без флага молча занижает долю
такси-служб. Это тот же класс ошибки, что переименование салона, — лечится тем же
списком «требует решения», а не аккуратностью админа.

**Фаза 2 — принята.** Простая таблица, инвариант держит уникальный индекс, запись
через `ON CONFLICT` одним соединением. `log_action` на изменение плана — не
перестраховка: план задним числом меняют, и «кто поставил 3 млн» спросят обязательно.

**Фаза 3 — принята.** Ключевая деталь — висячий пробел в `'Подтверждено '`; при
сравнении по сырой строке показатель молча становится нулём. Решение встроить синк в
существующий цикл Pyrus (а не поднимать свой планировщик) снимает риск второй волны
записи в `pyrus.db` — в проекте это уже дважды клало сайт. Окно 60 дней выбрано
осознанно: обращение правят и через месяц после создания, а объём смешной.

**Фаза 4 — принята с двумя дополнениями.** Первое: кэш нужно сбрасывать после ввода
плана, иначе админ решит, что ручка не сработала. Второе, важнее: **проверка доступа
должна резать данные, а не только меню.** Управляющий не должен получить выручку
чужого города, подставив `store_id` в адрес; `unmapped` и справочник связей вообще
только админу. Добавлены шаги 4.6 (доработан) и 4.8.

**Риск, который фаза не закрывает и закрыть сама не может:** доступ строится на
`user_stores`, а у учётки, автосозданной входом из Пульса (роль `sso_viewer`),
привязок к салонам нет — она увидит пустой экран. Логика фильтрации взята из кассовых
смен ([cashshifts/server.py:229](src/cashshifts/server.py#L229)), там ровно то же
поведение. Вопрос вынесен владельцу (см. ниже): если управляющие ходят через Пульс,
кто-то должен один раз проставить им салоны, иначе модуль для них пустой.

**Фаза 5 — принята.** Чек-лист регистрации раздела (5.4) не бюрократия: каждый его
пункт — реальный баг из истории проекта. UI справочника уехал в Фазу 0, здесь
остаются плашки-предупреждения.

**Фаза 6 — принята, но перенесена по смыслу.** Регресс выплат (1.9) нельзя откладывать
до конца: это единственное место, где новая функциональность трогает деньги.
Остальные проверки на месте.

**Соответствие бизнес-цели.** Экран отвечает на вопрос управляющего «как идёт мой
месяц» пятью цифрами и не требует ни одного ручного отчёта. Ручной труд остаётся в
двух местах: ввод плана (раз в месяц, автоматизировать нечем — это управленческое
решение) и подтверждение сопоставлений (редко, с подсказкой). Обе точки осознанные.

## Pre-mortem: почему это может провалиться

1. **Салон переименовали в Pyrus** — показатель молча обнулился, никто не заметил месяц.
   → экран несопоставленного + плашка на главной; это не опция, а часть Фазы 0.
2. **Менеджер без привязанных салонов** видит пустой экран и считает, что модуль сломан.
   → явный текст «салоны не привязаны, обратитесь к администратору», а не пустая таблица.
   Тестовый прогон обязательно с менеджером, у которого салон есть, и с тем, у кого нет.
3. **План не введён** — выполнение показывает 0% и выглядит как провал салона.
   → «план на месяц не задан» вместо нуля.
4. **Синк курьеров сломался после правки** — деньги курьерам посчитаются неверно.
   → правка только аддитивная, прогон `scripts/` по модулю курьеров до и после.
5. **Три чтения из трёх баз на каждый запрос** на медленном `/data` дадут секунды.
   → агрегаты только GROUP BY по индексам, in-process кэш на 60 секунд, замер
   `x-envoy-upstream-service-time` после деплоя.
6. **Академ реально торгует** (10 заказов за 2 дня), но салона нет в справочнике —
   его отгрузки не попадут никуда. Решение владельца «только текущие 9» принято;
   строка «вне справочника» в списке несопоставленного покажет, сколько это стоит,
   и решение можно будет пересмотреть на цифрах.
7. **Клубнику заводят в килограммах вместо граммов** — и средняя цена превращается в
   миллион за килограмм, а выглядит как обычное число. → коэффициент в справочнике
   группы (3В.2), плюс проверка правдоподобия: цена вне диапазона 100–10 000 ₽/кг
   показывается с пометкой «проверьте единицу измерения».
8. **В папку «Цветы» или «Клубника» добавили подпапку** — товары из неё молча выпадут
   из расчёта. → группы задаются папкой И её потомками, а новые папки каталога, не
   отнесённые ни к одной группе, попадают в список несопоставленного.
9. **Списание на точке означает не потери, а способ учёта** (Блюхера 61 — 98% суммы
   прихода). Тогда показатель формально верен, но управляющий читает его как «мы
   выбросили почти всё». → цифра сопровождается расшифровкой (сколько ₽ прихода и
   списания за период), чтобы разговор шёл о документах, а не о числе.

## Решения по итогам Чата 3

7. **Управляющие заходят и через Пульс, и своими логинами.** Значит модуль обязан
   переживать учётку без привязанных салонов: внятная плашка «салоны не привязаны,
   обратитесь к администратору» вместо пустой таблицы, а админу — прямой путь
   проставить салоны (ручка `POST /api/users/<username>/stores` уже есть,
   [auth.py:1104](src/auth.py#L1104)). После первого деплоя проверить, у всех ли
   реальных управляющих привязки заполнены.
8. **Сравнения с сетью не показываем.** Управляющий видит только свои салоны и свой
   план; сводная таблица по всем салонам остаётся админу и директору.
9. **Динамика к прошлому месяцу делается сразу**, с честной оговоркой: заказы CRM в
   витрине с 24.08, поэтому июль и август догружаются разовым ручным прогоном
   (CRM историю отдаёт), а до появления полного месяца стрелка не рисуется вовсе —
   вместо неё «нет данных за прошлый месяц». Качество и НОС сравниваются сразу: их
   история в Pyrus глубокая.

Отложено сознательно: уведомления об отставании от плана и всплеске негатива —
в проекте нет ни Telegram-бота, ни другой доставки уведомлений, это отдельная работа.
Доля «Улицы» по количеству заказов (в дополнение к сумме) — по запросу, если
понадобится после первого месяца использования.
