# Оплаченные счета не доезжают до ПланФакта — план починки

**Статус:** черновик, ждёт согласования с владельцем
**Дата:** 2026-08-26
**Цель:** счёт, оплаченный любым способом, всё равно доезжает до ПланФакта; если не
доехал — это видно в дашборде, а не теряется молча.

## 1. Симптом

Счета `REF-000021` и `REF-000016` показаны в разделе как оплаченные, но в ПланФакте не
разнесены. Во вкладке «Требует внимания» их нет — сбой полностью беззвучный.

## 2. Диагноз — подтверждён прогоном на реальном коде (2026-08-26)

**Причина №1. Статус `paid` перегружен: он означает и «оплачен», и «разнесён».**

Статус `paid` ставится тремя путями, а в ПланФакт пишет только один:

| Путь | Пишет в ПланФакт |
|---|---|
| Синк `_run_planfact_sync` | да: `PUT /operations/outcome/{id}` → затем `mark_invoice_paid()` |
| Кнопка «Отметить оплаченным» | нет, только статус |
| Массовое действие «Отметить оплаченными» | нет, только статус |

В `_match_planfact_operation` (`src/invoices/server.py`) стоит ранний выход:

```python
if invoice["status"] == "paid":
    return {"status": "skip"}
```

Отсюда цепочка: счёт отметили оплаченным руками → позже в ПланФакте появляется операция
с `REF-…` в назначении → синк видит `paid` → **молча пропускает навсегда**.

**Воспроизведено локально** (временная база, сеть заблокирована, клиент ПланФакта
подменён): счёт, оплаченный кнопкой, даёт `{'status': 'skip'}`, отправок в ПланФакт — 0,
записей в «Требует внимания» — 0. Контрольный счёт в статусе «Согласован» тем же кодом
разносится штатно (`matched`, одна отправка, статус становится `paid`).

**Причина №2 — ранний `skip` стоит до записи в `invoice_planfact_unmatched`**, поэтому
счёт не попадает в «Требует внимания». Владелец узнаёт о проблеме только из ПланФакта.

**Причина №3 (найдена по ходу, отдельный дефект).** `int(pf_category_id)` и
`int(project_id)` падают с `ValueError`, если id сопоставления вписан руками и не является
числом. Вписать такой id можно прямо в интерфейсе: когда ПланФакт не отвечает, вкладка
«Сопоставление» предлагает ручной ввод. Падение происходит **внутри цикла по операциям**,
поэтому обрывается весь прогон — остальные операции не разносятся тоже.

**Возможная причина №4 — проверить на боевых данных.** Если платёжку делали руками в
банке, а не через автозагрузку из модуля, в назначении платежа нет `REF-` кода, и
`searchString="REF-"` операцию просто не вернёт. `_build_bank_payment_purpose` ставит
`match_code` в начало назначения только при отправке через модуль.

**Неактуально из промпта:** `_auto_archive_if_ready` в коде больше нет — автоархивацию
отменил владелец 2026-08-25. Неразнесённый оплаченный счёт из списка не исчезает.

## 3. Решение

**Развести два разных факта.** «Оплачен» — факт об оплате. «Разнесён в ПланФакт» —
отдельный факт, со своим полем. Синк смотрит на него, а не на статус.

### Ключевая опасность: дубли в ПланФакте

Как только ранний `skip` убран, синк начнёт считать кандидатами **все** оплаченные счета,
включая те, что он сам разнёс раньше. Без признака «уже разнесён» он перезапишет их
повторно. Поэтому новое поле обязано быть **заполнено задним числом** до того, как
изменится логика: разнесённые ранее счета видны по `invoice_history` — статус `paid` им
проставил `planfact-sync`, а не человек.

### [x] Фаза 1 — Признак «разнесён в ПланФакт»

- [x] `ALTER TABLE invoices ADD COLUMN planfact_operation_id TEXT`
      и `planfact_synced_at TEXT` — под `BEGIN IMMEDIATE`, по образцу
      `_ensure_invoice_clarification_columns`
- [x] **Бэкфилл до смены логики:** счетам, у которых в `invoice_history` статус `paid`
      проставлен `planfact-sync`, записать `planfact_synced_at` из времени этой записи
- [x] Поле возвращается в списке и карточке (обе выборки берут `i.*`)
- [x] **Done when:** у ранее разнесённых счетов признак есть, у оплаченных вручную — нет

**Как сделано.** Две грабли по ходу:

1. Вызов миграции нельзя ставить рядом с остальными `ALTER` в начале
   `init_invoices_tables`: бэкфилл читает `invoice_history`, а она создаётся ниже по той
   же функции. При раннем вызове падала вся инициализация, и таблицы, которые создаются
   после, не появлялись вовсе (поймано прогоном: «no such table
   invoice_store_planfact_projects»). Вызов стоит в конце `init`.
2. Бэкфилл вынесен из-под условия «колонок ещё нет» и идёт **каждый старт**. Иначе один
   неудачный запуск (упал процесс, оборвалась сборка) оставил бы ранее разнесённые счета
   без признака — и следующий прогон синка разнёс бы их повторно, создав дубли в
   ПланФакте. Запрос идемпотентен, трогает только пустые значения.

### [x] Фаза 2 — Синк смотрит на признак, а не на статус

- [x] Ранний `skip` по `status == 'paid'` заменён на `skip` по `planfact_synced_at`
- [x] Оплаченный, но не разнесённый счёт — нормальный кандидат: `paid` добавлен в список
      допустимых статусов, проверки «не распределён» и «нет сопоставления» отрабатывают
      и для него, попадая в `invoice_planfact_unmatched`
- [x] После успешной записи проставляются `planfact_operation_id` и `planfact_synced_at`
- [x] **Done when:** счёт, оплаченный кнопкой, разносится следующим прогоном синка;
      повторный прогон его уже не трогает

**Как сделано.** Признак разноски ставится ДО `mark_invoice_paid`: если процесс упадёт
между шагами, лучше «разнесён, но не отмечен оплаченным» (человек увидит и поправит), чем
«оплачен, но не отмечен разнесённым» — второе синк попробует разнести ещё раз и создаст
дубль в ПланФакте.

Проверено прогоном на реальном коде (сеть заблокирована, клиент ПланФакта подменён):
счёт, оплаченный кнопкой, теперь `matched` с одной отправкой; повторный прогон даёт
`skip` без отправок; счёт, разнесённый синком до миграции, бэкфилл помечает и синк его
больше не трогает; оплаченный вручную бэкфилл не помечает; `dry_run` не пишет ни в
ПланФакт, ни в признак.

## 5. Вопрос к владельцу до кода

**Должна ли кнопка «Отметить оплаченным» сразу писать в ПланФакт?**

Предлагаю **нет**: живой вызов внешнего API из кнопки уже клал весь сайт (инцидент
2026-08-17, два воркера заняты медленным ответом). Безопаснее: счёт помечается «ждёт
разноски» и уезжает следующим прогоном синка, а в интерфейсе это видно (Фаза 3).
Если нужна разноска немедленно — отдельная кнопка «Разнести сейчас» с коротким таймаутом.
