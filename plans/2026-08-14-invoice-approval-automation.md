# Автоматизация согласования и оплаты счетов — план

**Статус:** [ ] В процессе
**Дата:** 2026-08-14 (обновлено)
**Цель:** Свой модуль в дашборде (без Pyrus) для полного цикла счёта. Ручными остаются только: создание счёта, согласование (решение) и подпись/отправка платежа в банке. Всё остальное — автоматически.

---

## Контекст (as-is, до изменений)

1. Сотрудник заводит счёт в форме Pyrus → согласование.
2. Согласованный счёт руками вводится в банк-клиент, оплачивается.
3. Плательщик руками ставит статус «Оплачен» в задаче Pyrus.
4. Оплата автоматически попадает в ПланФакт — банк уже подключён к ПФ напрямую (подтверждено).
5. Сотрудник руками разносит операцию по салону и статье расхода в ПФ.

## Правки от пользователя (Чат 1, раунд 2)

1. Ручной ввод счёта в банк-клиент — тоже должен уйти, а не остаться как раньше планировалось.
2. Pyrus в этой схеме использовать не хотим — форму и согласование делаем своим модулем.

Уточнено у пользователя:
- Банк — **Модульбанк**. У него есть публичный API (`api.modulbank.ru`), токен генерируется прямо в личном кабинете без согласований. Есть метод `POST /v1/operation-upload/1c` — загружает платёжное поручение в формате 1С в личный кабинет со статусом «Черновик»; подписание — только внутри личного кабинета вручную.
- Уровень автоматизации отправки платежа: **платёжка готовится и загружается автоматически, отправляет (подписывает) человек**. Полная автоотправка через API отклонена — сознательно оставляем контроль над движением денег за человеком.

## Архитектура (to-be)

Новый модуль внутри существующего Flask-дашборда (`src/dashboard/`) — использует готовую авторизацию и роли (admin/manager/florist/florist_analyst), plus новый бэкенд-пакет `src/invoices/` (по аналогии с `src/moysklad/`).

**Собственная модель данных счёта** (SQLite/Postgres, как у `src/pyrus/storage.py`, но без Pyrus): номер счёта (уникальный, генерируется модулем), контрагент, реквизиты, сумма, назначение платежа, салон, статья расхода, файл/скан счёта, статус (черновик → на согласовании → согласован/отклонён → отправлен в банк → оплачен), история согласования, created_by.

### Пошагово

1. **Создание счёта** — сотрудник заполняет форму в дашборде. РУЧНОЙ. Модуль сам генерирует уникальный номер счёта и подставляет его в назначение платежа.
2. **Согласование** — workflow внутри модуля (один или несколько согласующих по ролям), уведомления (Telegram-бот). Решение — РУЧНОЕ, интерфейс и уведомления — автоматические.
3. **Формирование платёжки** — сразу после финального согласования модуль автоматически собирает платёжное поручение в формате 1С и отправляет через Модульбанк API (`POST /v1/operation-upload/1c`) → попадает в личный кабинет банка статусом «Черновик». Автоматически, без участия человека.
4. **Подпись и отправка** — ответственный заходит в личный кабинет Модульбанка, проверяет реквизиты и подписывает/отправляет платёж. РУЧНОЙ — единственная точка, где человек управляет движением денег.
5. **Поступление в ПланФакт** — банк уже настроен на автоматическую выгрузку в ПФ, операция появляется там сама, без нашего участия.
6. **Матчинг** — модуль опрашивает API ПланФакт на новые операции списания, вытаскивает номер счёта из назначения платежа (regex), ищет соответствующую запись в своей БД счетов.
7. **Авто-разноска** — при совпадении модуль через API ПФ проставляет статью расхода и салон (уже известны из карточки счёта) и помечает счёт в своей БД как «Оплачен». Автоматически.
8. **Исключения** — если матчинг не удался (нет номера, опечатка, один платёж на несколько счетов) — уведомление ответственному, ручная разноска как fallback. Не должно тихо теряться.

## Открытые вопросы для Чата 2 (разбивка на фазы)

- Точная спецификация метода `operation-upload/1c` Модульбанка: обязательные поля платёжки (БИК, счёт получателя, КБК/НДС и т.д.), формат номера счёта в назначении платежа, лимиты на частоту запросов.
- Точные эндпоинты API ПланФакт для (а) опроса новых операций — вебхук или поллинг, (б) обновления категории/объекта на операции. Нужен токен API ПФ, сейчас есть только косвенные данные (через агрегатор Albato).
- Схема согласования: сколько этапов, кто согласующие, нужны ли параллельные/последовательные согласования, лимиты по сумме (например, крупные счета — доп. согласующий).
- Формат уведомлений: Telegram-бот (уже есть канал у бизнеса) или встроенные уведомления в дашборде.
- Частичные оплаты / оплата нескольких счетов одним платёжным поручением — не пытаться угадывать, сразу в очередь на ручную разноску.
- Нужна ли миграция существующих незавершённых счетов из Pyrus, или стартуем модуль с нуля.

## Риски (pre-mortem)

- Ошибка в реквизитах при автосборке платёжки (напр. неверный БИК из карточки контрагента) → банк отклонит или платёж уйдёт не туда. Нужна валидация реквизитов на этапе создания счёта, не на этапе отправки.
- Токен Модульбанк API — чувствительные данные, хранить только в `.env` в корне проекта, не логировать.
- Изменение схемы согласования «на лету» (кто-то в отпуске, нужен временный согласующий) — учесть делегирование прав в workflow.
- Если у ПФ нет вебхуков, только поллинг → задержка между оплатой и разноской. Не критично, но заложить в ожидания.
- Отказ от Pyrus означает полный перенос процесса — нужен явный день/момент отсечки, чтобы не было счетов «зависших» в старой и новой системе одновременно.

## Итог

**Реализовано (Фазы 1–4):** свой модуль счетов на оплату (`src/invoices/`) — модель данных, Flask API, права доступа, фронтенд в дашборде. Задеплоено на прод, три раунда пост-деплойных фиксов после реального использования:

1. У существующих admin/manager не догрузилось право на новый модуль (`migrate_permissions_for_existing_users()` бэкафиллит роли только пользователям без единой записи в permissions) — добавлена `migrate_new_module_permissions()` в `auth.py`.
2. Модалка создания счёта затемняла всю страницу — оверлей был сиблингом `.modal`, а не потомком (во всех остальных модалках оверлей вложен внутрь `.modal` и наследует его `display:none`).
3. `src/dashboard/users.js` хранит свой отдельный список модулей (`MODULE_NAMES`, `ROLE_PERMISSIONS`) для формы управления пользователями, не синхронизированный с `auth.py` — `invoices` туда не попал, админ не мог выдать доступ вручную.

Все три — из-за того, что при добавлении нового модуля в этот дашборд нужно править несколько мест одновременно (чек-лист сохранён в памяти как `dashboard-new-module-checklist`). Проверено: `scripts/test_invoices_db.py` (создание → согласование → отклонение → фильтры) на throwaway SQLite; `py_compile`/`node --check` на все изменённые файлы; баланс тегов в `index.html`; живая проверка на проде после каждого фикса. Полный запуск сервера в браузере на этой машине не проверялся — нет рабочего venv с зависимостями проекта (см. память `project-no-local-dev-env`).

Сотрудники теперь могут полностью перестать заводить счета в Pyrus: создание и согласование живут в `/invoices`. Отправка в банк и разноска в ПФ — пока вручную, как в старом процессе.

**Не начато (Фазы 5–7):** автоматическое формирование платёжки в Модульбанк и авторазноска в ПланФакт — заблокированы отсутствием токенов API этих сервисов.

**Решение по ходу:** от идеи многошагового согласования отказались в пользу одного согласующего (admin) — соответствует размеру команды (владелец работает один), можно расширить позже без изменения схемы БД (поле `approved_by` уже отдельное).
