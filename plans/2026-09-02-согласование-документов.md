# Согласование документов — черновой план (Чат 1 из 3)

**Статус:** 🎯 Черновой план + ресёрч. Фазы намечены крупно, детализация — Чат 2, критика — Чат 3.
**Дата:** 2026-09-02
**Цель:** Сотрудник заводит документ (доверенность, УПД, договор поставки, аренды) в дашборд,
владелец согласует его в одной очереди, документ уходит на подпись и возвращается в модуль
подписанным оригиналом. Реестр помнит сроки действия и сам напоминает о продлении.
В дальнейшем часть документов приезжает не руками, а из ЭДО по API.

| С каких типов документов стартуем | **Все сразу, но общим каркасом** | Одна сущность «документ» + справочник типов. Никаких отдельных таблиц под доверенности и договоры |
| Кто согласует | **Всё согласует владелец** | Маршрутов и конструктора маршрутов нет. Есть **очередь к одному человеку** |

### Раунд 2 (после ресёрча, вопросы §10 первой редакции)

| Вопрос | Ответ | Что из этого следует |
|---|---|---|
| Типы на старте | **Все четыре**: доверенности, договоры аренды, договоры поставки, УПД и акты | Справочник типов заполняется сидом сразу; форма обязана работать и с суммой, и со сроком действия, и без них |

| Кто видит реестр | **Как в других модулях:** админ — все документы, менеджер — только по своим салонам | Переиспользуем механику прав по салонам; отдельно решается видимость документов **без** салона (решение №14) |
| Печатная форма доверенности | **Шаблон есть, генерация нужна** | Фаза печатных форм входит в MVP, а не в усиление. Нужен сам файл шаблона |
| Объём | **20-100 документов в месяц** | Массовые действия и пагинация обязательны; распознавание сканов окупается; место на `/data` надо считать заранее |

## 3. Ресёрч: как это решают другие

### 3.1 Маршруты и SLA (мировая практика CLM/BPM)

- Четыре типа маршрута: последовательный, параллельный, условный, иерархический; на практике —
  гибрид: параллельно внутри этапа, последовательно между этапами.
  Правило выбора одно: **зависит ли согласующий от решения предыдущего**. Если нет — параллельно.
- **SLA ставится на этап, а не на процесс**, и главное в нём не число часов, а таймер с эскалацией:
  «поставь срок, эскалируй на молчание, считай эскалации» — отчёт по эскалациям находит узкое
  место быстрее любого опроса.
- Решение согласующего — всегда одно из **трёх** с меткой времени и причиной: согласовано /
  отклонено / **согласовано с условием**. Бинарные системы убивают сделки, которые условие бы спасло.
- Внедрять узко: взять самый частый тип документа, отработать 30 дней, потом расширять.
- Метрики, по которым видно, работает ли процесс: время цикла согласования, доля согласованных
  с первого раза, частота застреваний.
- **Автоматизировать всё вокруг решения, но не само решение** — ровно принцип из нашего CLAUDE.md.

Источники: [Sirion](https://www.sirion.ai/library/contract-insights/sequential-vs-parallel-approval-differences/),
[Kissflow](https://kissflow.com/workflow/bpm/parallel-vs-sequential-approvals-in-bpm/),
[Aavenir](https://aavenir.com/contract-approval-workflow/),
[Docupilot](https://www.docupilot.com/blog/contract-approval-workflow),
[Automation Consulting Services](https://www.automationconsultingservices.org/blog/approval-routing-automation).

**Что берём:** три исхода решения вместо двух, срок на этап с напоминанием, узкий пилот, метрики.
**Что не берём:** параллельные и условные маршруты — согласующий один (решение владельца).

### 3.2 Российская практика СЭД

- Маршрут может зависеть от суммы договора, типа контрагента, региона; способность к условному
  согласованию считается индикатором зрелости СЭД. Нам это пока не нужно, но структура
  «тип документа → правила» закладывается сразу.
- Лист согласования (кто, когда, какое решение, комментарий) — обязательная часть карточки:
  именно к нему возвращаются через годы.
- Отдельная стадия после согласования: **протокол разногласий** либо отправка на подпись;
  подписанный скан прикладывается к карточке, документ уходит в архив.
- КЭП — практика для внешних документов и всего, что может попасть в суд; НЭП/ПЭП — для внутренних.
- Сначала регламент, потом автоматизация.

Источники: [Jet form](https://jet-form.ru/blog/soglasovanie-dogovorov-v-organizacii),
[А2Б](https://a2b.su/blog/soglasovanie-v-sed-ponyatie-vidy-tipichnye-oshibki/),
[EnDocs](https://endocs.ru/top-programm-dlya-soglasovaniya-dogovorov/).

### 3.3 ЭДО: что нас ждёт, когда дойдём до интеграции

**Контур.Диадок.** Полноценный HTTP API, есть OpenAPI-спецификация.
Модель — **опрос ленты событий**, а не вебхуки: `GetNewEvents` (актуальна V8, V7 доживает
переходный период), листается через `afterIndexKey`. Документы — `GetDocuments` (V4),
фильтры включают статусы согласования: `WaitingForResolution`, `Approved`, `Disapproved`,
`Finished`. Согласование в API устроено парой «запрос резолюции → резолюция»
(`ResolutionRequest` → `ResolutionApprovement` / `ResolutionDisapprovement`).
Отправка — `PostMessage` (V3); **API не создаёт файл подписи**, подпись формирует наша сторона.
Авторизация — OpenID Connect плюс ключ разработчика по заявке. Подключение и входящие бесплатны,
платят за исходящие пакетами; маршруты согласования внутри Диадока — платная опция.

Источники: [документация API](https://developer.kontur.ru/doc/diadoc-api/),
[GetNewEvents](https://developer.kontur.ru/doc/diadoc-api/http/GetNewEvents.html),
[GetDocuments V4](https://developer.kontur.ru/doc/diadoc-api/http/GetDocuments_V4.html),
[авторизация](https://developer.kontur.ru/doc/diadoc-api/authentication.html),
[тарифы](https://kontur.ru/diadoc/price), [маршруты согласования](https://www.diadoc.ru/features/marshruty-soglasovaniya).

**СБИС / Saby.** Похожая модель: `СБИС.ПрочитатьДокумент`, `СБИС.ЗаписатьДокумент`,
`СБИС.ПодготовитьДействие`; входящие обрабатываются по статусу документа; есть отложенное
подписание — документ уходит контрагенту в момент, когда уполномоченный нажал «Подписать».
Источники: [порядок работы](https://saby.ru/help/integration/api/sequence),
[команды](https://saby.ru/help/integration/api/documents/).

**Вывод для плана:** обе системы устроены одинаково — «лента событий + карточка документа +
резолюция». Значит наша модель данных должна иметь `source`, `external_id`, `external_status`
и курсор синхронизации, а клиент — прятаться за интерфейсом из трёх методов. Тогда выбор
оператора остаётся решением на потом и не переписывает модуль.

### 3.4 Подпись: почему в модуле её не будет

- Подписать от имени организации в 2026 можно **только личной КЭП сотрудника вместе с МЧД**
  (ст. 17.2-17.3 63-ФЗ). С 01.02.2026 приказ Минцифры № 1001 ужесточил реквизиты МЧД:
  обязателен срок действия и наименование полномочия, паспортные данные стали необязательны.
- Серверная КЭП на Linux — это либо КриптоПро CSP с контейнером на машине, либо облачная
  КриптоПро DSS (ключи в HSM, подпись по API). Технически возможно, но это отдельный проект
  с лицензиями и разделением доступа к ключу.
- Внутренние документы можно закрыть **ПЭП**: логин-пароль плюс Положение о ПЭП и подписки
  сотрудников об ознакомлении. Без этих двух бумаг ПЭП юридических последствий не порождает.

Источники: [Контур.УЦ про МЧД](https://ca.kontur.ru/articles/25216-mashinochitaemaya_doverennost),
[Главбух про изменения с 01.02.2026](https://www.glavbukh.ru/art/387296-kak-primenyat-mchd-mashinochitaemaya-doverennost-v-2025-godu-polnoe-rukovodstvo-dlya),
[ст. 6 63-ФЗ](https://www.consultant.ru/document/cons_doc_LAW_112701/1d9a7d8c65fe414edd67ecae8acfa41bdbe52ba1/),
[КриптоПро DSS](https://cryptopro.ru/products/dss).

**Решение:** подписи в модуле нет (ответ владельца). Есть статус «на подписании» и фиксация
факта: кто подписал, когда, чем (бумага / ЭДО / КЭП), файл подписанного оригинала.
Отметка о подписании — не подпись, и в интерфейсе она так и называется.

### 3.5 Распознавание документа нейросетью

Практика внедрений сходится на одном: **распознавание даёт черновик, а не проводку**. Даже
идеально прочитанные реквизиты могут относиться не к тому договору и не к тому периоду.
Типовая архитектура: OCR/VLM → классификация типа → извлечение полей в JSON → валидация
(ИНН, арифметика сумм и НДС) → предзаполненная карточка со статусом «черновик» и подсветкой
полей с низкой уверенностью → подтверждение человеком. Начинать — с однотипного потока
хорошего качества.

Источники: [обзор LLM-распознавания](https://alial.group/raspoznavanie-dokumentov-ocr),
[практика бухгалтерии](https://mgutu.ru/media/buhuchet/raspoznavanie-pervichnyh-dokumentov-s-ii/),
[Smart Engines](https://smartengines.ru/intelligent-document-recognition/).

**Что берём:** извлечение полей через Claude API (vision) → черновик карточки с подсветкой
неуверенных полей. Это единственное место модуля, где агент заменяет ручной труд целиком,
и ровно оно отвечает на вопрос CLAUDE.md «что здесь делает человек, что мог бы сделать агент».
Ставим отдельной поздней фазой, а не в MVP.

## 4. Зафиксированные решения

1. **Одна сущность `documents` + справочник типов.** Отдельных таблиц под доверенность,
   УПД и договор нет. Разница между типами живёт в справочнике: какие поля обязательны,
   нужен ли срок действия, есть ли печатная форма, за сколько дней напоминать.
2. **EAV не делаем.** Общие поля — колонками; редкие поля типа — в `extra_json` одним полем.
   Конструктора полей в интерфейсе нет: типов документов у нас единицы, и «настраиваемая
   форма» — классический код ради кода.
3. **Модуль не подписывает.** Юридическая подпись — вне системы (решение владельца).
   Внутри — «Отметить подписанным» с обязательным оригиналом-файлом и способом подписания.
4. **Согласующий один — владелец.** Конструктора маршрутов нет. При этом решение согласующего
   пишется в отдельную таблицу `document_approvals` (шаг, кто, когда, исход, комментарий),
   а не в колонки документа: это и есть лист согласования, и он же снимет миграцию, когда
   согласующих станет двое. *Проверить на «код ради кода» в Чате 3.*
5. **Три исхода решения, а не два:** согласовано / **согласовано с условием** / отклонено.
   Условие — обязательный текст, попадает в ленту и в карточку. Без него договор с одной
   правкой в пункте уходит на второй круг целиком.
6. **`status` без `CHECK`-констрейнта.** SQLite не меняет `CHECK` через `ALTER` — только
   пересозданием таблицы, которое на двух воркерах уже дважды роняло прод (урок счетов,
   решение №5 того плана). Список статусов держим в Python-константе. Сразу закладываем
   и будущие ЭДО-статусы.
7. **Поля под ЭДО закладываются сразу, интеграция — нет.** `source` (`manual` / `edo`),
   `edo_operator`, `external_id`, `external_status`, `synced_at`. Пустые они ничего не стоят,
   а добавление колонок в живую таблицу на Amvera — всегда риск.
8. **Счета сюда не переезжают.** Счёт на оплату — отдельный модуль со своим процессом,
   банком и ПланФактом. Документы с ним связываются ссылкой (договор → счета по нему),
   но не поглощают его.
9. **Контрагенты — общий справочник `invoice_counterparties`.** Второй справочник в проекте
   недопустим; при необходимости таблица переименовывается позже, отдельной задачей.
10. **Персональные данные — режим ограниченного доступа.** Доверенность содержит ФИО и,
    возможно, паспорт сотрудника. Такие документы видит автор, владелец и роли с явным правом;
    в общий список они попадают без персональных полей. В логи и аудит содержимое не пишем.
11. **Срок действия — первоклассное поле, а не текст.** Дата окончания, признак пролонгации,
    напоминание за N дней. Ради этого модуль во многом и делается: пропущенный срок аренды
    стоит дороже, чем всё согласование вместе взятое.
12. **Уведомления — в дашборде** (бейдж, счётчик «N ждут вас», плюс лента). Telegram-бота
    в проекте нет; появится — прикрутим отдельной задачей.
13. **Протокола разногласий как стадии нет** (ответ владельца). Хватает «согласовано
    с условием» плюс обсуждение в карточке. Переговоры с контрагентом идут вне системы,
    в модуль возвращается новая версия файла (`document_files.version`).
14. **Права — по образцу счетов и смен: админ видит всё, менеджер — свои салоны.**
    Отдельно решается документ **без салона** (договор поставки на всю сеть, доверенность
    на юрлицо): у типа документа появляется флаг `visible_to_managers`. По умолчанию
    общесетевой документ виден только админу и автору — иначе договор с поставщиком и его
    условия уедут всем управляющим сразу. Документы типов с `is_sensitive` (доверенности)
    видит автор, тот, на кого он выписан, и админ.
15. **Печатная форма доверенности входит в MVP** (ответ владельца: шаблон есть).
    Подстановка полей в готовый шаблон, выдача файла на подпись. Нужен исходный файл шаблона —
    без него фаза не стартует.
16. **Импорт архива — отдельная фаза до реестра сроков.** Пустой реестр не напоминает ни
    о чём, а вручную разобрать сотню договоров никто не станет. Развилка для Чата 3: если
    в архиве больше ~50 файлов, распознавание (Фаза 9) выгоднее сделать **до** импорта и
    залить архив уже черновиками карточек. Нужен объём архива в файлах.

## 5. Модель данных (черновик)

Все таблицы — в общей `barhat.db` рядом со счетами и авторизацией.

```sql
-- Справочник типов документа. Единственное место, где типы различаются.
CREATE TABLE IF NOT EXISTS document_types (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    code TEXT NOT NULL,                    -- power_of_attorney | upd | contract_supply | contract_rent | other
    name TEXT NOT NULL,
    direction TEXT NOT NULL,               -- incoming | outgoing | internal
    needs_amount INTEGER NOT NULL DEFAULT 0,
    needs_validity INTEGER NOT NULL DEFAULT 0,   -- есть ли срок действия
    needs_counterparty INTEGER NOT NULL DEFAULT 1,
    remind_days_before INTEGER,            -- за сколько дней напомнить об окончании
    sla_hours INTEGER,                     -- срок на согласование
    is_sensitive INTEGER NOT NULL DEFAULT 0,     -- есть персональные данные (доверенности)
    visible_to_managers INTEGER NOT NULL DEFAULT 0,  -- виден ли менеджерам документ БЕЗ салона
    is_active INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
-- Частичный уникальный индекс, а не UNIQUE(code): на грабли
-- «имя занято невидимой удалённой записью» модуль счетов уже наступал.
CREATE UNIQUE INDEX IF NOT EXISTS idx_document_types_code
    ON document_types(code) WHERE is_active = 1;

CREATE TABLE IF NOT EXISTS documents (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    type_id INTEGER NOT NULL REFERENCES document_types(id),
    title TEXT NOT NULL,
    doc_number TEXT,
    doc_date TEXT,
    -- стороны
    payer_id INTEGER REFERENCES invoice_payers(id),        -- наше юрлицо
    counterparty_id INTEGER REFERENCES invoice_counterparties(id),
    counterparty_name TEXT,                                -- снимок на момент заведения
    counterparty_inn TEXT,
    store_id INTEGER REFERENCES stores(id),                -- салон (аренда и т.п.)
    city_id INTEGER REFERENCES invoice_cities(id),
    -- содержание
    amount REAL,
    currency TEXT NOT NULL DEFAULT 'RUB',
    valid_from TEXT,
    valid_until TEXT,
    auto_renew INTEGER NOT NULL DEFAULT 0,
    subject TEXT,                                          -- предмет / суть
    extra_json TEXT,                                       -- редкие поля типа
    -- процесс
    status TEXT NOT NULL DEFAULT 'draft',                  -- без CHECK, см. решение №6
    approval_due_at TEXT,                                  -- SLA согласования
    signed_at TEXT,
    signed_by TEXT,
    signed_method TEXT,                                    -- paper | edo | kep
    is_archived INTEGER NOT NULL DEFAULT 0,
    -- ЭДО (заранее, решение №7)
    source TEXT NOT NULL DEFAULT 'manual',
    edo_operator TEXT,
    external_id TEXT,
    external_status TEXT,
    synced_at TEXT,
    -- служебное
    created_by TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at TEXT
);
CREATE INDEX IF NOT EXISTS idx_documents_status ON documents(status);
CREATE INDEX IF NOT EXISTS idx_documents_valid_until ON documents(valid_until);
CREATE UNIQUE INDEX IF NOT EXISTS idx_documents_external
    ON documents(edo_operator, external_id) WHERE external_id IS NOT NULL;

CREATE TABLE IF NOT EXISTS document_approvals (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    document_id INTEGER NOT NULL REFERENCES documents(id),
    step_no INTEGER NOT NULL DEFAULT 1,
    approver TEXT NOT NULL,
    decision TEXT,                          -- approved | approved_with_condition | rejected | rework
    condition_text TEXT,
    decided_at TEXT,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS document_files (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    document_id INTEGER NOT NULL REFERENCES documents(id),
    kind TEXT NOT NULL DEFAULT 'draft',     -- draft | signed | annex | protocol
    version INTEGER NOT NULL DEFAULT 1,
    original_filename TEXT NOT NULL,
    stored_filename TEXT NOT NULL,
    uploaded_by TEXT NOT NULL,
    uploaded_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS document_history (   -- поле, старое, новое, кто, когда
    ...  -- копия invoice_history
);
CREATE TABLE IF NOT EXISTS document_comments ( -- обсуждение
    ...  -- копия invoice_comments
);
CREATE TABLE IF NOT EXISTS document_links (    -- связи: договор ↔ допник ↔ счёт
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    document_id INTEGER NOT NULL REFERENCES documents(id),
    linked_type TEXT NOT NULL,              -- document | invoice
    linked_id INTEGER NOT NULL,
    relation TEXT NOT NULL                  -- annex_of | invoice_by | replaces
);
```

**Статусы:** `draft` → `on_approval` → (`approved` | `approved_with_condition` | `rejected` |
`rework`) → `signing` → `signed` → `archived`; плюс `cancelled` и на будущее `sent_to_edo`,
`waiting_counterparty`.

**Файлы** — в папку из `resolve_data_path("DOCUMENT_FILES_DIR", "document_files")`.
Относительный путь на Amvera = потеря файлов на следующем деплое, так уже терялись вложения
к счетам 2026-08-23.

## 6. API (черновик)

Новый blueprint `src/documents/`, префикс `/api/documents`.

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/documents` | Список: фильтры (тип, статус, контрагент, салон, срок, автор), сортировка по белому списку, `limit/offset`, `total` |
| GET | `/api/documents/summary` | KPI: ждут согласования · просрочен SLA · истекают в 30 дней · без подписанного оригинала |
| POST | `/api/documents` | Создание (черновик или сразу на согласование) |
| GET | `/api/documents/<id>?include=history,comments,files,approvals` | Карточка одним запросом |
| PUT | `/api/documents/<id>` | Правка полей; границы правки — по статусу |
| POST | `/api/documents/<id>/submit` | Отправить на согласование |
| POST | `/api/documents/<id>/decision` | Решение: `approved` / `approved_with_condition` / `rejected` / `rework` + текст |
| POST | `/api/documents/<id>/sign-off` | Отметить подписанным: дата, способ, файл оригинала |
| POST/GET/DELETE | `/api/documents/<id>/files` | Вложения, версии |
| GET | `/api/documents/files/<id>/inline` | Превью: **белый список типов, `nosniff`, CSP**; PDF — `sandbox allow-scripts` без `allow-same-origin` (иначе просмотрщик гаснет — урок Фазы 3 счетов) |
| GET/POST | `/api/documents/<id>/comments` | Обсуждение на любом статусе |
| GET/POST/PUT | `/api/document-types` | Справочник типов (admin) |
| POST | `/api/documents/<id>/print` | Печатная форма по шаблону (доверенность) — поздняя фаза |

Требования, наследуемые из счетов и обязательные здесь: `BEGIN IMMEDIATE` на «проверил →
записал», `try/finally` на каждом соединении, `require_ajax_header` на новых POST,
запись в историю **после** коммита своей транзакции (вложенное соединение = взаимная
блокировка, ловили дважды), лимит размера пакета на массовых действиях.

## 7. Интерфейс

Раздел «Согласование документов», по [DESIGN-SPEC.md](../DESIGN-SPEC.md), токены `--bx-*`,
все правила CSS под скоуп страницы.

- **Шапка** — «N документов ждут вас», рядом «M истекают в этом месяце».
- **KPI-плитки:** ждут согласования · просрочен SLA · истекают в 30 дней · подписаны, но без оригинала.
- **Виды:** *Очередь* (документ слева, поля и кнопки справа — как в счетах), *Реестр*
  (таблица с фильтрами и сортировкой), *Сроки* (что заканчивается — по месяцам).
- **Карточка:** превью файла, поля, лист согласования, лента событий и обсуждения, связи
  с другими документами и счетами, версии файлов.
- **Заведение:** одна форма, набор полей зависит от типа; вставка скрина из буфера и
  drag-and-drop (обработчики вешаются только при активной странице раздела), сжатие фото
  на клиенте, `accept="image/*,.pdf"`, кнопка съёмки только при `pointer: coarse`.
- Перерисовка через `innerHTML` обязана возвращать прокрутку и фокус — правило CLAUDE.md,
  на длинной форме это ловится сразу.

## 9. Pre-mortem: почему через год это провалилось

1. **Никто не заводит документы** — проще скинуть фото в мессенджер. Лечение: заводить обязан
   тот, кому нужен результат (доверенность не выдаётся мимо модуля), и заведение должно быть
   быстрее мессенджера — фото с телефона в два касания.
2. **Модуль стал файлопомойкой:** документы лежат, процесса нет, сроки никто не смотрит.
   Лечение: KPI «истекают» на первом экране; документ без срока и без оригинала — видимый долг.
3. **Универсальный тип выродился в конструктор форм** ради трёх редких полей. Лечение:
   решение №2 и запрет на конструктор в интерфейсе.
4. **Пересечение со счетами:** часть документов заводят и туда, и сюда, суммы расходятся.
   Лечение: явная связь «договор → счета», счёт остаётся в своём модуле.
5. **Диск.** Сканы договоров тяжелее скринов счетов, `/data` платный и медленный. Лечение:
   сжатие изображений на клиенте, лимит на файл, отчёт по занятому месту.
6. **Персональные данные утекли** через общий список или логи. Лечение: решение №10, проверка
   в `/security-review` до деплоя.
7. **ЭДО пришёл — и модель не подошла.** Лечение: решение №7 (поля источника заранее) и
   клиент за интерфейсом из трёх методов.
8. **Согласующий один и он же владелец** — очередь встала, потому что человек в отпуске.
   Лечение на будущее: замещающий согласующий; в MVP — хотя бы видимый счётчик простоя.

- [ ] `require_ajax_header` на всех новых POST-ручках
- [ ] Вид «Очередь»: список слева, документ по центру, поля и кнопки справа;
      `GET /api/documents/<id>?include=history,comments,files,approvals` — **один** запрос
      на открытие карточки, не четыре
- [ ] Лента событий = слияние истории и переписки; сообщения визуально отличаются
      от системных записей; поле ввода доступно на любом статусе, `Ctrl+Enter` отправляет,
      черновик переживает перерисовку
- [ ] Лист согласования в карточке: шаг, кто, когда, исход, условие
- [ ] Счётчик «N ждут вас» в шапке + KPI-плитки (`GET /api/documents/summary`)
- [ ] Адрес карточки — параметром `?doc=<id>`, не сегментом пути (роутер дашборда разбирает
      `pathname` целиком и увёл бы на первую доступную страницу); `popstate` вешается

- [ ] Диалоги — только `window.BarhatUI`: нативные `confirm`/`prompt` в iframe Пульса молча
      игнорируются, и кнопка выглядит сломанной
- [ ] **Done when:** полный цикл проходит на реальном бэкенде; повторное решение по тому же
      шагу даёт 409; возврат на доработку без причины — 400; причина видна в ленте у автора

### [ ] Фаза 5 — Подписание (фиксация факта)

**Goal:** в карточке лежит подписанный оригинал, и видно, чего ещё не хватает.

- [ ] Статус `signing` после согласования; `POST /api/documents/<id>/sign-off`: дата,
      способ (`paper` / `edo` / `kep`), кто подписал
- [ ] Файл оригинала обязателен: `sign-off` без файла `kind='signed'` — 400
- [ ] В интерфейсе действие называется **«Отметить подписанным»**, не «Подписать»:
      модуль не подписывает и не хранит ключей (решение №3)
- [ ] KPI «ждут оригинал» — согласованные документы без файла `kind='signed'`
- [ ] **Done when:** документ без оригинала виден в KPI и уходит из него после загрузки
      файла; в истории есть кто и когда отметил

### [ ] Фаза 6 — Импорт архива

**Goal:** действующие договоры лежат в реестре со сроками, а не в облаке.

- [ ] `POST /api/documents/import` (`@role_required("admin")`): пачка файлов, лимит
      на размер пакета, каждый файл — черновик документа со статусом `draft`
- [ ] Дедупликация по `file_hash`: повторная заливка того же файла не создаёт второй документ,
      а возвращает «пропущен, уже есть №N»
- [ ] Экран разбора: очередь черновиков, минимум полей на карточку (тип, контрагент,
      салон, срок действия), кнопка «в реестр»
- [ ] Отчёт по итогам: залито N, без срока M, пропущено дублей K — поимённо
- [ ] Свободное место на `/data` проверяется **до** записи пакета: диск платный,
      сканы договоров тяжелее скринов счетов
- [ ] **Done when:** архив залит, повторная заливка не плодит дубли, документы без срока
      видны отдельным списком и их число известно

Развилка решения №16: если файлов больше ~50, эту фазу выгоднее делать **после** Фазы 9 —
тогда карточки приезжают уже заполненными, и человек только проверяет.

### [ ] Фаза 7 — Реестр, права и сроки

**Goal:** реестр открыт нужным людям и сам напоминает о приближающемся сроке.

- [ ] `GET /api/documents` — фильтры (тип, статус, контрагент, салон, срок, автор),
      сортировка по **белому списку** полей (подстановка только по словарю, неизвестный
      ключ — 400), `limit`/`offset` с потолком, `total` только при `offset=0`
- [ ] Права: админ видит всё; остальные — по `get_user_stores(username)`
      ([cashshifts/storage.py:515](../src/cashshifts/storage.py#L515)), как в
      `_build_invoice_filters` ([invoices/storage.py:2114](../src/invoices/storage.py#L2114))
- [ ] Документ **без салона** виден менеджеру только при `visible_to_managers` у типа;
      типы с `is_sensitive` — автор, тот, на кого выписан, и админ (решение №14)
- [ ] Точечная выдача доступа к одному документу — по образцу `invoice_access`
- [ ] `documents` в `SSO_MODULES` и раздача права ролям (перенесено из Фазы 1)
- [ ] Вид «Сроки»: что заканчивается, по месяцам; плитка «истекают в 30 дней»
- [ ] Таблица `document_reminders(document_id, kind, sent_at)` — иначе напоминание уйдёт
      на каждом тике планировщика
- [ ] Планировщик по образцу [cards_sync.py](../src/invoices/cards_sync.py):
      `try_claim_scheduled_run` + `try_acquire_sync_lock` с TTL + `renew_sync_lock`
      по времени. **Своя стартовая задержка**, не совпадающая с 15-минутным циклом
      синка карт: `/data` общий и медленный, волна синков кладёт логин всем сразу
- [ ] Напоминание = запись в ленте документа + бейдж в разделе. Telegram нет (решение №12)
- [ ] Часовые пояса через `BarhatTime`; `valid_until` — календарная дата, не конвертируется
- [ ] **Done when:** менеджер видит только свои салоны, админ — всё, доверенность чужого
      сотрудника не видна; за N дней до окончания аренды напоминание появляется само
      и не повторяется на каждом тике

### [ ] Фаза 8 — Печатная форма доверенности и связи

**Goal:** доверенность выходит из карточки готовой к подписи, без Word.

- [ ] Получить от владельца файл шаблона и список подставляемых полей
- [ ] **Рекомендация: HTML-шаблон + печать браузером.** В `requirements.txt` нет ни
      `python-docx`, ни `reportlab`, ни `weasyprint`; HTML даёт нулевые зависимости,
      точный контроль вёрстки и PDF через «Сохранить как PDF». Подстановка в DOCX —
      запасной вариант, у него своя ловушка: Word рвёт плейсхолдер на несколько `run`,
      и наивная замена по тексту не срабатывает
- [ ] `GET /api/documents/<id>/print` — отдельная страница печати, поля экранируются
- [ ] Реквизиты нашего юрлица — из `invoice_payers`, не из текста шаблона
- [ ] Связи `document_links`: договор ↔ допсоглашение ↔ счета по договору; в карточке —
      блок «Связанные документы», в счетах ничего не меняем
- [ ] **Done when:** доверенность печатается из карточки, реквизиты подставлены верно,

### [ ] Фаза 9 — Черновик карточки из скана (Claude API)

- [ ] **Done when:** на 10 реальных сканах ≥70% полей заполнены верно, все ошибки видны

## Итог

Ресёрч проведён, шесть вопросов владельцу сняты, фазы разбиты на шаги (Чат 2 закрыт

3. Ответ, нужна ли роль «заводит документы за других» (помощник, бухгалтер) — если да,
