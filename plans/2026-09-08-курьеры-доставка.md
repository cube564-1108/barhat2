# Модуль «Курьеры: доставка заказов» — план

**Статус:** 🎯 Черновой план (Чат 1 из 3) — ресёрч проведён, развилки сняты владельцем,
**Фаза 0 (разведка CRM) выполнена 2026-09-08** — результаты в §2-бис
**Дата:** 2026-09-08
**Цель:** Курьер видит на телефоне заказы своего города, забирает один себе (бронь),
отмечает «забрал» и «доставил» — каждое действие меняет статус в RetailCRM без участия
человека. Если заказов несколько — модуль подсказывает порядок объезда с учётом времени
доставки и открывает маршрут в Навигаторе.

## 2. Решения владельца (сняты 2026-09-08, менять только по его слову)

| Развилка | Решение |
|---|---|
| Как заказ достаётся курьеру | **Свободный захват + правила.** Курьер видит все подходящие заказы своего города и берёт сам. Ограничители: лимит одновременных броней, автоснятие зависшей брони, счётчик просрочек |
| Маршрут | **Свой расчёт, без платных API.** Координаты — Геокодер Яндекса (бесплатный лимит, кэш по адресу), порядок точек — свой солвер по временным окнам, езда — кнопка в Яндекс.Навигатор / 2ГИС |
| Уведомления | **PWA на телефон + web push.** Иконка на рабочем столе, звук при новом заказе даже если приложение закрыто |
| Срок брони | **От времени доставки.** Бронь держится, пока до окна доставки > 60 мин; за 60 мин — пуш «подтвердите», ещё через 15 мин бронь слетает и заказ видят все |
| Что значит «готов / не готов» | Владелец уточнил: это **доступность заказа** (свободен / забронирован / уже забран другим) |
| Готовность букета | В CRM **есть статус «Заказ готов»**, им помечают собранные заказы. Читаем его — своего экрана для флориста не делаем. Курьер видит и «готов», и «ещё собирают» |

## 2-бис. Результаты разведки CRM (Фаза 0, прогон 2026-09-08)

Скрипт `scripts/probe_crm_courier_fields.py`, только чтение. Замер: 1440 заказов за
7 дней, полная история изменений за 2026-09-07 (5090 записей), 121 доставочный заказ
за день.

**Поля — всё нужное есть, ничего заводить в CRM не надо:**

| Что нужно курьеру | Поле в CRM | Заполнено |
|---|---|---|
| Получатель, имя | `customFields.recipient_name` | 36% |
| Получатель, телефон | `customFields.recipient_phone` | 33% |
| «Получатель = заказчик» | `customFields.recipient_customer` (bool) | 8% = True |
| Заказчик, телефон | `customer.phones[].number` | 99% |
| **«Не связываться с получателем»** | `customFields.ne_sviazyvatsia_s_poluchatelem` | 5% = True |
| Адрес доставки | `delivery.address.text` | 99% у своей доставки |
| Окно доставки | `delivery.time.from` + `.to` | 97% |
| Плановая готовность | `customFields.data_i_vremia_gotovnosti` (дата+время) | 100% |
| Комментарий оператора | `managerComment` | 49% |
| Комментарий клиента | `customerComment` | 26% |
| Ещё один комментарий | `customFields.note_text` | 24% |
| Фото товара | `imageUrl` в `/api/v5/store/products` | 98%, все 30 проверенных ссылок живые |

**Статусы — все нужные заведены:**

| Действие | Код | Название | Как используется сейчас |
|---|---|---|---|
| Заказ виден курьеру | `send-to-florist` | Передан флористу | 75% заказов |
| Готовность букета | `order-complete` | **Заказ готов** | 85% заказов |
| Вызван курьер | `call-courier` | Вызван курьер | 83% заказов |
| Забрал | `send-to-delivery` | Передан курьеру | **2%** — свободен под нас |
| В пути | `wait-client` | Ожидает вручения | **0%** — свободен под нас |
| Доставлен | `order-delivery-complete` | Заказ доставлен | **0%** — свободен под нас |
| Не доставлен | `order-delivery-fail` | Заказ НЕ доставлен | 1% |

То есть живой путь сегодня: «Передан флористу → Заказ готов → Вызван курьер → Выполнен».
Статусы под действия курьера практически не используются — наш модуль не будет спорить
с людьми за одно поле.

**Пять находок, которые меняют решения:**

1. **«Заказ готов» ставят в момент начала окна доставки, а не заранее.** С поправкой на
   пояс салона: UTC+7 — медиана 20 мин до окна, у 34% статус ставят уже ПОСЛЕ его начала;
   UTC+5 — медиана 5 мин, после начала у 22%. **Ждать этого статуса курьеру нельзя** —
   он выедет впритык. Значит «Забрал» по готовности не блокируем (см. правку §4), а
   основной ориентир для курьера — плановое `data_i_vremia_gotovnosti` (заполнено у 100%).
2. **Заказы Яндекс.Доставки адреса не содержат вовсе** (`ya-dostavka` — 0% адресов,
   46 заказов в день из 121). Они и не для наших курьеров: лента фильтруется по типу
   доставки `dostavka-kurerom` (у него адрес есть у 99%).
3. **Координат в CRM нет ни в каком виде** — геокодер для маршрута обязателен.
4. **Историю нельзя листать по `page`**: на глубине CRM отвечает «Use the shift of the
   `filter[sinceId]` instead of `page`». И первый вызов без курсора отдаёт записи
   **с 2021 года** (41 708 записей за 7 дней в общей ленте). Значит курсор модуля
   инициализируется не нулём, а текущим максимумом id, иначе первый запуск вычитает
   четыре года истории.
5. **Свои записи в истории опознаются надёжно:** у записи есть `source` (`user` / `api` /
   `rule` / `code`) и `apiKey` вида `{'current': bool, 'id': int}`. Эхо наших правок
   отсекается по `apiKey.id`.
6. **Фото есть, но тяжёлые.** Все 30 проверенных ссылок отдают 200, однако это оригиналы
   с сайта: медиана **211 КБ**, максимум 1,4 МБ, миниатюр в CRM нет (`offers.images` —
   тот же самый URL). Значит: в ленте фото нет вовсе, в карточке — по тапу на позицию
   (решение владельца), плейсхолдер при ошибке. Прокси с ресайзом не делаем — это
   зависимость Pillow, ещё один кэш на медленном `/data` и лишняя работа ради экрана,
   который открывают осознанно. Если на мобильном интернете окажется тяжело — отдельная
   фаза. CSP правок не требует: `img-src` в политике не задан (там только
   `frame-ancestors`), внешние картинки не блокируются.

**Что печатать нельзя.** Первый прогон вывел в консоль имя и телефон получателя: в белом
списке стоял весь блок `customFields`, а в нём лежат `recipient_name`/`recipient_phone`.
Исправлено — теперь в белом списке точечные поля, персональные печатаются «формой»
(длина строки, число цифр). Сырые JSON — только в `c:/tmp`.

## 3. Ресёрч: что делают в мире и что из этого берём

Источники в §12. Коротко — что применимо, а что нет.

**Берём:**

1. **Пул + захват с ограничителями, а не чистый FCFS.** Вендоры (Bringg, Burq) и патенты по
   last-mile сходятся: открытый «кто первый нажал» даёт черри-пикинг — близкие заказы
   разбирают за секунды, дальние висят. Лечится не алгоритмом, а правилами: лимит броней,
   срок жизни брони, видимая статистика просрочек. Именно это и выбрано.
2. **Карточка-превью с триажем информации.** У курьера решение принимается на ходу: на
   превью только то, по чему принимают решение (номер, улица, время доставки, салон
   забора, состояние). Всё остальное — по тапу. Это прямое требование владельца и оно
   совпадает с практикой драйверских приложений.
3. **Крупные цели и текст, а не иконки.** Исследование редизайна драйверского приложения:
   дешёвые Android, дождь, солнце, спешка. Значит: кнопка действия во всю ширину, минимум
   48 px по высоте, подпись словом, а не пиктограммой, контраст под солнце.
4. **Предустановленные причины вместо ввода текста.** Набирать текст за рулём никто не
   будет: «не дозвонился», «получатель просит позже», «адрес не тот» — кнопками.
5. **Подтверждение доставки жестом, а не тапом.** Свайп «Доставлено» защищает от случайного
   нажатия в кармане; необратимое действие не должно висеть на одном тапе.
6. **Инкрементальное чтение изменений по курсору.** RetailCRM штатных вебхуков не даёт, но
   даёт `/api/v5/orders/history` с `filter[sinceId]` — официально рекомендованный способ
   «постоянной трансляции изменений во внешнюю систему». Один дешёвый запрос вместо
   перебора заказов (см. §6).
7. **Фиксация того, что реально ушло во внешнюю систему.** Наше же правило из `CLAUDE.md`
   (история с НДС в банк): храним, какой статус и когда мы отправили в CRM, и что она
   ответила.

**Отвергаем:**

- **Яндекс Маршрутизация** — от 4,8 млн ₽/год (мониторинг без планирования), при 3–8 точках
  на курьера это несопоставимо с задачей.
- **Автоназначение «ближайшему курьеру»** — требует постоянной геолокации курьеров
  (батарея, приватность, согласие) и точных координат. Для города с несколькими курьерами
  выигрыш меньше цены.
- **Пакетирование заказов алгоритмом (batching)** — имеет смысл на десятках заказов в час
  из одной точки; у нас курьер сам решает, что везёт вместе, а модуль лишь подсказывает
  порядок.
- **Рейтинг курьера / acceptance rate как санкция** — гиг-механика для тысяч исполнителей.
  У нас штатные курьеры, здесь работает разговор, а не алгоритм. Статистику просрочек
  показываем, но она — вход для человека, не автомат.

## 4. Жизненный цикл заказа в модуле

```
   CRM: «Передан флористу»
            │  (лента изменений, ≤ 60 сек)
            ▼
   ┌─────────────────┐   бронь    ┌──────────────┐  забрал   ┌───────────┐ доставил ┌───────────┐
   │  Свободен       │──────────▶ │ Забронирован │─────────▶ │  В пути   │────────▶ │ Доставлен │
   │ (виден всем)    │◀────────── │  (виден всем │           │           │          │           │
   └─────────────────┘  отказ /   │  как занятый)│           └─────┬─────┘          └───────────┘
                        автоснятие└──────────────┘                 │
                                                                   ▼
                                                          ┌──────────────────┐
                                                          │ Проблема:        │
                                                          │ не дозвонился /  │
                                                          │ перенос / отказ  │
                                                          └──────────────────┘
```

**Готовность букета — вторая, независимая ось.** Заказ становится виден курьеру со статуса
«Передан флористу», а когда флорист переводит его в **«Заказ готов»**, у карточки меняется
признак готовности. То есть у заказа одновременно два состояния:

```
доступность (наша):   свободен → забронирован → в пути → доставлен
готовность (из CRM):  собирают → готов
```

Бронировать можно и то, что ещё собирают: курьер планирует ходку заранее.

**«Забрал» у неготового заказа не блокируем — предупреждаем.** Разведка (§2-бис) показала:
статус «Заказ готов» ставят в момент начала окна доставки, а у трети заказов уже после
него. Курьер, которому запретили забирать неготовое, будет стоять в салоне и ждать, пока
флорист щёлкнет статус, — то есть модуль начнёт мешать работе вместо того, чтобы помогать.
Поэтому:

- готовность показывается бейджем, а главный ориентир на карточке — **плановое время
  готовности** (`data_i_vremia_gotovnosti`, заполнено у 100% заказов);
- у неготового заказа кнопка «Забрал» требует подтверждения («заказ не отмечен готовым,
  всё равно забираю») и пишет отметку в журнал;
- доля таких заборов — метрика для владельца: если она высокая, проблема не у курьеров,
  а в том, что статус ставят задним числом.

⚠️ **Ловушка: статус в CRM — одно поле, а пишут в него двое.** Флорист ставит «Заказ
готов» уже после того, как курьер забронировал. Если бы бронь жила в статусе CRM, отметка
флориста её бы затёрла — и наоборот. Поэтому:

- **Бронь хранится только у нас** (`delivery_assignments`), в CRM она не отражается статусом.
- **Смена статуса в CRM не снимает нашу бронь** — кроме отмены заказа (группа `cancel`)
  и перевода в статус, которого нет в списке видимых: тогда бронь снимается автоматически,
  курьеру уходит пуш «заказ отозван».
- Если владелец захочет видеть бронь в CRM — это **отдельное поле или комментарий**,
  а не статус. Отдельной фазой, когда станет понятно, нужно ли это оператору.

**Каждый переход пишет статус в CRM.** Какой именно код статуса ставится на каждое
действие — **настраивается в справочнике модуля**, а не зашито в коде. Это прямое
требование `CLAUDE.md` («то, что уходит во внешнюю систему, — данные, а не название»):
статусы в CRM переименовывают и заводят новые, и вывод кода из названия сломается молча.

Справочник `courier_action_statuses`: действие → код статуса CRM, заполняется владельцем
из выпадающего списка реальных статусов CRM (они уже синхронизируются в `order_statuses`).
**Пустой маппинг блокирует действие** с внятным текстом («для действия „Забрал“ не выбран
статус в CRM»), а не отправляет заказ в CRM как есть.

**Исходы, кроме успешного:** «не дозвонился», «перенос по просьбе получателя», «отказ» —
отдельные кнопки с фиксацией причины. Без них курьер, столкнувшись с реальностью, просто
не тронет модуль, и данные разъедутся с жизнью.

## 5. Модель данных (новые таблицы, база `couriers.db`)

```sql
-- Состояние заказа в глазах курьеров. Отдельно от courier_orders: та витрина
-- перезаписывается синком целиком (DELETE по окну дат), и бронь бы стиралась.
CREATE TABLE delivery_assignments (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    retailcrm_order_id INTEGER NOT NULL,
    courier_user_id INTEGER NOT NULL,      -- users.id, не courier_id из CRM
    state TEXT NOT NULL,                   -- claimed | picked_up | delivered | released | expired | problem
    claimed_at TEXT NOT NULL,
    picked_up_at TEXT,
    delivered_at TEXT,
    released_at TEXT,
    release_reason TEXT,                   -- self | expired | admin
    problem_code TEXT,                     -- no_answer | reschedule | refused | wrong_address
    problem_note TEXT,
    expires_at TEXT NOT NULL               -- вычисляется при брони, см. §7
);

-- Инвариант «у заказа не больше одной живой брони» — на уровне БД.
CREATE UNIQUE INDEX IF NOT EXISTS idx_assign_one_active
    ON delivery_assignments(retailcrm_order_id)
    WHERE state IN ('claimed', 'picked_up');

CREATE INDEX IF NOT EXISTS idx_assign_courier_state
    ON delivery_assignments(courier_user_id, state);

-- Что мы отправили в CRM и что она ответила. Очередь + журнал в одной таблице:
-- отправка не должна происходить внутри HTTP-запроса курьера.
CREATE TABLE crm_status_outbox (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    retailcrm_order_id INTEGER NOT NULL,
    assignment_id INTEGER,
    action TEXT NOT NULL,                  -- claim | pickup | deliver | problem
    target_status TEXT NOT NULL,           -- код статуса CRM на момент отправки
    state TEXT NOT NULL DEFAULT 'pending', -- pending | sent | failed
    attempts INTEGER NOT NULL DEFAULT 0,
    next_attempt_at TEXT,
    sent_at TEXT,
    response_code INTEGER,
    error_message TEXT,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX IF NOT EXISTS idx_outbox_pending ON crm_status_outbox(state, next_attempt_at);

-- Действие курьера → код статуса CRM. Заполняет человек, регуляркой не выводим.
CREATE TABLE courier_action_statuses (
    action TEXT PRIMARY KEY,               -- claim | pickup | deliver | no_answer | reschedule | refused
    status_code TEXT,                      -- NULL = действие заблокировано
    updated_by TEXT,
    updated_at TEXT
);

-- Какие статусы CRM что означают для курьера. Справочник, а не константа в коде:
-- сегодня видимый статус один («Передан флористу»), завтра заведут ещё.
--   role = 'visible' — заказ показывается курьеру
--   role = 'ready'   — заказ собран («Заказ готов»); тоже видимый
CREATE TABLE courier_visible_statuses (
    status_code TEXT PRIMARY KEY,
    role TEXT NOT NULL DEFAULT 'visible',
    updated_by TEXT,
    updated_at TEXT
);
```

## 6. Как заказы попадают в модуль быстро

Существующий синк ходит раз в 30 минут и выгружает окно по дате доставки — для отчёта это
нормально, для курьера нет: заказ «на сейчас» протухнет.

**Решение — два контура вместо учащения существующего:**

| Контур | Что делает | Частота | Цена |
|---|---|---|---|
| Глубокий синк (есть) | Полное окно дат, витрина, веса, показатели | 30 мин | Десятки запросов |
| **Лента изменений (новый)** | `GET /api/v5/orders/history?filter[sinceId]=N` | **60 сек** | 1 запрос, ~1 КБ |

Лента отдаёт только изменившиеся заказы с курсором. Логика тика:

1. Прочитать `sinceId` из `sync_state`. **Если его нет — не начинать с нуля.** Первый
   вызов без курсора отдаёт историю с 2021 года (проверено), поэтому при инициализации
   курсор ставится на текущий максимум id: узкое окно `filter[startDate]` за последние
   несколько минут → взять максимальный `id`.
2. Запросить историю по `filter[sinceId]`. **Листать только курсором:** на глубине CRM
   отвечает `Use the shift of the filter[sinceId] instead of page` — параметр `page`
   для истории неприменим.
3. Записи с `source = 'api'` и нашим `apiKey.id` **пропустить** — это эхо наших же
   записей, иначе получим цикл. Структура: `apiKey = {'current': bool, 'id': int}`.
4. Для заказов, чей статус попал в `courier_visible_statuses` или которые уже есть в
   модуле, — дозапросить карточку заказа и обновить строку витрины.
5. Сохранить новый `sinceId` **только после** успешной обработки страницы.
6. Новый заказ, ставший видимым, → пуш курьерам города.

**В ленту берём только свою доставку** (`delivery.code = dostavka-kurerom`). Заказы
Яндекс.Доставки — это 38% доставочных заказов дня, и адреса у них нет вовсе: показывать
их курьеру нечем и незачем.

Ограничения, которые обязаны быть по нашим же правилам:
- Своя стартовая задержка планировщика (не совпадающая с задержками других синков — иначе
  все синки идут одной волной по общему медленному `/data`).
- Лок с TTL и продление по времени.
- RetailCRM: не чаще 10 запросов/сек с одного IP. Тик в 60 сек с одним запросом — запас
  в тысячи раз.
- **Экран курьера не зовёт CRM.** Он читает только нашу базу, одним запросом. Внешний вызов
  из обработчика уже дважды укладывал прод.

## 7. Правило брони (полностью)

**Захват:**
- Курьер видит заказы своего города со статусами из `courier_visible_statuses`
  (сегодня — «Передан флористу») и без живой брони.
- Лимит одновременных броней — **настройка на город, а не одно число на всю сеть**
  (решение владельца 2026-09-08: число курьеров по городам разное). Таблица
  `courier_city_settings`: город → лимит броней, горизонт бронирования, тихие часы.
  Пустая строка = дефолты модуля, заводить руками каждый город не требуется.
- Нельзя забронировать заказ с датой доставки не сегодня/не завтра — чтобы нельзя было
  «забить неделю с утра». Горизонт — тоже параметр.

**Срок жизни (решение владельца):**
```
expires_at = начало окна доставки − 60 мин
за 15 мин до expires_at → пуш курьеру «Подтвердите: вы едете за заказом N»
наступил expires_at и статус всё ещё «забронирован» → бронь снимается,
     заказ возвращается в общий список, курьеру — пуш «Бронь снята»
```
- После «Забрал» бронь не сгорает никогда: заказ физически у курьера.
- Заказ без разобранного времени доставки → срок брони считается от конца дня салона,
  и такой заказ помечается в списке отдельно («время уточняется»).
- Самостоятельный отказ от брони — кнопка, без объяснений, но с записью в журнал.
- Автоснятия и отказы видны в отчёте по курьеру. Это вход для разговора, не для санкции.

**Гонка — по правилу `CLAUDE.md` «проверил → записал = одна транзакция»:**
```python
conn.execute("BEGIN IMMEDIATE")          # write-лок ДО чтения
# нет ли живой брони на этот заказ; не превышен ли лимит у курьера
conn.execute("INSERT INTO delivery_assignments ...")
conn.execute("COMMIT")
```
плюс частичный уникальный индекс (см. §5), плюс блокировка кнопки на фронте (`guardClicks`).
На проде до 16 параллельных обработчиков и запрос к базе стоит 90–700 мс — без этого двое
курьеров заберут один букет. Ровно так 29.08.26 открылись три смены на одной точке.

`IntegrityError` → **409 с текстом «Заказ уже забрал <имя>»**, а не 500.

⚠️ **Часовой пояс.** «За 60 минут до доставки» считается по стенным часам салона. Салоны
живут в UTC+5 и UTC+7, в базе всё в UTC, а пояс салона в системе **ещё не заведён**
(см. `plans` по таймзонам). Без него правило брони поедет на два часа у половины городов.
Поэтому пояс салона — Фаза 1, до всякой брони.

## 8. Экраны курьера

Всё по `DESIGN-SPEC.md`, без эмодзи, диалоги через `window.BarhatUI`.

**Экран 1. Лента «Свободные заказы»** — список превью-карточек:
```
┌──────────────────────────────────────────┐
│ № 12345          ● Свободен    ✓ Готов   │
│ Восход 3  →  ул. Ленина, 45              │
│ Доставка 14:00–15:00 · через 1 ч 20 мин  │
│ [ Забронировать ]                        │
└──────────────────────────────────────────┘
```
- Номер, салон-забор → улица и дом, окно доставки, обратный отсчёт.
- Два бейджа, потому что состояния два (§4): доступность — `Свободен` /
  `Забронирован (Иван)` / `Забрал Иван`, и готовность — `Готов` / `Собирают`.
  Курьер видит, что происходит со всеми заказами, а не только со своими.
- Фильтры сверху: `Все` / `Свободные` / `Готовые` / `Мои`. «Готовые и свободные» — то,
  что курьер смотрит чаще всего, поэтому это состояние списка по умолчанию.
- Заказ, ставший готовым, поднимается в списке и подсвечивается (плюс пуш тому, кто его
  забронировал).
- Занятые заказы показываем, но кнопка неактивна. Скрывать их нельзя: пропавший из списка
  заказ выглядит как сбой.
- Сортировка по времени доставки. Курьер видит **весь свой город**, а не один салон
  (решение владельца: за ходку берут заказы из разных салонов), но есть фильтр по салону
  и группировка «по салону забора» — чтобы собрать ходку из одной точки, когда так удобнее.
- **Телефона и точного адреса (квартира, подъезд, код) в ленте нет** — только улица и дом.
  Полные контакты открываются после брони (§10).

**Экран 2. Карточка заказа** (по тапу на превью):
- Номер заказа, статус, салон и адрес забора.
- Состав: строки позиций с названием и количеством, **фото открывается по тапу**
  (решение владельца 2026-09-08). Оригиналы весят 211 КБ в медиане, курьер на мобильном
  интернете — грузить их пачкой при каждом открытии карточки незачем. В строке —
  маленькая иконка «есть фото», по нажатию полноэкранный просмотр.
- Адрес доставки полностью, дата и время.
- Комментарий оператора (`managerComment`) и комментарий клиента (`customerComment`) —
  отдельными блоками, они разные по смыслу.
- Получатель: имя и телефон; **если поля получателя пустые — имя и телефон клиента**,
  с явной подписью «клиент» (курьер должен понимать, кому звонит: сюрприз-доставка —
  обычное дело у цветов).
- Кнопка звонка (`tel:`), кнопка «Маршрут» (deeplink в Навигатор/2ГИС).
- Действие внизу во всю ширину: `Забронировать` → `Забрал` → свайп `Доставлено`.
- «Проблема» — вторая кнопка, открывает список причин.

**Экран 3. «Мои заказы»** — забронированные и в пути, сортировка в порядке объезда,
сверху — сводка «3 заказа, ближайший к 15:00».

**Экран 4. «Маршрут»** (§9).

**Общее для всех экранов:**
- Перерисовка через `innerHTML` обязана возвращать прокрутку (`keepModalScroll`) —
  правило `CLAUDE.md`, иначе на длинном списке курьера выбрасывает наверх при каждом
  обновлении.
- Обновление ленты — раз в 30 сек и по возврату во вкладку (`visibilitychange`),
  без бесконечного поллинга в фоне.
- Оффлайн: если сети нет, показываем последнее загруженное с плашкой «данные на HH:MM» —
  цифра вчерашней свежести полезнее прочерка. Действия при отсутствии сети —
  «нет соединения, попробуйте снова» (офлайн-очередь в v1 не делаем, как и в PWA списаний).

## 9. Маршрут

**Что считаем:** порядок объезда для заказов, которые курьер уже взял (2–8 точек).
Не «оптимальный маршрут по городу» — этим занимается Навигатор.

**Данные:**
0. Координат в CRM нет — разведка проверила все поля адреса, там только текст и город.
   Значит геокодер обязателен, вариант «взять готовые координаты» отпал.
1. Координаты адреса — Геокодер Яндекса, результат навсегда в `geocode_cache`.
   Геокодируем **один раз при появлении заказа в модуле**, а не при построении маршрута:
   иначе курьер ждёт внешний API на экране.
2. Адрес, который не разобрался (точность «город» или ошибка) → заказ в маршруте
   помечается «адрес не распознан», ставится в конец и **не ломает расчёт**.

**Точек забора несколько** (решение владельца: курьер за одну ходку берёт заказы из
разных салонов города). Значит маршрут — это не «старт из салона и объезд», а
чередование: забор в салоне A → доставка → забор в салоне B → доставки. В расчёте это
жёсткое ограничение предшествования: заказ нельзя доставить раньше, чем забран, а забор
нельзя сделать раньше готовности. Салон, из которого уже всё забрано, из маршрута
выпадает.

**Алгоритм:**
- До 8 точек — точный перебор перестановок (8! = 40 320, миллисекунды на сервере).
  Точка забора и точка доставки считаются отдельными точками, поэтому 3 заказа из
  2 салонов — это уже 5 точек.
  Больше 8 — жадный выбор + локальные улучшения (2-opt).
- Стоимость: расстояние по прямой × коэффициент городской извилистости (≈1.3), скорость
  задаётся параметром модуля. **Штраф за опоздание к окну доставки на порядок выше
  стоимости лишнего километра** — приехать вовремя важнее, чем проехать меньше.
- Учитываем: старт от текущего салона забора, время на подъём/вручение (параметр, дефолт
  10 мин), жёсткое «не раньше начала окна».
- Результат: порядок с расчётным временем прибытия по каждой точке и честной пометкой
  «успеваем / впритык / не успеваем».

**Езда:** кнопка «Открыть в Навигаторе» строит deeplink с точками
(`yandexnavi://build_route_on_map?lat_to=…&lon_to=…`), плюс запасная ссылка на веб-карту.
Свою карту в модуле не рисуем — курьер и так живёт в Навигаторе.

**Почему не платный API:** на 3–8 точках в пределах города разница между «по прямой ×1.3»
и реальным временем с пробками меняет порядок редко, а стоит денег и внешней зависимости
в горячем пути. Если на практике порядок будет систематически неверным — подключаем
матрицу 2ГИС отдельной фазой, интерфейс от этого не меняется.

## 10. Безопасность и приватность

1. **Роль `courier` видит только свой город и только свои контакты.** Секция `courier_app`,
   привязка к городу через `user_stores`. Заказ чужого города не отдаётся API вовсе —
   фильтр на сервере, не на фронте.
2. **Контакты получателя открываются после брони.** До брони — улица и дом. Это снижает
   объём ПДн, «просматриваемых просто так», и совпадает с практикой драйверских
   приложений.
3. **Доступ к карточке пишется в аудит** (`log_action`) — кто и какой заказ открыл.
   Пишется фоновой очередью, не внутри запроса.
4. **Телефоны не попадают в логи.** Разведочные скрипты пишут сырой JSON только в `c:/tmp`,
   как `probe_crm_order_slots.py`.
5. **Push не содержит ПДн.** В уведомлении — «Новый заказ на ул. Ленина к 15:00», без
   имени и телефона: уведомление видно на экране блокировки.
6. **Курьер не может менять чужую бронь.** Проверка владельца брони на сервере.
7. **Ключ VAPID для push** — в `.env` в корне, как все секреты.
8. **Все пути к данным** — через `storage_paths.resolve` (фото товаров, если кэшируем).

## 12. Pre-mortem: прошёл год, модуль провалился. Почему?

1. **Курьеры не пользуются: «в вотсапе быстрее».** Лечится тем, что модуль даёт то, чего
   в чате нет: фото букета, маршрут, отсутствие вопроса «а этот заказ ещё свободен?».
   Если после месяца доля заказов, взятых через модуль, ниже ~70% — проблема в интерфейсе,
   а не в курьерах, и это видно по метрике из Фазы 8.
2. **Статусы в CRM разъехались.** Кто-то поменял название статуса, маппинг молча
   перестал работать. Защита: маппинг — по коду, а не по названию; журнал отправок;
   пустой маппинг блокирует действие. Тот же класс ошибки, что НДС в банк.
   Отдельная грань — **в поле статуса пишут двое**: флорист («Заказ готов») и наш модуль
   («Курьер забрал»). Поэтому бронь живёт у нас, а не в статусе CRM, и чужая запись
   статуса её не сбрасывает (§4).
3. **Двое приехали за одним букетом.** Защита — три уровня (индекс, `BEGIN IMMEDIATE`,
   блокировка кнопки) и сторож в тестах.
4. **Модуль положил сайт.** Лента ходит в CRM раз в 60 сек одним запросом, экран курьера
   не зовёт CRM вовсе, синки разведены по стартовой задержке, соединения — через
   `sqlite_conn`. Проверять `x-envoy-upstream-service-time` статики против ручек.
5. **Пуши не доходят.** Android гасит фон, iOS требует установленной PWA. Поэтому
   лента обновляется и сама, а пуш — усиление, а не единственный канал. Если окажется, что
   теряются — включаем Telegram как второй канал (владелец готов к этому позже).
6. **Утекли контакты клиентов.** Телефон на экране курьера — это ПДн. Ограничение по
   городу, открытие контактов только после брони, аудит доступа, отсутствие ПДн в пушах
   и логах.
7. **Бронь съела гибкость.** Курьер забронировал, у него сломалась машина — заказ висит.
   Автоснятие по времени доставки + ручное снятие управляющим закрывают это.
8. **Маршрут врёт из-за пробок и односторонних.** Поэтому ETA подаётся как оценка с
   пометкой, а не как обещание, и порядок всегда можно переопределить вручную.

## 13. Открытые вопросы (к Чату 2)

1. ~~Готовность букета~~ — **закрыто 2026-09-08**: в CRM есть статус «Заказ готов»,
   читаем его (см. §2 и §4). Осталось замерить в Фазе 0, насколько дисциплинированно его
   ставят — от этого зависит, блокировать ли «Забрал» у неготового заказа или только
   предупреждать.
2. ~~Один курьер — один салон или весь город?~~ — **закрыто 2026-09-08**: курьер берёт
   заказы из разных салонов города за одну ходку. Привязка курьера — к городу, в маршруте
   несколько точек забора (§9), в ленте — фильтр и группировка по салону.
3. ~~Оплата при доставке~~ — **закрыто 2026-09-08**: заказы оплачены до доставки, курьер
   денег не принимает. Модуль не касается касс и кассовых смен вовсе — ни полей суммы,
   ни отметок об оплате в карточке нет. Сумму заказа курьеру не показываем: она ему не
   нужна и создаёт соблазн выбирать заказы по чеку.
4. ~~Подтверждение доставки~~ — **закрыто 2026-09-08**: только отметка «Доставлено»
   (свайп), фото не делаем. Механика фото есть в списаниях, поэтому добавить её позже —
   это одна фаза, а не переделка: в схеме `delivery_assignments` для этого ничего
   резервировать заранее не нужно.
5. ~~Сколько курьеров в городе~~ — **закрыто 2026-09-08**: по-разному в разных городах,
   поэтому лимит броней и горизонт бронирования — настройка на город
   (`courier_city_settings`), а не константа. Сколько именно курьеров в каждом городе —
   выяснится при заведении учёток в Фазе 1.
6. ~~Заказы служб доставки~~ — **закрыто разведкой**: фильтруем ленту по типу доставки
   `dostavka-kurerom`; у `ya-dostavka` адреса нет вовсе, показывать нечего.
7. ~~Фото товара — какое именно~~ — **закрыто 2026-09-08**: в составе текстовые строки,
   фото открывается по тапу полноэкранно. Трафик тратится только когда курьер сам этого
   захотел.

**Все вопросы §13 закрыты.** План готов к Чату 2 (детализация фаз по шагам).
