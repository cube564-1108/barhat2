# Оплата курьерам (RetailCRM) — план

**Статус:** [x] Завершён (задеплоен 2026-08-24)
**Дата:** 2026-08-24
**Цель:** Модуль дашборда, который считает, сколько платить каждому курьеру за период:
сумма поля «Себестоимость доставки» по выполненным заказам, сгруппированная по курьеру,
с фильтрами по городу салона и дате доставки.

---

## Правила расчёта (от владельца)

1. Считаем только заказы в статусе **«Выполнен»** (`status = complete`, ровно один код —
   не вся группа `complete`: «Заказ доставлен» и «Удержание» не в счёт).
2. Сумма — поле заказа **«Себестоимость доставки»** (`delivery.netCost`).
3. Отчётный период — по **дате доставки** (`delivery.date`).
4. Фильтры: город салона + период по дате доставки.
5. Таблица: курьер → сумма себестоимости за период.
6. Курьер — из поля заказа (`delivery.data.courierId` / `firstName`).

## Что выяснено по API (проверено живыми запросами 2026-08-24)

| Нужное | Где лежит в ответе `/api/v5/orders` | Пример |
|---|---|---|
| Курьер | `delivery.data.courierId`, `delivery.data.firstName` | 288 / «Курьер 1 НСК» |
| Себестоимость доставки | `delivery.netCost` | 400 |
| Дата доставки | `delivery.date` (чистая дата, без времени) | `2026-08-22` |
| Салон | `site` (код) | `barkhat-nsk-levyi` |
| Город доставки | `delivery.address.city` | Новосибирск |
| Статус | `status` | `complete` |

Важное:
- Всё нужное приходит **прямо в списочном запросе** — поштучно заказы дёргать не надо.
- Работают фильтры `filter[deliveryDateFrom]` / `filter[deliveryDateTo]` (формат `YYYY-MM-DD`)
  и `filter[extendedStatus][]` — значит выборку можно сузить на стороне CRM.
- `limit` принимает только 20/50/100 — иначе `400 Errors in the pagination parameters`.
- Объём: за 7 дней ~1300 заказов по дате доставки, из них ~1200 «Выполнен» → 12 страниц.
- `delivery.date` — календарная дата, поэтому московского сдвига RetailCRM
  (см. `_MOSCOW_TZ` в `src/cashshifts/retailcrm_client.py`) здесь нет: сравниваем строки дат.
- В справочнике курьеров 282 записи, активных 34. Среди них службы доставки
  (Яндекс Доставка, Купер, Максим Такси, Драйв такси, Фловоу, «Общий») — отделяем флагом.

## Принятые решения

- **Данные из своей БД, не живым запросом.** Живые вызовы внешнего API из UI уже дважды
  клали прод (2 воркера gunicorn). Отдельная база `couriers.db` на постоянном диске
  (через `storage_paths.resolve`), синк фоновым планировщиком под локом в БД —
  паттерн `src/moysklad/server.py`.
- **Город = город салона** (из `site`), а не адрес доставки. Определяем по справочнику
  сайтов CRM: первое слово названия + словарь алиасов (НСК → Новосибирск, ЕКБ →
  Екатеринбург, Академ → Новосибирск). Город доставки тоже сохраняем — пригодится.
- **Курьеры-службы** помечаются флагом `is_service`, в отчёте переключатель
  «только свои курьеры» (по умолчанию включён). Автоопределение при синке:
  имя вида `Курьер <N> <город>` → свой, остальные → служба; флаг правится вручную.
- **Пересборка окна вместо инкремента по updated.** Синк удаляет строки за окно дат
  доставки и записывает их заново — так подхватываются и смена статуса, и смена курьера,
  и удалённые заказы. Инкремент по курсору здесь не нужен: окно маленькое.
- Заказы «Выполнен» **без курьера, но с себестоимостью** тоже пишем (courier_id NULL) —
  иначе дырка в заполнении CRM не видна. В отчёте они идут отдельным KPI, а не молча
  пропадают. Без курьера и с нулевой себестоимостью — это самовывоз, такие не храним.

## Итог

Реализовано и задеплоено 2026-08-24 (коммиты 9fabafa, 25f63ea, 9a7deee).

**Проверка на проде:** `/health` 200, база `/data/couriers.db` с `persistent: true`,
новый роут отвечает 401 (значит воркеры перезапустились с новым кодом), страница и статика
отдаются. Планировщик сам наполнил базу после деплоя; время ответа `/login` не изменилось
(~1.3 с до, во время и после синка) — фоновый прогон сайт не тормозит.

**Что получилось**
- `src/couriers/` — хранилище (`couriers.db` на постоянном диске), клиент RetailCRM, синк и API.
- Страница «Оплата курьерам» в дашборде: фильтры период/город/«только свои курьеры»,
  KPI, таблица, расшифровка по заказам, справочник курьеров, экспорт CSV.
- Синк раз в 30 минут (окно 7 дней), ночью — 90 дней; пустая база тянет квартал сразу.

**Что изменилось по ходу**
- Курьер нашёлся не в кастомных полях, а в `delivery.data.courierId` штатного заказа —
  справочник custom-fields проверять было незачем, но иначе это выяснить было нельзя.
- Заказы без курьера и с нулевой себестоимостью (самовывоз, ~62% выполненных) в базу не
  пишутся: они не про оплату курьерам и вдвое раздували бы данные. Без курьера, но с
  себестоимостью — пишутся и показываются отдельным KPI как дырка в заполнении CRM.
- Понадобился ещё один пункт, которого не было в чек-листе нового модуля: страничный
  маршрут `/<модуль>` в `pyrus/server.py` (без него прямая ссылка отдаёт 404).

**Проверено на живых данных (14 дней, 2134 заказа)**
- Сумма по расшифровке совпадает с суммой в отчёте.
- Повторный синк того же окна не даёт дублей.
- Ручной флаг «служба доставки» не перетирается синхронизацией.
- Все эндпоинты и валидация — через Flask test_client.

**Открытый вопрос**
- Сайты «Крафт» (`kraft`) и «Заказы сайтов» город не получают: их заказы видны только в
  режиме «Все города». Если Крафт нужно относить к какому-то городу — дописать в
  `CITY_ALIASES` (`src/couriers/retailcrm.py`).
