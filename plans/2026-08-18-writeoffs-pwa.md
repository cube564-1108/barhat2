# PWA для модуля списаний (Android) — план

**Статус:** 🎯 План с фазами, критика пройдена (Чат 1-3 за одну сессию)
**Дата:** 2026-08-18
**Цель:** Флорист устанавливает веб-приложение на Android-телефон (иконка на рабочем столе, без адресной строки браузера), заносит списание с фото через камеру — заявка идёт по уже готовой логике модуля `src/writeoffs/` без единой строчки изменений в бэкенде.

---

## Контекст

Модуль `src/writeoffs/` полностью реализован и задеплоен (`plans/2026-08-16-stock-writeoffs-module.md`) — REST API (`/api/writeoffs/*`), workflow согласования, интеграция с МойСклад. Форма флориста уже существует как часть общего дашборда (`src/dashboard/writeoffs.js` + фрагмент `index.html`), но:
- Открывается только через полный дашборд с боковым меню и остальными модулями — для телефона это лишний вес и не похоже на приложение.
- Загрузка фото — обычный `<input type="file">` без `capture` — открывает системный выбор файла, а не сразу камеру.
- Нет `manifest.json`/service worker — установить на рабочий стол Android нельзя, только «Добавить закладку».

**Почему это не отдельный проект, а надстройка:** вся авторизация (Flask-Login, cookie-сессии), API и бизнес-логика — общие с десктопным дашбордом. PWA-обёртка не создаёт новых точек входа в данные, только новый способ их открыть.

## Аналоги / на что опираемся

- `brand/logo.svg`, `brand/favicon.svg` — уже отдаются через `/brand/<filename>` (`src/pyrus/server.py`), есть откуда генерировать PNG-иконки для манифеста.
- Существующий паттерн отдельных HTML-страниц-роутов (`/writeoffs`, `/invoices`, `/cash-shifts` в `pyrus/server.py`, все — `send_from_directory(DASHBOARD_DIR, 'index.html')`) — для PWA нужен свой минимальный HTML-шаблон по той же схеме, а не переиспользование `index.html` целиком (там весь дашборд со всеми модулями, лишний вес для телефона).
- `writeoffs.js` уже не завязан на `script.js`/навигацию дашборда напрямую — работает через `window.WriteoffsModule.onPageActivated(userData)`, вызываемый снаружи. Для standalone-страницы достаточно своего маленького bootstrap-скрипта вместо `script.js`.

## Принятые решения (из обсуждения с владельцем)

| Вопрос | Решение |
|---|---|
| Нативное приложение vs PWA | PWA — переиспользует готовый API и форму, не отдельная кодовая база на Kotlin |
| Офлайн-очередь при обрыве связи | **Не делаем в v1** — при отсутствии сети просто ошибка «Нет соединения, попробуйте снова», как в большинстве обычных приложений. Не проектируем сложность под гипотетическую проблему — если на практике окажется, что связь в салонах правда часто рвётся, добавим отдельной фазой (IndexedDB-очередь + retry) |
| Экран для флориста | Отдельный минимальный HTML (не полный дашборд) — только форма списания + список своих заявок, без бокового меню и других модулей |

## Фаза 1: Манифест, иконки, service worker (устанавливаемость)

**Goal:** Chrome на Android предлагает «Установить приложение», иконка и сплэш-экран выглядят как приложение, не как сайт.

**Задачи:**
- [ ] Сгенерировать PNG-иконки (192×192, 512×512, желательно maskable-вариант с отступами) из `brand/logo.svg`
- [ ] `src/dashboard/manifest.json`: `name`, `short_name`, `start_url` (→ на страницу Фазы 2), `display: standalone`, `theme_color`/`background_color` из `brand/tokens.css`, `icons`
- [ ] Минимальный `src/dashboard/sw.js` (service worker) — Android требует зарегистрированный SW с `fetch`-обработчиком для показа промпта установки, даже без реального офлайн-кэширования в v1
- [ ] Роут в `pyrus/server.py`: отдать `manifest.json` и `sw.js` со **корневого** пути (`/manifest.json`, `/sw.js`) — scope service worker'а по умолчанию ограничен директорией, из которой он отдан
- [ ] Тег `<link rel="manifest">` + регистрация SW в новой странице (Фаза 2)

**Constraints:**
- Иконки — не хардкодить размеры вручную, использовать одну и ту же генерацию (скрипт или онлайн-инструмент) для консистентности
- SW в v1 — no-op прокси (`fetch` → `fetch(event.request)`), не кэширует агрессивно, чтобы не тащить проблему протухшего кэша раньше времени

**Done when:**
- Chrome на Android показывает баннер/пункт меню «Установить приложение»
- После установки иконка на рабочем столе — из `brand/logo.svg`, не дженерик-глобус

## Фаза 2: Отдельный минимальный экран для флориста

**Goal:** `start_url` манифеста ведёт на лёгкую страницу — только форма списания + список своих заявок, без остального дашборда.

**Задачи:**
- [ ] Новый шаблон `src/dashboard/writeoff-app.html` — своя `<head>` (manifest, viewport, минимум CSS: `styles.css` для `.btn`/`.modal`/`.form-*`, без стилей остальных модулей), в `<body>` — ровно markup формы и модалок из текущего фрагмента `index.html` (`data-page="writeoffs"` целиком), без `<aside class="sidebar">` и других `.page`
- [ ] Маленький bootstrap-скрипт (инлайн или `writeoff-app.js`): проверка авторизации (`fetch('/api/auth/me')`, редирект на `/login` если не авторизован) → `window.WriteoffsModule.onPageActivated(userData)` — без `script.js` и его логики переключения страниц
- [ ] Роут `/app/writeoff` в `pyrus/server.py` (по паттерну существующих `send_from_directory(DASHBOARD_DIR, ...)`), отдающий новый шаблон
- [ ] `manifest.json.start_url` → `/app/writeoff`

**Constraints:**
- `writeoffs.js` не трогаем — уже работает автономно через `onPageActivated`, новая страница только по-другому его подключает
- Проверка доступа — тот же `section_required`/`role_required` на API, дополнительно ничего не проверяем на фронте (бэкенд и так не отдаст чужие данные)

**Done when:**
- `/app/writeoff` открывается отдельно от дашборда, без бокового меню, показывает форму списания и работает так же, как внутри полного дашборда

## Фаза 3: Камера вместо выбора файла

**Goal:** При добавлении фото на телефоне сразу открывается камера, а не системный проводник.

**Задачи:**
- [ ] В `createPositionRow()` (`writeoffs.js`) добавить `fileInput.capture = 'environment'` (задняя камера)
- [ ] Проверить на реальном Android-телефоне: открывается ли камера напрямую или остаётся выбор «Камера/Галерея» (поведение отличается по браузерам/версиям Android — надо смотреть по факту, не считать данностью из документации)

**Constraints:**
- Не убирать возможность выбрать существующее фото из галереи как fallback — `capture` не блокирует это в большинстве браузеров, но подтвердить на реальном устройстве

**Done when:**
- На тестовом Android-телефоне при нажатии на поле фото открывается камера в 1 касание

## Фаза 4: Установка и прогон на реальном устройстве

**Goal:** Подтвердить, что всё вместе (манифест + отдельный экран + камера) реально работает как приложение на телефоне владельца/флориста.

**Задачи:**
- [ ] Установить на Android-телефон через Chrome (никаких магазинов приложений не нужно — прямая установка PWA)
- [ ] Пройти полный сценарий: открыть приложение с рабочего стола → списать товар с фото через камеру → отправить на согласование → (на другом устройстве/десктопе) согласовать → проверить статус в приложении

**Constraints:**
- Не могу выполнить сам — в среде разработки нет браузера/физического устройства (та же ситуация, что и с Фазой 6 основного модуля списаний)

**Done when:**
- Владелец подтвердил: иконка на рабочем столе, форма открывается быстро, фото через камеру, заявка доходит до согласования как обычно

## Критика (совмещённый Чат 3)

**1. Лучшее ли решение?** PWA поверх готового API — правильный выбор для этой задачи: нулевые изменения бэкенда, максимальное переиспользование уже написанного и протестированного `writeoffs.js`. Нативное приложение добавило бы отдельную кодовую базу и цикл релизов ради того же результата.

**2. Конфликты между фазами?** Нет — Фаза 2 (новый HTML) не трогает существующий `/writeoffs` внутри дашборда, оба входа продолжают работать параллельно (десктоп через дашборд, телефон через `/app/writeoff`). `writeoffs.js` используется без изменений в обоих случаях.

**3. Безопасность?** Новый статический роут (`/app/writeoff`) — та же проверка авторизации, что у остальных HTML-страниц дашборда (`current_user.is_authenticated`, редирект на `/login`). Service worker в v1 не кэширует авторизованные ответы API — не создаёт риска «показать чужие данные из кэша».

**4. Соответствие цели?** Прямое попадание: «флорист заносит данные в приложении, дальше — по уже созданной логике» — именно так и реализовано, без дублирования бизнес-логики.

**Pre-mortem:** если офлайн окажется реальной проблемой (связь в салоне часто рвётся) — v1 без очереди будет раздражать, но не терять данные молча: `submitWriteoff()` уже показывает `alert()` при ошибке сети, фото/заявка просто не уйдут, флорист увидит ошибку и попробует снова. Не идеально, но и не тихий провал — приемлемо для первой версии.
