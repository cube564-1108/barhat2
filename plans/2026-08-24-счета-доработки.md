## 2. Зафиксированные решения

1. **Источник реквизитов — только своя история счетов.** DaData и МойСклад
   рассмотрены и отклонены. Причина: расчётный счёт по ИНН не отдаёт публично
   никто, а название и КПП всё равно уже есть в наших счетах. Внешний вызов при
   этом стоил бы таймаутов и кэша — на проде всего 2 gunicorn-воркера.
2. **Наполнение справочника** — автоматом при создании счёта с новым контрагентом
   **плюс** отдельная страница для правки реквизитов и объединения дублей.
3. **Распределение в таблице** — раскрывающаяся строка: в колонке «N строк» со
   стрелкой, по клику под строкой счёта разворачивается подтаблица
   «салон / статья / сумма». Таблица остаётся узкой.
4. **«Комментарий»** — новая колонка в `invoices`, отдельная от ленты `invoice_comments`.
5. **Персональная настройка колонок — отложена** в отдельный план, не отменена.

## 3. Модель данных

### 3.1 Справочник контрагентов

```sql
CREATE TABLE IF NOT EXISTS invoice_counterparties (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,
    inn TEXT,
    kpp TEXT,
    bank_name TEXT,
    bank_bik TEXT,
    bank_account TEXT,
    bank_corr_account TEXT,
    is_active INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at TEXT
);

-- Ключ — пара «ИНН + расчётный счёт», а не имя и не один ИНН:
-- у одного юрлица легально несколько расчётных счетов, и платим мы
-- именно на счёт. Частичный индекс по is_active = 1, иначе удалённая
-- запись навсегда заблокирует повторное заведение того же контрагента.
CREATE UNIQUE INDEX IF NOT EXISTS idx_counterparties_inn_account
    ON invoice_counterparties(inn, bank_account)
    WHERE is_active = 1 AND inn IS NOT NULL AND bank_account IS NOT NULL;

CREATE INDEX IF NOT EXISTS idx_counterparties_inn ON invoice_counterparties(inn);
CREATE INDEX IF NOT EXISTS idx_counterparties_active
    ON invoice_counterparties(is_active) WHERE is_active = 1;
```

Имя таблицы с префиксом `invoice_`, как у остальных справочников модуля.
`UNIQUE(name)` намеренно нет — на этих граблях модуль уже стоял: soft-delete
плюс `UNIQUE(name)` даёт «имя занято невидимой записью».

**Счёт на справочник не ссылается.** `invoices.counterparty_*` остаются как есть:
реквизиты на момент платежа — часть документа, они не должны меняться задним
числом при правке справочника. Справочник — только источник для подстановки.

### 3.2 Поле «Комментарий»

`ALTER TABLE invoices ADD COLUMN comment TEXT` — через тот же паттерн, что
`_ensure_invoice_bank_columns` ([storage.py](../src/invoices/storage.py)):
проверка `_column_exists` → `BEGIN IMMEDIATE` → ALTER → commit. Без эксклюзивной
блокировки два воркера падают на `duplicate column name`.

В код добавить комментарий-предупреждение: `invoices.comment` — свойство счёта,
`invoice_comments` — лента переписки; в `server.py` уже есть третий `comment`
(текст операции ПланФакта), путаница вероятна.

Комментарий **не** попадает в платёжку Модульбанка — туда идёт только
`payment_purpose` ([modulbank/document.py](../src/modulbank/document.py)).

## 4. API

| Метод | Путь | Кто | Что делает |
|---|---|---|---|
| GET | `/api/invoices/counterparties?query=` | доступ к разделу | Поиск по ИНН и названию, до 10 записей — для автодополнения |
| GET | `/api/invoices/counterparties` | доступ к разделу | Полный список для страницы справочника |
| POST | `/api/invoices/counterparties` | admin | Завести вручную |
| PUT | `/api/invoices/counterparties/<id>` | admin | Правка реквизитов |
| DELETE | `/api/invoices/counterparties/<id>` | admin | Soft-delete (`is_active = 0`) |
| POST | `/api/invoices/counterparties/<id>/merge` | admin | Объединить дубль: пометить источник неактивным |

Изменения в существующих ручках:
- `GET /api/invoices` — в каждый счёт добавляется `line_items` со `store_name`
  и `category_name`. **Одним запросом** `WHERE invoice_id IN (...)` с JOIN, не по
  счёту на строку: на 100 счетах это 100 лишних запросов.
- `POST /api/invoices` и `PUT /api/invoices/<id>` — принимают `comment`;
  `comment` добавляется в `_EDITABLE_INVOICE_FIELDS`, значит правка автоматически
  попадёт в `invoice_history`.

## 5. Интерфейс

Всё новое — по `DESIGN-SPEC.md`: токены `--bx-*`, Vollkorn в заголовках, белые
карточки 16px, **без эмодзи**, иконки линейные (lucide, stroke-width 1.75).
Перед сдачей — чек-лист §9.

**Форма счёта.** Поле «ИНН контрагента» получает выпадающие подсказки от 4
введённых символов; поиск также по названию в поле «Наименование». Выбор
подставляет остальные 6 полей, они остаются редактируемыми. Под полями —
подпись серым: «Реквизиты из справочника, последний счёт от 12.07».
При рендере подсказок экранировать значения корректно — трюк
`div.textContent` не экранирует кавычку и молча режет `value="..."`.

**Комментарий** — `<textarea rows="2">` сразу под «Назначением платежа» в модалке
создания и в блоке правки полей в деталях.

**Таблица счетов.** Новая колонка «Распределение»: `▸ 3 строки`, по клику —
вставка `<tr>` с подтаблицей под строкой счёта. Если строк нет — «—», кнопки нет.

Рендер строк таблицы при этом переписывается на декларативный массив
`COLUMNS = [{key, label, render}]`, из которого строятся и шапка, и строки, и
`colspan` пустого состояния. Формально это задел под отложенную настройку
колонок, но делать иначе всё равно нельзя: раскрывающаяся строка ломает
нынешний плоский шаблон, а `colspan="10"` перестаёт быть верным.

**Страница справочника** — таблица контрагентов, поиск, правка в модалке,
кнопка «Объединить с…». Диалоги — только `window.BarhatUI`
([ui-dialog.js](../src/dashboard/ui-dialog.js)): в iframe Пульса нативные
`confirm`/`alert` молча игнорируются и кнопка «ничего не делает».

При добавлении страницы пройти чек-лист нового модуля дашборда: секция в
`auth.py` (в двух местах), `users.js`, `script.js`, вложенность `modal-overlay`.

## 6. Прецеденты (вместо внешнего ресёрча)

- **Справочники этого же модуля** — `REFERENCE_TABLES`, общий CRUD, soft-delete,
  правка админом. Новый справочник шире (7 полей вместо `name`), поэтому в общий
  CRUD не влезает, но соглашения берём оттуда.
- **План «Каталог товаров»** ([2026-08-22-каталог-товаров.md](2026-08-22-каталог-товаров.md))
  — там уже решено, что личные виды списка хранятся на сервере, а не в
  `localStorage`, потому что модуль работает в iframe. Отложенная настройка
  колонок в счетах должна лечь на ту же механику, а не изобретать вторую.
- **Раскрывающиеся строки** — в дашборде пока нигде нет; ближайшее по смыслу
  «5 из 6 → разворачивается» из плана каталога (§60).

Внешний ресёрч (как это решают в 1С, Диадоке, Контуре) не проводился — сетевые
запросы без явного разрешения не делаю. Если нужно — Чат 2.

## Риски и pre-mortem

*«Прошёл год, справочник не используют. Почему?»*

1. **Бэкфилл занёс мусор.** Реквизиты вводились руками год — там опечатки,
   «ООО Ромашка» и «ООО "Ромашка"», ИНН с пробелами. Подстановка мусора хуже
   пустых полей. Лечение: Фаза 2 идёт **до** Фазы 3, нормализация ИНН и счёта
   (только цифры) при сравнении.
2. **Справочник расходится с реальностью.** Контрагент сменил банк, а
   подстановка тянет старый счёт — деньги уходят не туда. Лечение: подпись
   «из счёта от <дата>» рядом с подставленными полями, поля редактируемые.
3. **Автообновление затирает правку.** Поэтому существующие записи автоматом
   **не** обновляются: последний счёт не побеждает, иначе одна опечатка портит
   справочник для всех. Правка — только руками. → открытый вопрос №1.
4. **Миграция на проде подвесила сайт.** ALTER без `BEGIN IMMEDIATE` при двух
   воркерах уже дважды ломал прод. Лечение: паттерн из §3.2, ничего своего.
5. **N+1 на списке счетов.** Распределение по строке = сотня запросов на
   загрузку списка, и «сайт тормозит». Лечение: один запрос `IN (...)`.
