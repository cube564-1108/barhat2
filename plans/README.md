# Plans — технические планы реализации

## Правила

1. **Один план = одна функция.** Не смешивать несколько задач в один файл.
2. **Имя файла:** `YYYY-MM-DD-название-функции.md`
3. **Фазы с чекбоксами** `[ ]` (не начата) / `[x]` (завершена)
4. **Агент обязан** обновлять план после каждой сессии.
5. **В конце плана** — итоговый блок: реализовано / частично / не начато.

## Шаблон плана

```markdown
# [Название функции] — план

**Статус:** [ ] В процессе / [x] Завершён  
**Дата:** YYYY-MM-DD  
**Цель:** [1-2 предложения что должно получиться]

---

## Фазы

### [ ] Фаза 1 — [Название]
- [ ] Шаг 1.1
- [ ] Шаг 1.2

### [ ] Фаза 2 — [Название]
- [ ] Шаг 2.1

---

## Итог

[Что реализовано, что осталось, что поменялось по ходу]
```

## Цикл создания плана (3 чата Миллера)

```
Чат 1: «Создай план реализации [функция]. Поищи как другие решали.»
        → черновой план → сохрани в plans/YYYY-MM-DD-название.md

Чат 2: «Прочитай план. Разбей на фазы с чекбоксами.»
        → план с фазами

Чат 3: «Проверь каждую фазу:
        - Лучшее ли решение?
        - Конфликты между фазами?
        - Безопасность?
        - Соответствие бизнес-целям?»
        → финальный план

Чат 4+: реализация фаза за фазой
```

### 2026-08-29-рабочие-карты.md
Расходы с рабочих карт управляющих: заявка на пополнение → перемещение в ПланФакте,
трата с фото чека вместо гугл-таблицы → расход в ПФ нужной статьёй и салоном, сверка
остатка подотчёта.

**Подход:** отдельного модуля нет — три типа заявки в существующем разделе счетов
(счёт на оплату / расход с карты / пополнение карты). Карта = подотчётный счёт в ПФ
(одна карта — один счёт), пополнение уезжает `POST /operations/move`, трата —
`POST /operations/outcome` со счёта карты. По картам в ПФ ничего не тянется автоматически,
модуль — единственный источник этих операций. Записи только фоновым синком, признак
разноски отдельным полем (урок плана 2026-08-26)
**Требует:** справочник `work_cards`, три колонки в `invoices`, три метода в
`src/planfact/client.py`. Выписки по картам нет и не будет — карты личные, трату вводит человек

**Ключевой риск:** карточные заявки нельзя пустить в старый REF-синк счетов — иначе
пополнение уедет расходом и тот же рубль ляжет дважды. Идемпотентность держится на маркере
`[cardexp:id]` в комментарии операции: искать по `externalId` в API нечем

**Статус:** 🚧 Фазы 0-3 реализованы 2026-08-29 — полный рабочий цикл (справочник карт, три
типа заявки, форма и список, фоновая разноска). Фаза 0 на проде, фазы 1-3 ждут выкатки.
Остались Фаза 4 (сводный экран остатков и сверка с ПФ) и Фаза 5 (предупреждение о долге)

### 2026-09-02-согласование-документов.md
Модуль согласования документов: доверенности, УПД, договоры поставки и аренды заводятся
сотрудниками, согласуются владельцем, возвращаются подписанным оригиналом; реестр помнит
сроки действия и напоминает о продлении.

**Подход:** одна сущность `documents` + справочник типов (никаких таблиц под каждый тип и
никакого EAV), очередь к одному согласующему вместо маршрутов, три исхода решения
(согласовано / с условием / отклонено). Подписи в модуле **нет** — юридическая подпись
остаётся во внешнем ЭДО или на бумаге, внутри только фиксация факта с оригиналом-файлом
**Требует:** новый модуль `src/documents/`, папку файлов через `resolve_data_path`,
фоновый планировщик напоминаний о сроках

**Ключевое ограничение:** оператор ЭДО не выбран, поэтому интеграции сейчас нет — но поля
`source`/`external_id`/`external_status` закладываются в схему сразу. Диадок и СБИС устроены
одинаково («лента событий → карточка → резолюция»), клиент прячется за интерфейсом из трёх
методов. Подпись от имени организации в 2026 возможна только личной КЭП + МЧД, серверная
подпись — отдельный проект с КриптоПро DSS
