## КРИТИЧЕСКИ ВАЖНО: где лежат данные

**Всё, что пишется на диск (базы, загрузки, выгрузки, кэши), должно получать путь
из `src/storage_paths.py`.**

На Amvera постоянный диск — `/data`, а `/app` пересоздаётся при каждой сборке.
Относительный путь = потеря данных на следующем деплое. Так уже терялись база
Pyrus (2026-08-18) и вложения к счетам (2026-08-23).

```python
from storage_paths import resolve as resolve_data_path
ATTACHMENTS_DIR = resolve_data_path("MY_DIR_ENV", "my_dir")
```

Резолвить путь нужно **в модуле при импорте**, а не в точке входа — иначе защита
отваливается при любом другом способе запуска. Проверка на проде: `GET /health`,
поле `persistent`.

## КРИТИЧЕСКИ ВАЖНО: соединения с SQLite

**Соединение с базой открывается только через `connect` из `src/sqlite_conn.py`.
Никаких `sqlite3.connect()` напрямую и никаких PRAGMA россыпью по модулям.**

Диск `/data` на Amvera сетевой и медленный. Замер прода 2026-08-26: отдача
статики — 3 мс, любой запрос, коснувшийся базы, — 90–700 мс, при этом Python
простаивал. Цену запроса определяет не код, а **число открытых соединений и
число fsync**, поэтому:

```python
from sqlite_conn import connect as sqlite_connect

def get_db():
    return sqlite_connect(DB_PATH, timeout=20)
```

Три правила, которые этот модуль удерживает:

- `journal_mode=WAL` — **один раз на файл за жизнь процесса**. Это свойство
  файла, а не соединения; PRAGMA на каждом `get_db()` — лишняя запись на диск.
- `synchronous=NORMAL` — **каждому соединению**. С дефолтным FULL fsync идёт
  на каждый commit, и во время фонового синка сайт встаёт у всех сразу:
  `/data` общий для `barhat.db`, `pyrus.db`, `moysklad.db`, `couriers.db`,
  а на `barhat.db` держится авторизация.
- **Не открывать базу в горячем пути лишний раз.** Права грузятся тем же
  соединением, что и учётка; аудит (`log_action`) пишется фоновой очередью,
  а не внутри запроса.

Сторож: `python scripts/test_db_hot_path.py` — считает соединения на один
HTTP-запрос и падает, если их снова стало больше.

**Фоновые синки — это тот же диск.** У нового планировщика обязаны быть:
своя стартовая задержка (не совпадающая с чужой, иначе синки идут одной
волной), лок с TTL и продление лока по времени, а не после каждой страницы.

**Соединение закрывается через `try/finally`, без исключений.** Функция вида
`conn = get_db(); ...; conn.close()` теряет соединение на любой ошибке, а
незакрытое соединение с неоткатанной транзакцией держит write-лок общей БД до
перезапуска воркера — после этого висит вход в дашборд и любая запись во всех
модулях сразу. Так ронялся логин 2026-08-19, и так же в `cashshifts/storage.py`
жили 22 функции до 2026-08-30.

## КРИТИЧЕСКИ ВАЖНО: «проверил → записал» — это одна транзакция

**Если перед записью есть проверка «а можно ли», проверка и запись идут одним
соединением под `BEGIN IMMEDIATE`, а инвариант дублируется уникальным индексом
в схеме.**

На проде 2 воркера gunicorn по 8 потоков (`amvera.yml`) — до 16 параллельных
обработчиков, а запрос к базе стоит 90–700 мс. Между `SELECT` в одном
соединении и `INSERT` в другом лежит окно шириной в сотни миллисекунд, и в
него проходят все параллельные запросы разом. 29.08.26 так открылись **три
дневные смены на одной точке**: все три прочитали «открытых смен нет».

```python
conn = get_db()
conn.isolation_level = None          # транзакцией управляем сами
try:
    conn.execute("BEGIN IMMEDIATE")  # write-лок ДО чтения; обычный BEGIN не спасёт
    if conn.execute("SELECT ...").fetchone():
        conn.execute("ROLLBACK")
        raise AlreadyExistsError(...)
    conn.execute("INSERT ...")
    conn.execute("COMMIT")
finally:
    conn.close()
```

Три уровня, нужны все три:

- **БД** — частичный уникальный индекс (`... ON t(store_id) WHERE status='open'`).
  Последняя преграда: держит инвариант, даже если появится новый путь записи.
  Поверх уже накопленных дублей он не построится — ловить `IntegrityError`,
  логировать и **не ронять старт воркера**, разбор дублей делать отдельной
  админской ручкой.
- **Бэкенд** — `BEGIN IMMEDIATE` как выше, `IntegrityError` → 409 с внятным
  текстом, а не 500.
- **Фронт** — кнопка блокируется на время запроса (`guardClicks` в
  `src/dashboard/cash-shifts.js`). Без этого один медленный клик превращается
  в три запроса: кнопка выглядит живой, и её дожимают.

Разовые операции с боевой базой (разбор дублей, чистка) — только HTTP-ручкой
под `@role_required("admin")` плюс плашка в интерфейсе: консоли контейнера на
этом тарифе Amvera нет. Удалять при этом можно только заведомо пустые записи,
спорные — показывать человеку.

Сторож: `python scripts/test_shift_open_race.py` — 20 потоков на одну точку,
разбор дублей, HTTP-проверка 409/403.

## КРИТИЧЕСКИ ВАЖНО: TLS российских API

**Любой новый клиент к российскому сервису обязан вешать на сессию
`trust_russian_ca` из `src/russian_ca.py`.**

Российские сервисы переходят на сертификаты НУЦ Минцифры, корня которых нет в
бандле `certifi`. Запрос падает ещё до отправки данных, а формулировка сбивает
с толку — «self-signed» относится к неизвестному корню, а не к сертификату сервиса:

```
SSLError: certificate verify failed: self-signed certificate in certificate chain
```

Так 2026-08-25 отвалилась отправка счетов в Модульбанк.

```python
import requests
from russian_ca import trust_russian_ca

session = requests.Session()
trust_russian_ca(session)
```

**Никогда не чинить это через `verify=False`** — это открывает MITM на платёжных
и складских API. Корень добавляется *к* штатному бандлу, остальные сайты
проверяются как раньше.

Через переменные окружения (`REQUESTS_CA_BUNDLE`, `SSL_CERT_FILE`) не починить:
у наших клиентов стоит `trust_env = False`, а он их отключает.

## КРИТИЧЕСКИ ВАЖНО: перерисовка через innerHTML теряет прокрутку и фокус

**Если функция вида `renderX()` переписывает `host.innerHTML` целиком, она
обязана вернуть на место прокрутку — а действие, добавляющее элемент, ещё и
поставить в него курсор.**

Модули дашборда перерисовывают экран целиком: так проще держать разметку в
соответствии с состоянием, и обработчики вешаются заново одним `bindX()`. Цена —
браузер выбрасывает и позицию прокрутки, и фокус, и выделение в поле. На
длинной форме это выглядит как отдельный баг: заполнил строку распределения
внизу, нажал «Добавить строку» — и ты снова в шапке счёта (модуль счетов,
2026-08-31).

```js
function renderForm() {
    const restoreScroll = keepModalScroll(host);   // до перезаписи
    host.innerHTML = `...`;
    bindForm(host);
    restoreScroll();                                // после привязки
}
```

- **Чинить перерисовку, а не кнопку.** У бага всегда несколько входов: ту же
  форму перерисовывают удаление строки, автораскладка суммы, подстановка
  контрагента, смена значения в селекте.
- **Прокрутка бывает не одна.** У модалки скроллится и тело (`max-height` на
  десктопе), и внешний слой (на узком экране) — запоминать оба.
- **Восстанавливать только для того же объекта.** Открыли соседний счёт —
  прокрутка не его; сверять по `dataset`.
- **Поле ввода, живущее внутри перерисовки, требует ещё и каретки:**
  `focus()` + `setSelectionRange(len, len)`, иначе набор обрывается на первом
  символе. Где это мешает постоянно (поиск, суммы) — обновлять точечно, как
  `updateAllocationSummary`.

## Как выполнять задачи

**Структурируй любую задачу по схеме:**

```
Goal → Context → Constraints → Done when
```

| Элемент | Что это | Пример |
|---|---|---|
| **Goal** | Чёткая цель задачи | Исправить KeyError в /api/criteria |
| **Context** | Файлы, ошибки, документация | Читаю traceback, смотрю код в src/api/criteria.py |
| **Constraints** | Стандарты, архитектура, зависимости | Python 3.11, не сломать другие эндпоинты |
| **Done when** | Критерий завершения | Тест проходит, ошибка не воспроизводится |

Это резко снижает число холостых итераций.

**Сложные задачи требуют подробного плана:**

- **Задача сложная**, если: >3 шагов, затрагивает несколько файлов, новый функционал
- **Перед началом** → прописывай подробный план действий
- **План** → разбей на подзадачи, каждая с Goal → Done when
- **Только после плана** → начинаешь выполнение

**Загружай контекст upfront (даёт всё сразу):**

- **Не подкармливай по файлу** — давай сразу все релевантные файлы
- **Ошибка?** → давай traceback + все затронутые файлы одним сообщением
- **Новая задача?** → давай похожие файлы (примеры из кода) сразу
- **Если не хватает данных** → запрашивай сразу всё, а не по одному

Это устраняет циклы «агент не видит нужный модуль → правит не туда».
