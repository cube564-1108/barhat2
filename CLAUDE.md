## Что это за проект

**Бархат** — сеть цветочных салонов. Занимаемся изготовлением и продажей букетов из цветов, клубники в шоколаде и других подарков.
Текущий статус: бизнес запущен и работает, в стадии масштабирования. Цель: автоматизировать процессы, увеличить выручку и прибыль, улучшить маркетинг.

**Этот сервис — дашборд БАРХАТ, часть общей среды команды** (`barkhat-hq/barkhat-dashboard`).
Среда — несколько отдельных сервисов вокруг одной базы-ядра `barkhat-core`, которые ведут трое
(Роман, Андрей, Стас), каждый через своего AI-агента. Владелец этого сервиса — Стас.

## ОБЯЗАТЕЛЬНО: мозги и лицо — где живёт обработка

Любая функция = **мозги (сервис)** + **лицо (модуль Пульса)**, связанные через базу. Обработка
живёт в мозгах, не в лице.

**Мозги — сервис.** Вся обработка и все вызовы внешних систем (RetailCRM, Flowwow, Яндекс.Еда,
МойСклад, PlanFact, банк). Ходит в источники, считает, пишет результат в свою схему. В источник
пишет **только он** — через API источника.

**Лицо — Пульс.** Не «мозги». Делает три вещи:
1. **Показывает** — читает готовые витрины из базы под ролью «только чтение».
2. **Управляет** — по кнопке отдаёт команду + данные нужному сервису, сервис исполняет.
3. **Пишет своё** — только свою `app`-схему (задачи, доступы, черновики, настройки).

**В Пульсе НЕ делаем:** прямые вызовы источников на рендере; тяжёлые расчёты/агрегацию на рендере;
запись в зеркало (его пишет только синк) и в чужие схемы; изменение реальных данных в базе (оно
идёт через API источника внутри сервиса).

**Суть:** Пульс командует сервисами, но сам во внешние системы не ходит и зеркало не трогает.
Обработку выносим в сервис — лицо остаётся тонким.

## ОБЯЗАТЕЛЬНО: работа с общей базой

База **одна на всех** (`barkhat-core`, Postgres на Amvera) и устроена как **read-only зеркало
источников + свои схемы сервисов**.

**Главный принцип:** в зеркало пишет **только синхронизатор**, в свою схему — **только её сервис**.
Зеркало и чужие схемы **никто не перезаписывает**. Менять реальные данные (заказ, клиента, остаток)
— **через API источника** (RetailCRM, МойСклад…), НЕ в нашей базе. Наша база — проекция источников
для чтения, не вторая правда.

| Зона | Кто ПИШЕТ | Кто ЧИТАЕТ |
|---|---|---|
| Зеркало источников (`crm`, `sklad`, `catalog`…) | только синхронизатор («заготовщик») | все — read-only |
| Своя схема сервиса (счета, ЗП, задачи, промо…) | только этот сервис | другие — по надобности, read-only |

**Можно свободно:** читать любые данные (SELECT ничего не ломает); создавать таблицы и писать в
**СВОЮ** схему; добавлять новое поле в свою таблицу.

**Нельзя / только через проверку:** писать в зеркало источников; писать в чужую схему;
менять/удалять/переименовывать общие структуры, тип поля, тяжёлые миграции, тяжёлые запросы,
удаление данных — только через версионную миграцию с просмотром.

**Правила изменения общих структур:** (1) сначала узнай, кто пользуется, и предупреди;
(2) «добавляй, не ломай» (expand → migrate → contract) — не переименовывать на месте;
(3) только файл-миграцией, версионной, с просмотром перед merge; (4) дашборды читают под ролью
«только чтение» и берут готовые витрины, а не тяжёлые живые запросы; (5) проверяй на снимке и
держи откат, тяжёлые миграции — в непиковое время.

**Статус этого сервиса:** пока живёт на своих SQLite-базах на диске `/data` Amvera; переезд на
`barkhat-core` — отдельный планируемый шаг (инвентаризация SQLite → схема `dashboard` + роль
`bh_dashboard_writer` + логин `svc_dashboard` → портирование DDL → репойнт на `DATABASE_URL` →
cutover с живым SQLite для отката). До переезда правила выше применяются к коду, который уже
сейчас пишется под общую базу.

## КРИТИЧЕСКИ ВАЖНО: где лежат данные

**Всё, что пишется на диск (базы, загрузки, выгрузки, кэши), должно получать путь
из `src/storage_paths.py`.**

На Amvera постоянный диск — `/data`, а `/app` пересоздаётся при каждой сборке.
Относительный путь = потеря данных на следующем деплое. Так уже терялись база
Pyrus (2026-08-18) и вложения к счетам (2026-08-23).

```python
from storage_paths import resolve as resolve_data_path
ATTACHMENTS_DIR = resolve_data_path("MY_DIR_ENV", "my_dir")
```

Резолвить путь нужно **в модуле при импорте**, а не в точке входа — иначе защита
отваливается при любом другом способе запуска. Проверка на проде: `GET /health`,
поле `persistent`.

## КРИТИЧЕСКИ ВАЖНО: соединения с SQLite

**Соединение с базой открывается только через `connect` из `src/sqlite_conn.py`.
Никаких `sqlite3.connect()` напрямую и никаких PRAGMA россыпью по модулям.**

Диск `/data` на Amvera сетевой и медленный. Замер прода 2026-08-26: отдача
статики — 3 мс, любой запрос, коснувшийся базы, — 90–700 мс, при этом Python
простаивал. Цену запроса определяет не код, а **число открытых соединений и
число fsync**, поэтому:

```python
from sqlite_conn import connect as sqlite_connect

def get_db():
    return sqlite_connect(DB_PATH, timeout=20)
```

Три правила, которые этот модуль удерживает:

- `journal_mode=WAL` — **один раз на файл за жизнь процесса**. Это свойство
  файла, а не соединения; PRAGMA на каждом `get_db()` — лишняя запись на диск.
- `synchronous=NORMAL` — **каждому соединению**. С дефолтным FULL fsync идёт
  на каждый commit, и во время фонового синка сайт встаёт у всех сразу:
  `/data` общий для `barhat.db`, `pyrus.db`, `moysklad.db`, `couriers.db`,
  а на `barhat.db` держится авторизация.
- **Не открывать базу в горячем пути лишний раз.** Права грузятся тем же
  соединением, что и учётка; аудит (`log_action`) пишется фоновой очередью,
  а не внутри запроса.

Сторож: `python scripts/test_db_hot_path.py` — считает соединения на один
HTTP-запрос и падает, если их снова стало больше.

**Фоновые синки — это тот же диск.** У нового планировщика обязаны быть:
своя стартовая задержка (не совпадающая с чужой, иначе синки идут одной
волной), лок с TTL и продление лока по времени, а не после каждой страницы.

**Соединение закрывается через `try/finally`, без исключений.** Функция вида
`conn = get_db(); ...; conn.close()` теряет соединение на любой ошибке, а
незакрытое соединение с неоткатанной транзакцией держит write-лок общей БД до
перезапуска воркера — после этого висит вход в дашборд и любая запись во всех
модулях сразу. Так ронялся логин 2026-08-19, и так же в `cashshifts/storage.py`
жили 22 функции до 2026-08-30.

## КРИТИЧЕСКИ ВАЖНО: экран не зависит от диагностики, а диагностика не сканирует витрину

**Функция вида `health_snapshot()` считает состояние по ОКНУ, а не по всей
таблице. Экран не имеет права её вызывать: подпись «на какой момент данные» —
это отдельный дешёвый запрос по показываемому периоду.**

Диск `/data` сетевой, и цену запроса определяет объём чтения. Полный скан
витрины на 15 тыс. строк плюс `COUNT(*)` по 25 тыс. позиций — это **секунды**,
а не миллисекунды. 07.09.2026 так вышло `/health` за 6–9 секунд против 2 мс на
статику, и те же секунды платил бы каждый показ сетки нагрузки: от диагностики
зависела её подпись о свежести данных.

- **Диагностика — по окну** (`HEALTH_WINDOW_DAYS`), и окно отдаётся в ответе:
  иначе непонятно, за какой период цифры.
- **`MAX(колонка)` по индексу вместо скана** — читается одна строка индекса.
- **Экрану — своя функция** (`couriers.load_freshness(date_from, date_to)`),
  которая берёт только нужное и только по показываемому периоду.
- **Тесты этого не поймают**: в них база маленькая и локальная. Ловится только
  замером на проде — `x-envoy-upstream-service-time` статики против ручки.

**Цену диагностики определяет число открытых соединений, а не размер таблиц.**
09.09.2026 `/health` отвечал 3,4–13,5 с, и «очевидной» причиной выглядели сканы
витрин — база МойСклада на 1,13 ГБ, витрина качества на 196 МБ. Замер по копиям
боевых баз показал другое: витрины маленькие (`warehouse_flows` — 2 956 строк,
`quality_scores` — 16 487), все пять снимков вместе считаются за 22 мс. Гигабайты
лежали в соседних таблицах. Дорого было то, что **один вызов открывал 10
соединений к четырём базам** на общем сетевом `/data` по 90–700 мс за обращение.

- **Меряй раньше, чем чинишь** — даже когда диагноз в задаче звучит убедительно.
  Считать соединения счётчиком вокруг `sqlite3.connect` (см. сторожа) дешевле,
  чем переписывать пять функций не по той причине.
- **Ручка отвечает на один вопрос дёшево, на остальные — по явному параметру.**
  `/health` — жив ли процесс и на месте ли данные; `/health?full=1` — витрины,
  инварианты схемы, полные счётчики. Опрашивают часто первое.
- **`SELECT MIN(x), MAX(x)` — это скан.** SQLite сводит запрос к чтению крайней
  строки индекса, только когда агрегат в нём **один**. Границы дат — двумя
  отдельными запросами.
- **Отдавай `timings_ms` по каждому блоку.** Следующий разбор «почему медленно»
  обязан начинаться с числа, а не с чтения кода.

Сторожа: `python scripts/test_db_hot_path.py` (обращения к базе на запрос),
`python scripts/test_health_cost.py` (соединения на один вызов `/health`).

## КРИТИЧЕСКИ ВАЖНО: «проверил → записал» — это одна транзакция

**Если перед записью есть проверка «а можно ли», проверка и запись идут одним
соединением под `BEGIN IMMEDIATE`, а инвариант дублируется уникальным индексом
в схеме.**

На проде 2 воркера gunicorn по 8 потоков (`amvera.yml`) — до 16 параллельных
обработчиков, а запрос к базе стоит 90–700 мс. Между `SELECT` в одном
соединении и `INSERT` в другом лежит окно шириной в сотни миллисекунд, и в
него проходят все параллельные запросы разом. 29.08.26 так открылись **три
дневные смены на одной точке**: все три прочитали «открытых смен нет».

```python
conn = get_db()
conn.isolation_level = None          # транзакцией управляем сами
try:
    conn.execute("BEGIN IMMEDIATE")  # write-лок ДО чтения; обычный BEGIN не спасёт
    if conn.execute("SELECT ...").fetchone():
        conn.execute("ROLLBACK")
        raise AlreadyExistsError(...)
    conn.execute("INSERT ...")
    conn.execute("COMMIT")
finally:
    conn.close()
```

Три уровня, нужны все три:

- **БД** — частичный уникальный индекс (`... ON t(store_id) WHERE status='open'`).
  Последняя преграда: держит инвариант, даже если появится новый путь записи.
  Поверх уже накопленных дублей он не построится — ловить `IntegrityError`,
  логировать и **не ронять старт воркера**, разбор дублей делать отдельной
  админской ручкой.
- **Бэкенд** — `BEGIN IMMEDIATE` как выше, `IntegrityError` → 409 с внятным
  текстом, а не 500.
- **Фронт** — кнопка блокируется на время запроса (`guardClicks` в
  `src/dashboard/cash-shifts.js`). Без этого один медленный клик превращается
  в три запроса: кнопка выглядит живой, и её дожимают.

Разовые операции с боевой базой (разбор дублей, чистка) — только HTTP-ручкой
под `@role_required("admin")` плюс плашка в интерфейсе: консоли контейнера на
этом тарифе Amvera нет. Удалять при этом можно только заведомо пустые записи,
спорные — показывать человеку.

Сторож: `python scripts/test_shift_open_race.py` — 20 потоков на одну точку,
разбор дублей, HTTP-проверка 409/403.

## КРИТИЧЕСКИ ВАЖНО: то, что уходит во внешнюю систему, — данные, а не название

**Если от справочной записи зависит поведение внешней системы (банк, ПланФакт,
МойСклад), нужный ей параметр хранится отдельным полем и вводится человеком.
Выводить его регуляркой из названия записи нельзя.**

Название заводят руками, и оно живёт по своим законам: его пишут как удобно,
переименовывают, дублируют. Разбор названия работает ровно до первого варианта,
который назвали иначе, — и ломается молча, потому что внешняя система принимает
запрос и просто теряет параметр.

Так 04.09.2026 счета уходили в Модульбанк без НДС (счёт REF-000168). Ставку
брали регуляркой из названия варианта справочника: `20%` разбиралось, а
`С НДС`, `НДС 20/120`, `20` — нет, и в платёжку шло бесполезное `НДС: С НДС.`.
Банк платёжку принимал, поле НДС в кабинете оставалось пустым, ошибки не было
нигде. Вылезло это через три недели после самого фикса — когда НДС сделали
обязательным и варианты стали выбирать все подряд.

- **Поле в схеме, а не разбор строки.** `invoice_vat_options.rate`:
  число — ставка, `0` — без налога, `NULL` — не задана.
- **Разбор названия оставляем только для разового бэкфилла** существующих
  записей. Что не разобралось — остаётся пустым и видно в справочнике,
  а не заполняется «наиболее вероятным» значением.
- **Пустой параметр останавливает отправку** с внятным текстом («у варианта
  НДС «С НДС» не задана ставка»), а не уезжает во внешнюю систему как есть.
  Проверка стоит на самой отправке: валидация в форме покрывает только тот
  путь, по которому шёл автор, а ручку зовут ещё и массовые действия.
- **Сохраняй то, что реально ушло** (`invoice_bank_documents` + кнопка
  «Платёжка в банк»). Вопрос «что мы им отправили» возникает всегда, и
  отвечать на него чтением кода — потерянный час.
- **Значения для построчных форматов (1С-обмен) чистим от `\r\n\t`**:
  перевод строки из textarea разрывает документ, и хвост поля пропадает.

## КРИТИЧЕСКИ ВАЖНО: количество из внешней системы — не безразмерное число

**Прежде чем умножать `quantity` на что-либо, ответь, в чём оно меряется.
Если в разных строках по-разному — умножать нельзя, нужна единица измерения
отдельным полем.**

В RetailCRM и МойСкладе `quantity` — это штуки у букета, граммы у клубники,
стебли у розы, метры у ленты. Формула `Σ количество × вес` выглядит очевидной
и молча превращает 600 г клубники в 600 заказов. Так 07.09.2026 модуль
«Загрузка салонов» показывал не загрузку, а граммы: «Клубника» — 3.7% позиций
и **71% всей нагрузки**, 6.6% заказов давали 75.5% нагрузки, один сборный
заказ съедал ёмкость дня.

- **Базовая единица — сущность, а не её состав.** Заказ весит заказ; позиции
  только уточняют. Модель «база + надбавки» устойчива к тому, как заведены
  строки: один и тот же букет бывает и одной позицией из каталога, и четырьмя
  строками компонентов.
- **Неизвестное не должно раздувать.** «Вес по умолчанию» для нового товара
  звучит осторожно, но это ноль наоборот: неизвестный товар получает право
  съесть ёмкость дня. Правильный дефолт — не участвовать в надбавках.
- **База начисления — поле, а не догадка по названию.** «за штуку / за позицию
  / за 100 г» вводит человек. Регулярка по названию сломается на «Винограде» и
  «Бананах» — они тоже в граммах (см. раздел про параметры для внешних систем).
- **Проверяй на реальных данных, а не на примере.** Медиана заказа была 1, а
  p95 — 38 при максимуме 2001. Средние ничего не показывают, ошибка живёт в
  хвосте: «сколько процентов нагрузки дают 5% заказов» — тот вопрос, который
  её вскрывает.
- **Смена формулы требует бэкфилла.** Пересчитать уже накопленное разово и под
  отметкой в `sync_state`, иначе старые числа живут до следующего глубокого
  синка, а подсказки норм («сколько собирали на самом деле») считаются по ним.
- **Меняется единица измерения поля — заводится НОВОЕ поле.** «6 единиц в час»
  и «6 флористов в смене» выглядят одинаково и значат разное; конвертация
  старого значения «по коэффициенту» — это выдуманные данные, которые уже
  никто не отличит от введённых руками. Новая колонка рядом со старой, плашка
  «задано в старых единицах — перезадайте», и обе живут вместе, пока модель не
  переключена. Девять салонов по одному значению — пять минут работы человека.
- **Подсказка под полем обязана быть в единицах этого поля.** «За месяц
  собирали 6,2» под полем «флористов в смене» применят как есть, и салон
  получит шесть человек вместо одного. Пересчитывать в подсказке, а не в
  голове у читающего.

Сторожа: `python scripts/test_salon_load.py` (разделы 14–15),
`python scripts/test_ready_slot.py` (разделы 9–10).

## КРИТИЧЕСКИ ВАЖНО: у внешнего API есть не только таймаут, но и квота

**Прежде чем звать внешний API из интерфейса или планировщика, ответь: сколько
запросов в месяц позволяет тариф и сколько их сделает твой код. Остаток квоты
из заголовков ответа надо запоминать и показывать — до того, как она кончится.**

Мы привыкли защищаться от медленного ответа (таймаут, ретраи, «не звать из
обработчика»), и совсем не защищались от исчерпания лимита. У ПланФакта лимит
не посекундный, а **месячный: 2500 запросов**, то есть ≈83 в сутки на весь
модуль. 07.09.2026 он кончился к седьмому числу месяца, и ПланФакт стал
отвечать `403` на любой запрос: встали остатки карт, разноска счетов и фоновая
разноска трат. Узнали об этом от владельца — по жалобе, что в «Остатках на
картах» написано «ПланФакт не ответил».

Три причины, все системные:

- **Планировщик с частым тиком.** Разноска карт ходила раз в 15 минут и при
  непустой очереди тратила минимум 2 запроса за тик — ~200 в сутки, месячная
  квота за неделю. Тик выбирается из срочности задачи и цены запроса, а не «ну
  пусть будет почаще».
- **Вечный кандидат в очереди.** Заявка, которая не уедет никогда (не настроено
  сопоставление), заставляла ходить наружу каждый тик. Упавшая задача
  повторяется с отсрочкой (`FAILED_RETRY_SECONDS`), а отсрочка снимается,
  когда починили её причину, — не по таймеру.
- **Справочник, который грузится на каждое открытие вкладки.** Кэш в памяти
  воркера не считается: воркеров два, деплой его стирает. Кэш общий, в базе,
  с TTL по скорости изменения данных (для справочников — часы).

Что обязано быть у любого клиента к внешнему API:

- **Заголовки квоты читаются в одном месте — внутри `request()`** (см.
  `src/planfact/quota.py`): `X-Quota-Limit/Used/Remaining/Reset`. Остаток
  запоминается, переживает перезапуск и виден обоим воркерам.
- **Остаток показан в интерфейсе и в `/health`, пока он ещё есть.** Смысл — в
  предупреждении, а не в объяснении задним числом.
- **Исчерпание — отдельная новость, а не «сервис не ответил».** Это разные
  действия человека: «расширить тариф» против «подождать». Текст ошибки должен
  их различать.
- **Пока квота не сброшена, наружу не ходим вообще**: каждый такой поход
  вернёт 403 и займёт воркер. Момент разблокировки — `X-Quota-Reset`.
- **Но блокировка обязана сама себя перепроверять.** Остаток приходит ТОЛЬКО
  в заголовке ответа, а ответа нет, пока мы заблокированы, — замкнутый круг:
  расширение тарифа для нас невидимо. 15.09.2026 лимит подняли с 2500 до
  50000, и модуль всё равно остался бы мёртвым до 1 октября — до сброса,
  записанного ещё старым тарифом. Раз в N часов исчерпанная квота тратит
  **один** запрос на пробу (`PROBE_AFTER_SECONDS`). Пробу расходует только то
  место, за которым сразу идёт отправка (`is_blocked()` в `request()`), а не
  ранние выходы по `error_text()` в модулях, — иначе она сгорает, а запрос
  всё равно не уходит.
- **Показываем последнее сохранённое** (с пометкой «устарело») вместо пустого
  экрана: цифра вчерашней свежести полезнее прочерка.

Сторож: `python scripts/test_planfact_quota.py`.

## КРИТИЧЕСКИ ВАЖНО: «подробности в логах сервера» — это подробности нигде

**Консоли у контейнера на нашем тарифе Amvera нет. Любой текст, отсылающий
человека к логам, равносилен отсутствию объяснения. Причину, которую назвала
внешняя система, надо сохранять в ту же запись, о которой идёт речь, и
показывать на экране.**

Клиент внешнего API обычно возвращает `None` на любую неудачу, а объяснение
пишет в лог. Наверх уходит безликое «не приняли», и запись повисает в статусе,
из которого человек не может выйти: он не знает, что чинить.

Так 15.09.2026 заявка СЧ-000287 висела с текстом «ПланФакт не принял операцию
(подробности в логах сервера)». ПланФакт при этом называл причину в
`errorMessage`/`errorCode` каждого отказа.

- **Клиент запоминает последнее объяснение** (`PlanFactClient.last_error`,
  заполняется внутри `request()` — там же, где читаются заголовки квоты).
  Сбрасывать в начале каждого запроса: иначе чужая ошибка приклеится к
  следующей записи в том же прогоне.
- **Разбирать штатные поля ответа, а не только HTTP-код.** У ПланФакта отказ
  приходит и с `200 OK` при `isSuccess: false`. `raise_for_status()` здесь
  вреден: он прячет тело ответа в исключение, из которого текст уже не достают.
- **Код ошибки сохранять вместе с текстом** — по нему ищут в документации.
- **Причина живёт в записи, а не в подсказке.** Атрибут `title` у бейджа не
  виден ни на телефоне, ни в Пульсе, и в него надо попасть курсором. Место
  причины — карточка записи (`iv2-syncerr` в модуле счетов).

Сторожа: `python scripts/test_planfact_quota.py` (раздел 13),
`python scripts/test_card_sync.py` (раздел 7).

## КРИТИЧЕСКИ ВАЖНО: «ещё рано» — это не «сломано»

**Прежде чем пометить запись ошибкой, ответь: её нельзя отправить вообще или
нельзя отправить СЕЙЧАС? Второе — не ошибка, и человека звать не надо.**

Красная плашка требует действия. Если действия не существует — она заставляет
искать поломку там, где её нет, а следующий прогон снова бьётся в тот же отказ
и тратит запросы.

15.09.2026 заявки СЧ-000287 и СЧ-000323 завели с датой оплаты на завтра.
ПланФакт отверг их: «Нельзя создать часть операции с подтвержденной в будущем
датой начисления (40)» — мы шлём `isCalculationCommitted: true` всегда. Заявки
висели «Ошибка разноски», хотя чинить было нечего: нужно было дождаться дня.

- **Отсеивать до отправки, а не по ответу.** Условие известно нам самим
  (`is_future_operation` в `cards_sync.py`): заведомо отвергаемый запрос не
  отправляется вовсе.
- **Показывать срок, а не тревогу:** «Уедет в ПланФакт 16.09» вместо «Ошибка
  разноски». Бейдж и плашка — нейтральные.
- **Снимать ранее записанную ложную ошибку отдельной командой.** Запись с
  ошибкой не попадает в обычную выборку кандидатов (отсрочка повтора), поэтому
  внутри цикла по кандидатам её не починить — плашка провисит всю отсрочку.
- **Сравнивать даты в поясе прода (UTC).** Салоны в UTC+5 и UTC+7, день у них
  наступает раньше: заявка уедет на несколько часов позже, чем могла бы, и это
  правильная сторона ошибки — обратная упрётся в отказ.

Сторож: `python scripts/test_card_sync.py` (раздел 9).

## КРИТИЧЕСКИ ВАЖНО: TLS российских API

**Любой новый клиент к российскому сервису обязан вешать на сессию
`trust_russian_ca` из `src/russian_ca.py`.**

Российские сервисы переходят на сертификаты НУЦ Минцифры, корня которых нет в
бандле `certifi`. Запрос падает ещё до отправки данных, а формулировка сбивает
с толку — «self-signed» относится к неизвестному корню, а не к сертификату сервиса:

```
SSLError: certificate verify failed: self-signed certificate in certificate chain
```

Так 2026-08-25 отвалилась отправка счетов в Модульбанк.

```python
import requests
from russian_ca import trust_russian_ca

session = requests.Session()
trust_russian_ca(session)
```

**Никогда не чинить это через `verify=False`** — это открывает MITM на платёжных
и складских API. Корень добавляется *к* штатному бандлу, остальные сайты
проверяются как раньше.

Через переменные окружения (`REQUESTS_CA_BUNDLE`, `SSL_CERT_FILE`) не починить:
у наших клиентов стоит `trust_env = False`, а он их отключает.

## КРИТИЧЕСКИ ВАЖНО: обязательное вложение обязано иметь путь дозагрузки

**Если проверка на отправке/согласовании требует файл, а единственное место
загрузки — форма создания, то любой обрыв сети превращает запись в мусор,
который нельзя ни починить, ни провести.**

Кнопка «добавить файл» в карточке — не удобство, а условие того, что проверка
вообще имеет право существовать. Без неё единственный выход из записи —
завести её заново и залить всё повторно.

Так жил модуль списаний до 14.09.2026. Фото крепилось к каждой позиции,
`uploadPositionPhoto` гасил ошибку внутри себя, а `submitWriteoff` всё равно
звал `closeCreateModal()`. Заявка создавалась, позиция оставалась без фото,
согласование отбивалось проверкой — и добавить фото было нечем: ручка
`POST /positions/<id>/attachments` существовала, а кнопки не было нигде.
Управляющий видел «платформа тупит» и «потом не даёт согласовать».

- **Загрузка возвращает результат, а не тост.** Функция вида
  `uploadX() -> true//false`; вызывающий решает, закрывать ли форму. Проглоченная
  ошибка плюс безусловное закрытие — это и есть механизм порчи данных.
- **Сбой не закрывает форму.** Запись уже создана — показываем её номер и
  кнопку «Повторить загрузку», которая дозаливает в ту же запись.
- **Дозагрузка живёт в карточке** и разрешена в тех статусах, где правка ещё
  осмысленна. Права — те же, что на сервере, и продублированы на сервере.
- **Удалить последнее обязательное вложение нельзя** — иначе запись возвращается
  ровно в непроводимое состояние. Проверка «не последнее» и удаление — одна
  транзакция под `BEGIN IMMEDIATE`: два клика по разным крестикам иначе снесут оба.
- **Пустой файл отбивается на сервере.** При обрыве он доезжает и выглядит как
  успешная загрузка.

**Фото с камеры не отправляется как есть.** Снимок телефона — 3–5 МБ и
4000×3000; клиент уменьшает до 1600 px по длинной стороне и жмёт в JPEG
(`src/dashboard/image-compress.js`, `window.BarhatImage`). Это 200–400 КБ вместо
мегабайтов и заодно снимает вопрос форматов: iPhone снимает в HEIC, который
белый список расширений просто не пропускал. Два условия обязательны:
`imageOrientation: 'from-image'` (иначе вертикальный кадр ляжет набок — canvas
не знает про EXIF, а `<img>` знает, поэтому баг не виден до отправки) и
**возврат оригинала при любом сбое**, потому что пустой файл превращается в
успешно созданную запись без вложения.

Сторожа: `python scripts/test_writeoff_photos.py`,
`node scripts/test_writeoff_form.js`, `node scripts/test_image_compress.js`.

## КРИТИЧЕСКИ ВАЖНО: перерисовка через innerHTML теряет прокрутку и фокус

**Если функция вида `renderX()` переписывает `host.innerHTML` целиком, она
обязана вернуть на место прокрутку — а действие, добавляющее элемент, ещё и
поставить в него курсор.**

Модули дашборда перерисовывают экран целиком: так проще держать разметку в
соответствии с состоянием, и обработчики вешаются заново одним `bindX()`. Цена —
браузер выбрасывает и позицию прокрутки, и фокус, и выделение в поле. На
длинной форме это выглядит как отдельный баг: заполнил строку распределения
внизу, нажал «Добавить строку» — и ты снова в шапке счёта (модуль счетов,
2026-08-31).

```js
function renderForm() {
    const restoreScroll = keepModalScroll(host);   // до перезаписи
    host.innerHTML = `...`;
    bindForm(host);
    restoreScroll();                                // после привязки
}
```

- **Чинить перерисовку, а не кнопку.** У бага всегда несколько входов: ту же
  форму перерисовывают удаление строки, автораскладка суммы, подстановка
  контрагента, смена значения в селекте.
- **Прокрутка бывает не одна.** У модалки скроллится и тело (`max-height` на
  десктопе), и внешний слой (на узком экране) — запоминать оба.
- **Восстанавливать только для того же объекта.** Открыли соседний счёт —
  прокрутка не его; сверять по `dataset`.
- **Поле ввода, живущее внутри перерисовки, требует ещё и каретки:**
  `focus()` + `setSelectionRange(len, len)`, иначе набор обрывается на первом
  символе. Где это мешает постоянно (поиск, суммы) — обновлять точечно, как
  `updateAllocationSummary`.

## КРИТИЧЕСКИ ВАЖНО: правка «для скорости» без замера на проде — это угадывание

**Локальный замер доказывает форму запроса (план, число обращений к базе), но
НЕ его цену. Цену определяет сетевой `/data`, и узнать её можно только на
проде. Значит: одна правка за деплой, замер до и после, а при ухудшении —
откат первым действием.**

16.09.2026 модуль курьеров чинили «на скорость» три раза подряд. Первая правка
была верной и подтверждённой (индекс: 430 мс → 28 мс на объёме прода). Вторая
— сокращение соединений с 5 до 3 — проверялась только локально, на быстром
диске и чистой базе: «стало меньше обращений, значит быстрее». После выкатки
лента отвечала 6–13 секунд, а затем сервис перестал отдавать даже статику,
то есть повисли все воркеры. Причина так и не была установлена — потому что
разбирать её начали поверх сломанного прода.

- **Две правки в одном деплое = неизвестно, какая виновата.** Выкатывать по
  одной, между ними — замер. Соблазн «заодно» стоит ровно того часа, который
  потом уходит на разделение причин.
- **Ухудшение метрики = откат, а не диагностика.** Прод не площадка для
  проверки гипотез: сначала вернуть рабочее состояние (`git revert`, пуш —
  он же перезапускает контейнер), потом разбираться на копии боевой базы.
- **Статика против ручки отделяет код от инфраструктуры** (см. раздел про
  `/health`). Если встала и статика — заняты воркеры, и виноват не SQL.
- **Экран обязан мягко переносить медленный ответ.** Список нельзя очищать
  до прихода данных: «медленно» превращается в «пусто», и человек видит
  сломанное приложение вместо задержки. Показывать прежние данные с пометкой,
  ставить таймаут на запрос, давать кнопку повтора.
- **Считать соединения полезно, но это не метрика скорости.** Число обращений
  — то, что можно проверить сторожем (`test_db_hot_path.py`); время ответа —
  то, что придётся мерить на проде руками. Не подменять одно другим.

**Не нашёл причину со второй попытки — встраивай измерение, а не правку.**
17.09.2026 причину тормозов ленты назвала разбивка по шагам внутри ручки
(`timings_ms` в `meta` + строка в лог при превышении порога): `query` 412–1720
мс при ДВУХ строках в ответе. До этого два дня ушло на догадки — «медленный
диск», «много соединений», — каждая из которых звучала убедительно и ни одна
не была причиной. Разбивка дала ответ за один запрос.

- **Мерить дешёвой ручкой.** `/health?full=1` читает четыре базы и занимает
  воркер на минуту-две: сам такой замер и создаёт «замедление», которое потом
  ищут в коде.
- **`fetch` в консоли меряет очередь браузера**, а не сервер: он держит шесть
  соединений на домен, и при повторных запусках числа растут линейно, как
  деградация. Смотреть надо `x-envoy-upstream-service-time` — чистое время
  Python, и запускать замер ОДИН раз.
- **Инструмент измерения проверяется как сторож.** Сниппет, читающий не то
  поле, печатает `undefined` и уводит в сторону хуже, чем его отсутствие.

**Фильтр по двум полям требует составного индекса: одиночные не складываются.**
Там же вскрылась причина: лента отбирает «город + день», а в схеме были два
отдельных индекса — по городу и по дате. SQLite берёт на таблицу ОДИН индекс,
выбрал город и перебирал все 16 750 заказов города за все времена, считая на
каждом коррелированный подзапрос, чтобы вернуть две строки за сегодня.
Составной `(city, delivery_date)` дал 4,10 мс → 0,04 мс.

- **Проверять планом, а не временем.** На тестовой базе разница незаметна
  (миллисекунды), на сетевом `/data` это секунды: цену определяет число
  прочитанных страниц. `EXPLAIN QUERY PLAN` на объёме прода — обязательная
  часть разбора, и он же годится в сторож (см. `test_courier_orders_api.py`).
- **Такое не ломается в один день.** Витрина росла, перебор дорожал
  постепенно — и «вдруг стало медленно» означает, что порог перешли неделю
  назад.

## КРИТИЧЕСКИ ВАЖНО: строку, которую разберёт чужой парсер, проверяй его разбором

**Если значение уходит туда, где его будет разбирать не твой код (адрес в
`location.href`, путь в файловой системе, имя хоста, SQL, HTML), проверка «по
началу строки» и любая другая проверка глазами — бессильна. Разбирать надо тем
же инструментом, что и потребитель, и сравнивать РЕЗУЛЬТАТ разбора.**

Свой взгляд видит символы. Парсер видит другое: он выбрасывает невидимое,
нормализует разделители и склеивает то, что выглядело раздельно. Между этими
двумя картинами и живёт обход — всегда молча, потому что проверка отрабатывает
и говорит «всё хорошо».

17.09.2026 так обошлась защита `?next=` на форме входа. Проверка звучала
исчерпывающе: «начинается с одного `/`, дальше не `/` и не `\`». Парсер адресов
по стандарту **выбрасывает табы и переводы строк** и приводит `\` к `/`,
поэтому `?next=/%09/чужой-домен` проходил её как свой путь, а браузер шёл на
`//чужой-домен`. Три написания из четырёх уезжали на чужой origin. Цена ровно
та, ради которой проверку и писали: человек вводит пароль на НАШЕЙ форме и по
ссылке из мессенджера уезжает на подделку.

- **Сравнивай разобранное, а не исходное.** `new URL(raw, origin).origin ===
  location.origin`, а не `raw.startsWith(...)`. То же для путей
  (`os.path.realpath` внутри разрешённого каталога, а не «нет ли `..`») и для
  имён хостов.
- **Сторож, который ищет слова в файле, ЗАКРЕПЛЯЕТ ошибку.** Первая версия
  проверяла наличие `startsWith('//')` — то есть охраняла ту самую бессильную
  строку. Сторож обязан ВЫПОЛНЯТЬ проверку на враждебных входах (образец:
  `scripts/test_login_next.js`, одиннадцать написаний) и падать на старой
  версии — это проверяется отдельно, до коммита.
- **Уверенный комментарий рядом с проверкой — не доказательство.** Здесь он
  был, и подробный: обход нашёл обязательный `/security-review` перед пушем.
  Правило «`/security-review` → `/review` перед деплоем» существует ровно для
  этого и пропускаться не должно даже на «мелкой правке интерфейса».

Сторож: `node scripts/test_login_next.js`.

## Как работать с планами (цикл 3 чатов)

```
Чат 1: создать черновой план + поиск аналогов
Чат 2: разбить на фазы с [ ] / [x]
Чат 3: критика каждой фазы (лучшее решение? конфликты? безопасность?)
Чат 4+: реализация фаза за фазой
```

Имя файла плана: `plans/YYYY-MM-DD-название-функции.md`

## Как выполнять задачи

**Структурируй любую задачу по схеме:**

```
Goal → Context → Constraints → Done when
```

| Элемент | Что это | Пример |
|---|---|---|
| **Goal** | Чёткая цель задачи | Исправить KeyError в /api/criteria |
| **Context** | Файлы, ошибки, документация | Читаю traceback, смотрю код в src/api/criteria.py |
| **Constraints** | Стандарты, архитектура, зависимости | Python 3.11, не сломать другие эндпоинты |
| **Done when** | Критерий завершения | Тест проходит, ошибка не воспроизводится |

Это резко снижает число холостых итераций.

**Сложные задачи требуют подробного плана:**

- **Задача сложная**, если: >3 шагов, затрагивает несколько файлов, новый функционал
- **Перед началом** → прописывай подробный план действий
- **План** → разбей на подзадачи, каждая с Goal → Done when
- **Только после плана** → начинаешь выполнение

**Загружай контекст upfront (даёт всё сразу):**

- **Не подкармливай по файлу** — давай сразу все релевантные файлы
- **Ошибка?** → давай traceback + все затронутые файлы одним сообщением
- **Новая задача?** → давай похожие файлы (примеры из кода) сразу
- **Если не хватает данных** → запрашивай сразу всё, а не по одному

Это устраняет циклы «агент не видит нужный модуль → правит не туда».

1. **Никогда не деплой, пока я не разрешу.**

4. **Каждая отдельная правка обязана оставлять файл рабочим.** Над репозиторием работают

   лежит на диске **сейчас** — вместе с твоей недоделанной половиной.
   08.09.2026 так уехал в прод INSERT, где имена колонок уже добавлены, а значения ещё
   нет: `statement uses 30, and there are 17 supplied` — встал глубокий синк заказов, то
   есть данные выплат курьерам, показателей и загрузки салонов одновременно.
   - Многострочный SQL, списки аргументов, сигнатуры — менять **одним** Edit'ом, даже
     если он большой. Разбил на два — коммить сразу после первого.
   - В общем файле коммить **только свою версию**: `git show HEAD:path > tmp`, наложить
     свои правки, `git hash-object -w` + `git update-index --cacheinfo`. Тогда твой
     коммит не утащит чужую незаконченную работу, а чужой — твою.
   - Проверять последствия не на своём рабочем дереве, а на чистой копии:
     `git worktree add --detach /tmp/check HEAD`. «У меня локально работает» ничего не
     говорит о том, что лежит в проде.

## Безопасность

- **Не читать `.env` и файлы с секретами** (поставить хук-защиту в `.claude/settings.json`)
- Любой устанавливаемый скилл/CLI из интернета — проверять: от создателя ли, нет ли вредоносного кода
- `.gitignore` заранее (`.env`, `.business/`): GitHub помнит всё — утёкшие ключи остаются в истории навсегда
- Не делать внешние запросы без явного разрешения

**КРИТИЧЕСКОЕ ПРАВИЛО: новая изменяющая ручка — `@require_ajax_header`.**
CSRF-токенов в проекте нет. Единственная защита — `SESSION_COOKIE_SAMESITE="Lax"`,
но сессиям из портала Пульс кука выдаётся с `SameSite=None` (иначе Chrome режет
её в чужом iframe), то есть **у большинства сотрудников защиты нет вообще**.

Проверять надо не «есть ли тело», а может ли запрос уйти без CORS-предпроверки:

- `POST` с `multipart/form-data`, `application/x-www-form-urlencoded` или вовсе
  без тела — **простой запрос**, его отправит обычная форма с чужого сайта.
  Нужен декоратор.
- `POST` с `Content-Type: application/json` и любой `DELETE`/`PUT` предпроверку
  требуют, поэтому защищены и так — но декоратор им не мешает.

Правка всегда парная: декоратор на сервере + `'X-Requested-With': 'barhat-dashboard'`
в клиенте, иначе ручка начнёт отвечать 403 на проде. В тестах ходить с тем же
заголовком и отдельно проверять, что **без** него приходит 403.

Так 15.09.2026 в модуле списаний уехали бы незащищёнными загрузка фото
(`multipart`) и **согласование** — `POST` без тела, который списывает остатки в
МойСклад необратимо. Подробности механики — докстрока `require_ajax_header`
в `src/auth.py`.

**КРИТИЧЕСКОЕ ПРАВИЛО `.env`:**
- `.env` — **только в корне проекта**, никогда не копировать никуда
- Все секреты берутся **только** из `.env` в корне проекта
- `.env` никуда не копируется: не в подпапки, не в деплой, не в бэкапы
- **НИКОГДА** не коммить `.env` в git (должен быть в `.gitignore`)
- Не удалять файлы без подтверждения
- Перед `git push`/деплоем агентов — `/security-review` → `/review`
