## Симптом от владельца

Счета `REF-000021` и `REF-000016` (это `match_code` счетов с id 21 и 16) **не разнесены
в ПланФакте**, при этом в разделе «Согласование счетов» оба показаны как **оплаченные**.
Во вкладке «Требует внимания» их тоже нет — сбой полностью беззвучный.

## Диагноз (сделан в прошлой сессии, перепроверять с нуля не нужно)

Статус `paid` в модуле ставится **тремя путями**, и только один из них пишет в ПланФакт:

| Путь | Пишет в ПланФакт |
|---|---|
| Синк ПланФакта `_run_planfact_sync` (`src/invoices/server.py:1453`) | да: `PUT /operations/outcome/{id}` → затем `mark_invoice_paid()` |
| Кнопка «Отметить оплаченным» (`src/dashboard/invoices-v2.js:1824` → `server.py:654`) | **нет**, только статус |
| Массовое действие «Оплачен» (`server.py:919`, `bulk-mark-paid`) | **нет**, только статус |

Ключевая строка — `src/invoices/server.py:1373-1374`:

```python
if invoice["status"] == "paid":
    return {"status": "skip"}
```

Синк использует статус `paid` как признак «уже разнесено в ПланФакт». Но `paid` ставится
и вручную. Отсюда цепочка: счёт отметили оплаченным руками → позже в ПланФакте появляется
операция с `REF-000016` в назначении → синк видит `status == 'paid'` → **молча пропускает
навсегда**. Операция остаётся нераспределённой.

Усугубляет ещё два обстоятельства:

1. Ранний `skip` стоит **до** записи в `invoice_planfact_unmatched`, поэтому счёт не
   попадает в «Требует внимания» — владелец узнаёт о проблеме только из ПланФакта.
2. Отдельного поля «разнесено в ПланФакт» в таблице `invoices` **нет вообще**
   (см. схему в `src/invoices/storage.py:160-192`) — признак один и он перегружен.

### Второй возможный слой — проверить на реальных данных

Если платёжку по этим счетам делали руками в банке, а не через автозагрузку из модуля,
в назначении платежа нет `REF-` кода, и `searchString="REF-"`
(`src/planfact/client.py:121`) операцию просто не вернёт. Это даёт ту же картину и
складывается с первой причиной. `_build_bank_payment_purpose` (`server.py:704`) ставит
`match_code` в начало назначения только при отправке через модуль.

## Задача

**Goal:** оплаченный любым способом счёт всё равно доезжает до ПланФакта, а если не доехал —
это видно владельцу, а не теряется молча.

Чинить **класс бага, а не два счёта**. Предлагаемое направление (согласовать с владельцем
до кода):

1. **Развести два разных факта.** Добавить в `invoices` поля `planfact_operation_id`
   и `planfact_synced_at`; синк проверяет их, а не статус. «Оплачен» остаётся фактом
   об оплате, «разнесён» — отдельным фактом.
2. **Убрать ранний `skip` для `paid`.** Счёт оплачен, но не разнесён — это нормальный
   кандидат на разноску, а не мусор. Проверки «не распределён» / «нет сопоставления
   салона-статьи» должны отрабатывать и для оплаченных счетов и попадать в
   `invoice_planfact_unmatched`.
3. **Ручная отметка оплаты не должна молчать** — либо сразу пробовать разнести, либо
   ставить счёт в состояние «ждёт разноски» и показывать это в интерфейсе (плитка/бейдж).
   Учесть: `mark_invoice_paid` умеет сразу отправлять счёт в архив
   (`_auto_archive_if_ready`) — неразнесённый счёт не должен исчезать из виду.
4. **Два текущих счёта** после фикса разнести прогоном синка. Если в назначении платежа
   в ПланФакте нет `REF-` — синк их не найдёт, и это отдельный разговор с владельцем
   (разнести руками либо дописать код в комментарий операции).

## Грабли этого модуля (проверено кровью, не наступать заново)

- **Миграция схемы — только `ADD COLUMN` под `BEGIN IMMEDIATE`**, образец рядом:
  `_ensure_invoice_comment_column` (`storage.py:532`). Никакого пересоздания таблиц:
  два gunicorn-воркера на проде стартуют параллельно, без блокировки это уже дважды
  роняло прод («duplicate column name», зависший логин).
- **`add_invoice_history` и `_auto_archive_if_ready` открывают свои соединения** — звать
  их только после `commit()` своего, иначе «database is locked».
- **`PUT /operations/outcome/{id}` — полная замена операции**, не PATCH: верхнеуровневые
  поля (`operationDate`, `accountId`, `comment`, `isCommitted`) берём из уже загруженной
  операции. Счёт списания лежит в `op["account"]["accountId"]`, сумма — в `op["value"]`;
  плоских `accountId`/`amount` у операции нет (на этом уже был инцидент 2026-08-18).
- **Ответы ПланФакта завёрнуты в `{"items": [...]}`** — не плоский массив.
- **TLS российских API**: любой новый клиент — через `trust_russian_ca` из
  `src/russian_ca.py`, никогда `verify=False`.
- **Внешние вызовы из UI-ручек** — короткий таймаут + кэш, иначе живой вызов блокирует
  оба воркера и кладёт весь сайт (уже было).
- **Диалоги только `window.BarhatUI`** (`src/dashboard/ui-dialog.js`): нативные
  `confirm`/`prompt` в iframe Пульса молча игнорируются.
- **Заголовки ответа проверять на живом ответе** (`curl -D -`), глобальный `after_request`
  молча выигрывает у вьюхи.
- **CSS нового раздела скоупить под `.iv2`**, модалки монтировать внутрь `#iv2Modals`.
- Правки фронта делать точечно: полная перезапись HTML/JS уже теряла обработчики,
  `node --check` такое не ловит — прогонять сверку «кнопка → обработчик»,
  «`$('#id')` → разметка».

## Как работать

Схема `Goal → Context → Constraints → Done when`. Сначала план фазами в
`plans/2026-08-26-планфакт-разноска.md`, согласование с владельцем, потом код по одной
фазе: реализация → статическая проверка → прогон на реальном бэкенде через Flask
`test_client` на временной базе (осторожно: прогон читает боевой `.env` и уходит в боевые
внешние API — блокировать сокеты) → отметки в плане → коммит → сводка владельцу →
ждать подтверждения на следующую фазу.

**Не деплоить без явного разрешения** — спрашивать каждый раз, а не один раз за сессию.
