### Суть задачи одним абзацем

Текущий раздел «Счета на оплату» неудобен: работа не приходит к согласующему сама,
согласование поштучное, скан не виден рядом с полями, вложение нельзя вставить из буфера.
Делаем **новый раздел на существующих таблицах и API** — миграции данных нет. Старый
раздел не трогаем ни строкой: он остаётся у админа архивом и служит точкой отката.
Новый раздел живёт на отдельной секции прав `invoices_v2` и первое время виден только
администратору.

### Порядок работы

Фазы идут по плану, по одной. Минимум для замены старого раздела — **фазы 1-6 и 10**;
фазы 8 (шаблоны) и 9 (платёжный борд) — улучшения сверх замены, их можно двигать.
Фаза 0 (выгрузка базы) обязательна перед фазами 7 и 8, которые меняют схему.

**Начинаем с Фазы 1 — каркас раздела.** Её Done when:
админ видит новый раздел с градиентной шапкой и счётчиком «N ждут вас», менеджер его
не видит, старый раздел работает без изменений.

После каждой фазы: обнови чекбоксы в плане, сделай коммит, покажи мне краткую сводку
изменений и жди подтверждения на следующую фазу.

### Что критично не забыть (найдено при критике плана, проверено по коду)

1. **`invoices_v2` даёт только пункт меню.** Все ручки счетов проверяют
   `@section_required("invoices")` (`src/auth.py:539`), поэтому доступ к данным идёт
   по старой секции. У админа она есть. Снимать её у сотрудников нельзя, пока
   `section_required` не научится принимать две секции — это отдельный пункт Фазы 10.
2. **Чек-лист нового модуля дашборда** — четыре места регистрации: `auth.py` (два места:
   `ROLE_SECTIONS` и список секций + `migrate_new_module_permissions`), `users.js` (метка),
   `script.js` (заголовок и инициализация), `index.html` (пункт навигации, `div.page`,
   подключение скрипта). Пропуск любого из них уже давал реальные баги.
3. **Диалоги — только `window.BarhatUI`** (`src/dashboard/ui-dialog.js`). Нативные
   `confirm`/`prompt` в iframe Пульса молча игнорируются, и кнопка выглядит сломанной.
4. **Экранирование — через `escapeHtml` модуля.** Трюк `div.textContent` не экранирует
   кавычку и молча режет `value="..."`.
5. **Время — через `window.BarhatTime`** (`src/dashboard/datetime.js`): в базе UTC,
   показываем по поясу устройства; `due_date` — календарная дата, не конвертируется.
6. **Стили нового раздела скоупить внутрь страницы**, чтобы `--bx-*` не задели остальной
   дашборд на `--barkhat-*`.

### Чего делать нельзя

- **Не менять схему БД** в фазах 1-6 и 9. Схему трогают только фазы 7 и 8, и только после
  того, как появится выгрузка базы (Фаза 0).
- **Не дублировать бизнес-логику** счетов. Новый фронт работает на существующем
  `invoices_bp`; недостающее добавляем аддитивно туда же, а не вторым модулем.
- **Не править `src/dashboard/invoices.js`** и разметку старого раздела — он заморожен.
- **Не деплоить без моего явного разрешения.** Коммитить — часто и только свои изменения.

### Как отвечать

Работай по схеме Goal → Context → Constraints → Done when. Сложную фазу сначала разбей
на подзадачи, потом делай. Проверяй результат статически (у каждой кнопки есть обработчик,
каждый `$('#id')` существует в разметке, каждое `data-act` обработано) — на этом уже
ловились молча неработающие кнопки.
